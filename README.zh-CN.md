# spec-flow

**给 AI 编码 agent 用的一套流程规矩。** 把它 clone 进你的 agent 的技能目录；此后你交办一件值得先设计的活时，agent 会先跟你把「要做什么」谈定，**再**动代码——而它产出的每一份东西都要过一道闸，**由你**决定给它多少审核。

流程本身没有运行时或服务。它是 agent 读的 Markdown，加上纸面痕迹：代码前有 spec、动手前有 issue、两者有永久链接。代码地图默认停用；普通任务通过源码检索、实际 diff 和相关测试核对影响。

本次正文预算为 **4,700 字符**、frontmatter **500**、整份 **5,200**，均含换行。[`scripts/check-docs.sh`](scripts/check-docs.sh) 同时核三笔账，并拦额外元信息和多行 description。字符预算不是跨客户端的 token 或压缩保留保证；动作细则使用当刻必须读，压缩丢失后重新读。

**每条规矩都有可回溯来源。** [`references/rationale.md`](references/rationale.md) 有 **27 条记录**，包括日期、实测、决定、代价和验证边界。

## 用起来是什么样

两边你打的字一模一样：**「给个人资料页加个头像上传」**。

**没有它**，agent 当场开写。四十分钟后你拿到一个横跨十一个文件的 diff、一张你没要过的数据库表，和一个它自己定的体积上限。它是怎么决定的——你得读代码才知道。

**有它**，agent 两分钟就回来，带着三个它替不了你决定的问题——文件存哪、要不要支持手机、40MB 的上传该怎么办——此外什么都没有。接着它写一份 spec：改什么、**刻意不碰什么**、每部分怎么验。这份 spec 单独开一个 PR，代码一行都还没有，然后你收到一张卡，问这份东西要多少审核——**不审 / 轻审 / 重审 / 重审 + 变异**。你点一个。它这才在自己的 git worktree 里开工，合并前再给你一张卡。

**那个本来要等到第四十分钟才暴露的误解，现在第二分钟就暴露了。**

<!-- s:problem -->
## 它解决什么

编码 agent 栽跟头的地方不在某一步里面，在**接缝**上：

- **在你的交代和它的理解之间**——它拿着半成形的需求就开写，你到看 diff 时才撞见误解；
- **在一份交付物和下一份之间**——它一口气干完一大坨，中间没有一处能拦住那个走错的弯，整坨都建在它上面；
- **在 agent 和「检查 agent 的那个东西」之间**——它报告「已由独立审核复核」，而那个审核是它自己派的、自己写的 prompt、自己给的角度，还是想要放行的那一方自己挑的；
- **在两个 agent 之间**——两边都把同一个 issue 读成「没人认领」，同一件事做了两遍；
- **在上个月的决定和今天的活之间**——一次改动背后的道理留在一场没人能重新打开的对话里。

这些都不是模型能力问题，也不是「某一步再努力一点」能修的。它们是**没人认领的边界**。

<!-- s:scars -->
## 这些规矩是从哪来的

不是从理论来的。每条规矩都是一次具体事故的沉淀，日期和数字都记在 [`references/rationale.md`](references/rationale.md) 里。其中五个案例：

- **一条判据放宽了，别处一个没动。** IDC 判据从「CIDR 段」扩成「CIDR ∪ ASN」，只改了那一句——机制、实现、实施步骤、验收四处还都在描述旧行为，父文档总纲也没改。照那份 spec 施工，做出来是 CIDR-only。独立审核抓出 2 处严重。→ **R1**：改一条判据，它的每个落点都要同步。
- **两个 agent 认领了同一个 issue。** 两边都把 *open* 读成「没人在做」，同一件事做了两遍，废掉一份。→ **R7**：认领的证据是 worktree 建成了，不是 issue 的状态。
- **一家客户从十二份拆分里漏掉了。** 其中两份各自写了一遍「这个账号是否启用」——一份查标志位，另一份只查「按姓名查得到行」。这个差异没人认领，实施期才炸出来。→ **R15**：拆分要写下来的是依赖边，不只是文件地盘。
- **一份 spec，被改了十七次。** 一个项目的唯一那份 spec 从 448 行长到 762 行，横跨 17 个提交，其中 14 个改的是正文。它的 owner 最后在 agent 干到一半时打断：*「我们这是新需求，写新的 spec，别老是改以前的 spec，越改越乱。」* → **R12**：改已合并的 spec 是一张要你点的卡，不是可以自己拿的主意。
- **五个进程，一把锁。** 实测：五个进程抢同一个号，恰好一个建成了 worktree，其余四个全被拒。→ **R6**：这把锁是 git 的，不是我们发明的。

<!-- s:what -->
## 它怎么解决

**两段流程，共用一道闸。** 每一步认领上面的一条接缝。

- **段一 · 方案期** —— 描述需求 → 一起确认需求 → 出 spec → 过 PR 和闸 → 合并 → 开 issue。此时一行代码都不写。
- **段二 · 实施期** —— 认领 issue → 实施 → 过闸 → 合并 → 回填 issue、放锁。

| 这一步 | 它认领的接缝 |
|---|---|
| 确认需求是一道硬关口——你没点头，spec 文件碰都不许碰 | 交代 ↔ 理解 |
| 每份交付物各过各的闸 | 一份交付物 ↔ 下一份 |
| agent 不许替自己产出审核结论 | agent ↔ 检查它的东西 |
| 认领 issue = 建一个以它命名的 worktree | 一个 agent ↔ 另一个 |
| issue 锚着 spec 合并后的永久链接 | 上个月 ↔ 今天 |

<!-- s:self-review -->
## 唯一值得直接拿走的一条：分身不是第二个人

agent 派出去的一切都还是它自己——同一件事、同一段 prompt、同一个看问题的框架，而且是想要放行的那一方自己挑的。所以分身的结论只有它自己的分量，一分不多。

因此 spec-flow 禁止 agent 替自己产出审核结论：审不审、审哪档由你点，它不许自己派一个来替它判。某一步真的需要一份不属于它的意见时，这一步就停下来，等人。

<!-- s:smooth -->
## 为什么它不累赘

它不是往 agent 身上绑约束，是把返工挪到返工便宜的地方去——而且每个机制都刻意做到**尽量少占用你的注意力**。

| 这么设计 | 丝滑在哪 |
|---|---|
| 档位按每份交付物当场点，不可沿用 | 成本跟着风险走：**不审 / 轻审 / 重审 / 重审 + 变异**。改一行文档零成本，改核心才上两个审核。没有一刀切的口径要吵。 |
| 卡没答，绝不替你加码 | 六张卡的默认值全都躲开「往前加东西」那一侧：不审、不合、不出 spec、不纳入、不动笔。 |
| 打断按「要不要你答」分层 | 新增的机制单独一张卡——那正是你事后会问「这是什么、哪来的」的东西。agent 自己定的其余细节（默认值、命名、落点）统一列在末尾一块，扫一眼就行，不逐项问。 |
| 判断权从 agent 手里收走 | 它不许自己判「这次算不算核心」。省掉的不只是风险，是那场论证。 |
| 每条规矩都点出它从哪次事故来 | 不认同一条规矩？它的出处就在一跳之外。不用从头重新吵。 |

<!-- s:longrun -->
## 它凭什么扛得住长活

**状态存在 git 里，不存在 agent 的脑袋里。**

| 想知道 | 写在哪 | 为什么信得过 |
|---|---|---|
| 谁在做 | worktree 的名字——锁本身 | 开 `issue-42` 开得成 = 没人做；被拒 = 有人在做。（`git worktree list` 能一眼看全，但锁本身是「开得成」这件事。）没有另一张会对不上的任务分配表。 |
| 做到哪了 | issue 的状态和 PR | 持久，跨会话可读，换台机器、交给别人，还是同一份。 |
| 当初为什么这么做 | `docs/specs/` 里的 spec，issue 链过去 | 它过了闸、是人话、跟着代码一起版本化——能 diff、能 blame、能回滚。 |

把这类东西存在自己私有索引里的工具，漂了不会告诉你。这个不会：git 会在出事的那一刻当场喊出来。

<!-- s:limits -->
## 它不做什么

- **它不记得过程。** 试过什么又放弃了、哪个死胡同耗了一小时、你上次卡在第几步——没写下来的就没了。写下来的那部分是审核留痕：每条发现和它的处置，追加在 spec 末尾。所以新会话读到的是「要做什么、做到哪、上次抓出了什么」，读不到「那条没走的路为什么没走通」。
- **它不是运行时。** 这里没有任何东西会去调度 agent、给一次跑留检查点、或者把凌晨三点挂掉的那次续起来。它假定你在场，站在闸前面。
- **它大部分靠自觉，不是靠强制。** 这些是请 agent 遵守的规矩，不是逼它遵守的机制。真正被强制的那部分，靠的是 git（worktree 那把锁）和本仓自己的检查脚本。
- **它假定你用 GitHub。** issue 和 PR 在这里是承重墙，不是装饰。

## 装

```bash
git clone https://github.com/Strelizialeomon/spec-flow.git ~/.claude/skills/spec-flow
```

这是技能安装，不是项目接入或工具配置。Claude Code 从 `~/.claude/skills/<名字>/SKILL.md` 读个人 skill；在该检出里 `git pull` 更新。其他客户端使用各自的技能发现路径。

习惯把仓放在别处（作者就是这样），就 clone 到别处再软链进来：

```bash
git clone https://github.com/Strelizialeomon/spec-flow.git ~/code/spec-flow
ln -s ~/code/spec-flow ~/.claude/skills/spec-flow
```

要求：一个能发现 skills、跑 shell（`git worktree`）、开 PR（`gh`）的 agent。正文是 Markdown，但发现链、权限和压缩行为仍需真实客户端验证；文档检查绿不证明客户端读到或遵守了规则。

## 怎么用

描述一件值得先设计的活就能触发它——比如「这个改动要动接口、数据库和前端」——也可以直接点名调用。接下来 agent 会就它判断不了的岔路问你，把 spec 写进 `docs/specs/<日期>-<名字>.md`，开 PR，然后把审核档位摆给你点。

也可以从中间进：说「做 #12」就从段二开始，同样要过闸才能合。

首次接入说 **「把 spec-flow 应用到本项目」**：写入 `AGENTS.md` 指针，仅在已有 `CLAUDE.md` 时补 `@AGENTS.md`，不抄正文。**「更新本项目的 spec-flow 接入」** 显式校验和升级旧入口，包括已采用的 ADR 动作与旧文档读序；重复执行幂等、不自动启用未采用选修，普通任务不顺手改制度。

**代码地图默认停用。** 普通任务和接入升级不查图、不检查地图就绪、不补配置，仍按需用源码检索、实际 diff 和相关测试核影响。只有用户另行明确要求试用 / 恢复时才读[地图细则](references/code-map.md)；旧接入、工具已安装或现有配置不代表恢复。当次试用不授权长期启用、安装或 Hook，试用结果与停用决定见 rationale R27。

已采用 ADR 的项目在调查、旧 issue 或免方案期首次实施前检索，明确长期拍板后按条件记录，收尾核本次处理。实施前必须读当前获批施工 spec；只有历史规格在追溯时按需读。这些嵌在已有动作，不增加步骤或三道固定 ADR 闸。

## 本仓自己就是样板

spec-flow 是用 spec-flow 开发的。2026-10-16 这个时点的账面：66 个已合并 PR、17 个 issue、16 份 spec（`docs/specs/`）。每份 spec 是一次改动的设计记录；过了审核的那些 PR，讨论里留着发现——包括后来改掉了规矩的发现。

规矩按 `R` 编号被引用，形如 `（依据：rationale R12）`，每一条都指进 [`references/rationale.md`](references/rationale.md)。**那个文件记录完整案例与边界**：IDC 那条判据在一处放宽而另外四处连同父文档都没改；那条让「没有 bug」不再等于「我们保证以后永不出错」的完成标准；以及两个已采用项目怎样消费与记录架构决定的对照及其证据边界。

## 文件

| 文件 | 装什么 |
|---|---|
| `SKILL.md` | 流程正文——agent 加载的就是它 |
| `AGENTS.md` | 本仓的维护规矩（给 agent 看的） |
| `CLAUDE.md` | 一行 `@AGENTS.md` |
| `references/rationale.md` | 每条规矩的依据：案例、实测、决定（R1–R27） |
| `references/gate-details.md` | 闸怎么执行：审核、文档检查、一卡盖批 |
| `references/worktree-lock.md` | 认领 issue；worktree 那把锁，以及它怎么坏 |
| `references/spec-revision-sync.md` | 改一条判据要同步所有落点 |
| `references/code-map.md` | 默认停用；明确试用时的查询、覆盖边界与回落细则 |
| `references/done-criteria.md` | 完成标准、观察式收尾、三类例外 |
| `references/split-large-spec.md` | 拆大 spec：交付物地图、依赖台账 |
| `references/adr-decision-records.md` | 可选：架构决策记录（ADR） |
| `references/documentation-lifecycle.md` | 可选：spec / ADR / issue 分工 |
| `references/issue-status-labels.md` | 可选：issue 状态标签 |
| `references/apply-to-project.md` | 应用、显式升级、指针模板与资产边界；地图恢复须明确请求 |
| `references/adoption-model.md` | 采纳模型的历史解释，不增加流程义务 |
| `docs/maintainer-notes.md` | 本仓自己的说明：这份检出怎么接的线、最早的提交为什么是重建的 |
| `scripts/check-docs.sh` | 正文 / frontmatter / 整份预算、路径、双语同步、参考表区域采用护栏 |

流程正文是 `SKILL.md`——这份 README 与它说法不一致时，以 `SKILL.md` 为准。哪个参考什么时候读，见 `SKILL.md` 末尾那张表。

## 参与

小步来。开个 issue，或者直接发 PR。一条约定：改动新增或修改了规矩，就把背后的案例记进 `references/rationale.md`、编个新 `R` 号——这里的规矩得指得出发生过的事。
