## 背景：要解什么问题

agent 在方案 / spec / 实施里加入用户没拍板的机制或细节，用户事后才发现。
2026-09-15 ~ 09-22 一周会话挖掘（Kimi Code + Claude Code 两侧，约 200 个会话窗口，30 多起相关事件，一半以上是用户事后才发现）确认四种反复形态：

1. **机制混在方案书里被批量点头滑过**——09-16 豁免名单事件：机制随 PR #2 合并进 SKILL.md，第二天用户才惊觉「豁免名单？是什么奇奇怪怪的东西」，当天整张砍掉。
2. **审核审了「设计对不对」，没审「这个概念该不该存在」**——09-20 brand 映射层：用户被迫就细节拍板 4 次，从没拍过「要不要这个概念本身」（「这破玩意我记得我已经决策了好几次了」），最终整层砍掉，22 个文件减法返工。
3. **用户只能拦住 agent 说出来的部分**——09-16 ruimei 删按钮（Hard scope 硬指令在场仍被违反，第二天才发现：「你把这个按钮给我弄丢了」）；09-15 xhs #806 臆造评论区信号（被追问时现场编造设计意图，agent 自认「那是我自己编的解释」）。
4. **扩权落在流程管不到的地方**——09-20「哪来的规矩？我咋不知道」（一次性指令被写进跨会话记忆、以「用户定的规矩」措辞执行）；09-16 spec-flow 自身漂移（五个窗口累计 45 次修改，用户「没有印象同意过」）。

机制结论（owner 2026-09-22 拍板）：不是把方案写得更细给用户审，而是把「要拍板的东西」从方案正文里拆出来单列成短清单——用户拍「要不要它存在」，不审「它设计得多细」。
业界对照（[Anthropic 官方 best practices](https://code.claude.com/docs/en/best-practices)）：「state what is out of scope」是好 spec 必备项；「check that nothing outside the task's scope changed」是官方列出的新鲜上下文复审项；并明示审核写狠了会反向逼出过度设计。GitHub spec-kit 用[强制 Assumptions 段落](https://raw.githubusercontent.com/github/spec-kit/main/templates/spec-template.md)收编 agent 自定的默认值。

## 机制清单（本 spec 自身新增的机制，按本 spec 的规矩先自列）

| # | 机制 | 解决什么 | 没有它会怎样 |
|---|---|---|---|
| 1 | 机制清单（方案期 + spec 期） | 机制混在正文被批量点头 | 形态 1 / 2 继续 |
| 2 | 自定细节清单（spec 文末） | agent 自定的默认值不留痕 | 形态 3 的 spec 侧继续 |
| 3 | 范围外对账（实施期，并入既有审核档位、不加价；不审档由实施 agent 合并前自查兜底） | 不点审核时范围洞全开 | 形态 3 的实施侧继续 |
| 4 | 记忆写入闸（AGENTS.md） | 一次性指令被升格成长期规矩 | 形态 4 的记忆侧继续 |

## 改动面（三处）

### 改动 1：SKILL.md「各步细则」新增第 2/3 步小节——两张清单

插入位置：「各步细则」标题之后、第 4 步小节之前。条文草稿：

> **第 2/3 步（确认需求 / 出 spec）——两张清单，方案期和 spec 期都管：**
>
> - **机制清单**：方案 / spec 每新增一个机制、概念或抽象，单列一条，每条一行写清「解决什么 / 没有它会怎样」。判定口径：用户事后可能问「这是什么 / 哪来的」的，都算。没有新增就写「无新增机制」——清单不许空着不表态。呈现时配卡「全要 / 全砍 / 逐项挑」——机制不许混在方案正文里让用户批量点头。
> - **自定细节清单**：spec 没写死、agent 自己定的细节（默认值、判定规则、命名、落点），逐条列在 spec 末尾「自定细节」节，每条一行。用户扫一眼、不逐项问；该列不列 = 违规。
> - spec 期审核对应加一条核对项：spec 里的机制 ↔ 机制清单逐条对得上，清单外有机制 = 漏报。

### 改动 2：SKILL.md 第 4 步——对账并入既有档位，不加价

- 档位表「轻审」行定位改为：「spec 期 = 规格符合性核对 + 机制清单完整性；实施期 = 对抗式找 bug + 范围外对账」。**派发数与约时不变**（1 个 ≈5 分钟）。
- 档位表下加一行说明：清单完整性 / 范围外对账两项**不新增派发**——轻审由那 1 个 agent 一并做；重审并进「规格符合性」那一路，不新增第三路。
- 「⚠️ 轻审只有 1 个 agent，定位按阶段劈」一段补一句桥接：实施期定位由「对抗式找 bug」扩为「对抗式找 bug + 范围外对账」；该段关于严重发现分布的实测论据不变。
- 「执行时按老规矩」加两条：
  - 范围外对账只报「spec 改动面之外的变更」，不扩展成质量意见——审核 prompt 写狠了会反向逼实施方加防御层（[Anthropic 官方明示的代价](https://code.claude.com/docs/en/best-practices)）。
  - 「不审」档不是无账：实施 agent 合并 PR 前自己拿 diff 对 spec 改动面过一遍；发现范围外变更必须停下报给用户处置，不许静默留下。零成本、只报异常、不算派审核（不破「档位用户点」）。

### 改动 3：`~/.agents/AGENTS.md`「§四 配套硬规则」末尾加一条

> - **记忆写入先问**：每次要把任何内容写进跨会话记忆前，先把那条内容原样亮出来问一句「要不要记」——点头才写，没点头不写。一次性指令、agent 自己的推断、规矩类条目，同此一道闸。
