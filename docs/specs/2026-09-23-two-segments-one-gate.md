对照：其余 15 个走到实施合并的会话摆卡全合规，共性是「skill 被加载、且规则恰好在视野里」。即：**规则文本本身有效，失效的是它的可达性。**

三个结构性根因（与漏法一一对应）：

1. **骨架没有实施期的位置**——六步到 issue 为止；「实施 PR 合并前走同一张卡」只是第 4 步细则的一行（SKILL.md:53-54），而骨架头条写「第 4 步摆完卡即为走完」（SKILL.md:8）：spec 卡一摆，第 4 步打勾关闭，实施期再无触发点。漏法 1/2/7 由此来。
2. **措辞反噬**——「走同一张卡」「档位与代价不分期」字面可读成「档位两期通用」；「不审 → 不追问」（SKILL.md:52）强化不再问。漏法 1 的自释原文正是这个读法。
3. **只做实施的会话两头够不着**——description 触发词只管「描述需求 / 要设计 / 动多端」（SKILL.md:3），「请你做 #N」不匹配，skill 不加载（漏法 3 自白）；项目 AGENTS.md 指针块按设计不复述步骤（`references/apply-to-project.md` §二），也没有「实施期摆卡」这句。漏法 3/4/5 由此来。

owner 拍板（2026-09-23 对话）：**不打补丁，重梳六步与实施 PR 的关系**——原话「长期打补丁一定会导致这个项目重新走 sop-better 的老路」。结构选型经卡片拍板为「两段一闸」（备选：线性九步、交付物循环）；机制清单 5 条经卡片拍板「全要」。

## 机制清单（本 spec 新增的机制）

| # | 机制 | 解决什么 | 没有它会怎样 |
|---|---|---|---|
| 1 | **闸**（独立一节，两段共用）：审核卡从「第 4 步的一步」改为合并闸门，每份交付物合并前过一道 | 实施期摆卡没有骨架位置 | 实施期审核继续当脚注，接着漏 |
| 2 | **段二·实施期**（第 7-9 步）：认领（锁）→ 实施 → 过闸 → 合并回填关单；「认领与防撞车」从脚注升正文 | 只做实施的会话没有自己的流程 | 实施会话不知道从哪进 |
| 3 | **两个入口**：description 与指针模板各加实施入口触发语 | 实施会话不加载 skill | 段二写得再好，实施会话看不见 |
| 4 | **交付物口径**：闸按交付物过——spec、实施成果（代码或交付型文档）必过；回填 issue 号 / 状态行 / 索引等无新内容的机械文档变更免过，走长期授权 | 文档 PR 摆一半漏一半的漂移（实录：同一会话 8 个文档 PR 摆 4 漏 4） | 口径继续靠 agent 现场发挥 |
| 5 | **一卡盖批须声明**：一次出 N 份实施 PR 允许一张卡盖本批，卡上必须写明「共 N 份 × 档 = N 个 agent / Y 分钟」；未声明份数的，每份各过一道 | 多份 PR 要么逐份摆卡啰嗦、要么静默漏 | 批处理继续靠运气 |

口径依据（机制 4/5）：交付物漏卡 owner 抓过 3 次（漏法 3/4/5），回填类 PR 静默合并从未被抱怨（多例）；一卡盖批 owner 点头过（#370 五批次一卡，09-23），未声明静默漏也发生过（漏法 7）。

## 改动面（四个文件）

### 改动 1：SKILL.md —— 骨架重排为「两段一闸」

新骨架（**细则逐字搬家、只动骨架**，语义改动仅限本节列出各处）：

```
段一·方案期（新需求从这里进）
  1 用户描述需求
  2 一起确认需求
  3 出 spec（用户点头之后才动 spec 文件）
  4 过闸：spec PR 合并前（→ 闸节）
  5 按需要修订 → 开 PR 合并（第 5 步硬规矩原文保留）
  6 开 issue，正文锚 spec 永久链接

段二·实施期（认领 issue 从这里进）
  7 认领 issue（锁 = worktree 分支名，现「认领与防撞车」节升入）
  8 实施（worktree 规矩照旧）
  9 过闸：实施 PR 合并前（→ 闸节）→ 合并 → 回填 issue、关单、放锁

闸（独立一节，两段共用）
```

逐条落点：

- **H1 与引言**：`# 复杂活的六步流程` → `# 复杂活的两段流程`（副题：方案期六步 + 实施期三步，共用一道合并闸）；引言「按顺序走，别跳步、别把两步合成一步」保留；「第 4 步摆完卡即为走完」改为闸节统一口径「**摆完卡这道闸即为过完**——用户点『不审』也算过完」。
- **第 4 步**改为「过闸（spec PR 合并前）」：本步只留 spec 期特有细则（两张清单完整性核对、审核修订记录表），档位表与通用规矩全部移入闸节。
- **现 53-54 行废止**：「实施 PR 合并前走同一张卡」「档位与代价不分期」两句删除，由闸节取代——闸节明文「**闸按交付物过：每份交付各过一道，档位当场点；不存在可沿用的档位**」（结构上消灭「跨期」问题，不靠禁令看住）。
- **闸节**（位置：两段骨架之后、「工作区规矩」之前）收编现第 4 步全部通用细则，**逐字保留**：档位表（不审 / 轻审 / 重审 / 重审+变异及代价）、agent 不自派不判断、没点 / 点了别的按「不审」走不追问、项目禁档不摆、摆卡算账（N 份 × 档）、轻审定位随阶段换、变异只跟重审捆绑、执行老规矩（只读审 / `file:line` 逐条核对 / 给足上下文 / 审核修订记录表 / 范围外对账只报范围外 / 不审档自己拿 diff 对一遍）、「没做审核 ≠ 流程没走完」。**新增三条**：① 交付物口径（机制 4）；② 一卡盖批须声明（机制 5）；③ 「长期授权不免闸」——现 90-91 行的「文档 PR 合并长期授权」免的是「合并动作要不要再问」，不免闸（机制 4 的落地澄清，见 D11）。
- **第 6 步**保留 issue 节；其中「实施 PR 合并后勾验收项 + 评论 + 放锁」一段移入第 9 步。
- **第 7-9 步**：第 7 步 = 现「认领与防撞车」节正文（内容不变，升为步，入口句「手里有 issue 号就从这段进，段一与你无关——spec 已在 main」）；第 8 步一句话（worktree 里实施，规矩见「工作区规矩」节）；第 9 步 = 过闸（→ 闸节）→ 合并（代码 PR 仍按「Git: 危险操作」规矩）→ 回填（勾验收项、评论「代码已合」、放锁）。
- **frontmatter description** 重写为两个入口：保留现有需求入口语义，追加「认领 issue 做实施 /『请你做 #N』类任务也走本 skill——从段二进，实施 PR 合并前过闸」。「应用到项目」功能描述保留。
- **其余各节不动**：工作区规矩、分工边界、应用到项目、参考（非流程）、例外——除「六步」指称同步外不碰（见改动 3）。
