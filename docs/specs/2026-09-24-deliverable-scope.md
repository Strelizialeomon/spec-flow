# spec：交付物口径明文化——仓外临时产物不是交付物、不过闸

- 日期：2026-09-24
- Issue：#29
- 状态：已实施

## 背景：要解什么问题

2026-09-24 #25 实施现场：实施 agent 开出 PR #27 后照闸节摆档位卡，owner 疑惑「这种文档其实没必要审」——把 `/tmp` 里的 PR 正文底稿（仓外临时产物）和 PR 本身（仓内交付物）混成了一份，进而怀疑卡弹错、提议「只审核项目内的文档」。当场对账结论：卡弹得对（PR #27 是实施成果、必过闸），仓外草稿本就无卡。

但现行「交付物口径」条（SKILL.md:107-109）只从正面列举——spec、实施成果必过闸，机械文档变更免过闸——**没有一句从边界上明排「不进仓的文件不算交付物」**。判定靠 agent 现场发挥，就会漂成两个方向：给底稿也摆张卡（多），或以为文档 PR 不该有卡（漏）。本单管的是前者这一类混淆的根治。

owner 拍板（2026-09-24 对话，原话「单开一个 spec 和 issue 来处理这件事」）：把边界句明文化。（主 agent 当场建议过「不改」，owner 裁决仍要明文化——记录在案。）

## 机制清单

本 spec 只对既有「交付物口径」作明文化：把隐含的边界判定写成明文，不引入新概念、新抽象、新归边规则。

| 机制 | 解决什么 | 没有它会怎样 |
|---|---|---|
| **无 PR 交付物不豁免**（实施期补，2026-09-24 owner 裁决） | 无 PR 可走的实施成果（非 git 仓、目标仓无远端等）适用闸的依据 | 无 PR 改动成唯一无闸交付——连 2026-09-22 先例「改完把 diff 贴给用户过目」也失去依据 |

## 改动面（一处，两行新增）

SKILL.md 闸节「交付物口径」条，主句（现 107 行）之后、「归边不明」行（现 110 行）之前，新增两行：

```
  **交付物 = 随 PR 进入目标仓的改动**；不进仓的文件（/tmp 草稿、PR 正文底稿、会话中间产物）不是交付物，不过闸、不摆卡。
  **无 PR 可走的实施成果**（非 git 仓、目标仓无远端等）**不在上句排除内**——仍是交付物、照摆闸卡，「合并」读作「交付」（交付前摆卡，diff 随卡给用户过目）；算不算「临时产物」判不明的，照旧按下一条「归边不明」处理（闸卡附带一问）。
```

第二行（桥句）系实施期轻审发现 1 的裁决修订，原文照录（2026-09-24 owner 拍板）；边界句一字未动。既有条文其余一字不动。

**回响自查（第 5 步硬规矩）**：纯加边界定义与一条例外（桥句），不改既有判据 / 定义 / 术语。已 grep「交付物」全仓（2026-09-24 实施期复跑，按出现次数口径）：SKILL.md 12 处（本改动新加两行共含 3 处，改后 15；其余无需动）、`README.md` 与 `references/` 四文件零命中、兄弟 spec 四份中两份命中共 32 处（另两份零命中），命中的均为已实施历史时点记录、不同步。桥句引入的「无 PR」全仓另仅命中 `docs/specs/2026-09-22-design-control-gates.md:55`（正是桥句要接回的那条先例，历史时点记录、不同步）；「临时产物」命本 spec 标题与背景，无第三处。无需第二处改动。

## 不做清单

- 不改「必过闸 / 免过闸」两套既有归边，只补边界句。
- 不因本句改变任何在途 PR 的闸——PR #27 照常过闸合并（本 spec 起草时它已合并）。
- 不立「仓内但不进 PR 的文件」的任何规矩（untracked 草稿、临时脚本等）——它们同样不随 PR 进仓，边界句已覆盖，不另举例膨胀条文。
- 不改 frontmatter description、不改「文档检查入闸」条（其触发口径复用本条的既有归边，边界句对它同向生效、无需回指）。
