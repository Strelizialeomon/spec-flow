# spec：闸节新增「文档检查入闸」——文档类交付物摆闸卡前必跑目标仓文档检查链

- 日期：2026-09-24
- Issue：#25
- 状态：已实施（实现见 PR #27；spec 期轻审 5 条 + 实施期轻审 7 条，全数处置，见文末「审核修订记录」）

## 背景：要解什么问题

采纳仓 taoxi-system（私有 monorepo，237 份 md / 40,039 行，主改动者为 AI agent、人也直接改）已有 6 个文档检查脚本 + 单一入口 `scripts/check-doc-links.sh`（四个快脚本串行实测约 8 秒，全量约 90 秒），覆盖断链与锚点、ADR 结构、AGENTS/CLAUDE 配对、spec 状态词、登记串重复、文档新鲜度。

**痛点不在能力在触发**：该仓无 CI、无 git hook，检查只在「有人记得手动敲」时跑——上一轮治理把机制建好后，一天内就又开始漂（owner 原话，见 #25）。

该仓对候选触发机制做过一轮专项调研，2026-09-24 本方逐条复核（信源为各官方文档 / 官方 issue tracker，结论全部成立）：

| 候选 | 结论 | 2026-09-24 复核 |
|---|---|---|
| git hook（pre-commit/pre-push） | 需每台机器手工 `git config core.hooksPath`（静默漏装即失效），`--no-verify` 可绕 | 属实；另有 IDE 静默改写 hooksPath 致 hook 全失效的实例（git-scm.com/docs/githooks；Cursor 论坛 2026-08） |
| harness hooks（Claude / Codex / Kimi） | 三家都有 Stop 类事件，但配置位置不一：Claude `.claude/settings.json` 可入仓；Codex `.codex/hooks.json` 可入仓但 trust 按 hook 定义 hash 记录、改一次全员重新 trust；Kimi 只有用户级 `~/.kimi-code/config.toml`，无项目级 hooks。一份配置无法通吃，且管不住「人不用 agent 直接改」 | 属实（code.claude.com/docs/en/hooks；Codex hooks 官方文档 trust-by-hash；kimi.com/code/docs Hooks 页 2026-09-23 更新后仍只有用户级 config.toml 一个落点） |
| fswatch 常驻文件监听 | 结果到不了 agent，弃 | 成立（无回填通道） |
| CI | 最强兜底，但该仓发版管线未迁移，现阶段不可用 | 成立（仓情） |
| Google《SWE at Google》ch10 | 文档像代码一样对待 = 明确 owner / 随代码评审 / issue 跟踪 / 定期评估，四条里只有一条是「检查」 | 成立 |

owner 拍板（2026-09-24，#25）：**不上任何 hook，采用流程闸方案**——文档类交付物过 spec-flow 合并闸时强制跑文档检查链。依据：该仓文档改动全部走 spec-flow，闸是唯一必经点；与 Google ch10「随代码一起评审」同款；满足四条硬约束（工具无关 / 检查逻辑单份只在 scripts/ / 结果必须到达改文件的人或 agent / 不依赖远端服务）。

本仓 owner 拍板（2026-09-24 对话，卡片记录）：机制清单**全要**；触发口径**宽**——代码 PR 夹带文档改动也跑；红**阻合并、可当场豁免**；入口发现**自报 + 双约定路径**。

## 机制清单（本 spec 新增的机制）

| # | 机制 | 解决什么 | 没有它会怎样 |
|---|---|---|---|
| 1 | **文档检查入闸**：交付物含文档改动时，摆闸卡前 agent 必跑目标仓文档检查入口，结果（绿 / 红+摘要 / 无入口）写进闸卡；红 = 修好转绿后重摆闸卡再合并，用户可在卡上当场豁免一次 | 检查机制建好但靠人肉触发，一天就漂 | 检查脚本建好即摆设，文档继续漂 |
| 2 | **检查入口发现约定**（自报优先 → 双约定路径 → 无入口不算红） | spec-flow 是通用 skill，不能写死某一个仓的脚本路径 | 每个采纳仓都要改 spec-flow 本体才能受益 |

口径依据（机制 1/2）：taoxi-system 痛点实录（#25 前因节：机制建好后一天就漂）；「结果必须到达改文件的人」是该仓四条硬约束之一；宽口径由 owner 卡片拍板（2026-09-24），覆盖了「代码 PR 顺手改文档漏检」的窄口径缺口。

## 改动面（一处）

### SKILL.md 闸节 —— 新增「文档检查入闸」一条

位置：闸节 bullets 中「交付物口径」条之后、「一卡盖批须声明」条之前。条文草稿（实施时逐字落；除本块新增与下方配套半句外，既有条文一字不动）：

```
- **文档检查入闸**：交付物含文档改动（口径见下）时，**摆闸卡前先在交付物工作区跑目标仓的文档检查入口，把结果写进闸卡**——固定一行「文档检查：绿 / 红+摘要 / 无入口」；无论用户点哪档（含「不审」）都先跑再摆卡。
  - **触发口径**：交付物本身是 spec / 交付型文档（纯文档 PR）→ 必跑；代码 PR 的 diff 含文档文件改动 → 也跑（宽口径）；免过闸的机械文档变更 → 免跑（免过闸者优先——免过闸者本无闸卡，检查挂在「摆闸卡前」，自然不沾）。归边不明照旧——闸卡附带一问摆给用户。本口径复用上方「交付物口径」条的既有归边，只加「代码 PR 看 diff」一条，不另立第三套归边规则。
  - **入口发现（约定优于配置）**：① 目标仓指令文件（AGENTS.md / CLAUDE.md）里自报的文档检查入口 → ② 约定路径按序取第一个存在的：`scripts/check-docs.sh`、`scripts/check-doc-links.sh` → ③ 都没有：闸卡该行写「该仓无文档检查入口」，**不算红**。
  - **红的行为**：修完重跑转绿后**重摆闸卡**再合并；脚本存在但无法执行 / 跑崩溃也算红（原因写进摘要行——存在但跑不起来 = 检查能力坏了，标「无入口」是把坏装成没有）；用户可在闸卡上当场明示豁免一次，豁免理由写进卡。
```

配套（半句级）：「一卡盖批须声明」条末尾加半句——批卡时任一成员触发文档检查即跑，结果行注明覆盖哪些成员。

**回响自查（第 5 步硬规矩）**：本改动是闸节纯新增一条 + 一处半句配套，不改既有判据 / 定义 / 术语。已 grep 逐类核对落点：`README.md` 不列闸节细则（零命中）；`references/` 四文件零命中（apply-to-project.md 指针块只指向不复述，split-large-spec.md:71 仅指针式提「闸节」）；**兄弟 spec 一类有命中**——`docs/specs/2026-09-23-two-segments-one-gate.md` 逐字引「交付物口径」「一卡盖批须声明」两处：它是已实施的历史时点记录（状态：已实施），且本改动为纯新增不改旧条语义，按惯例不同步历史 spec。除闸节新增块外无需第二处改动。

## 不做清单

- 不改审核档位体系：档位永远用户点，文档检查是摆卡前的固定机器动作，与档位正交——不是「文档强制送审」。
- 不动「只含 spec / 文档的 PR 合并长期授权」：它管「合并动作要不要再问」，与本机制无涉（owner 2026-09-24 对话已确认保留）。
- 不要求任何仓必须建检查入口：无入口 = 闸卡标注、不算红，采纳零门槛。
- 不做 CI / hook / 守护进程等流程外硬闸——本流程软约束定位不变；本机制仍是「agent 照规矩跑」，防不了故意绕过。
- 不为本仓（spec-flow 仓）自建文档检查脚本——本仓当前无入口，按新规即「无入口不算红」；要不要建是另一件事。
- 不改 frontmatter description：本机制不改 skill 触发语义。
- 不刷各仓存量指针块与指令文件：指针指向真身，合并后自动获益（#25 影响面节原话）。
