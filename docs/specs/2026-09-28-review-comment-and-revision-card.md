- 日期：2026-09-28
- Issue：#41

## 背景：要解什么问题

### 现状（2026-09-28 实测）

- **审核结论落点不一**：近期有审核的几个 PR 里，结论落在三种地方——#34、#35 贴在 PR 评论（「审核留档」）；#37 spec 期贴在 issue 评论；#37 实施期（PR #39）14 条**没贴成 PR 评论**，只有 PR 正文一节摘要（计数 + 两条严重各一句）、issue #37 回填评论一句、仓内 spec 末尾的逐条处置表。`SKILL.md` 没有任何一句规定审核结论落哪。
- **审完默认自动全改**：`SKILL.md:73` 只写「修订时在 spec 末尾留『审核修订记录』表格」，默认审完就修。#37 spec 期 16 条、实施期 14 条均由 agent 当日自行全数处置，经 owner 卡片确认的各只有 1 处（spec 期机制 5 保留、实施期范围外一处保留）。
- **第 5 步措辞与实际相反**：`SKILL.md:17-18` 写的是「4. 过闸 → 5. 按需要修订 → 开 PR 并合并」，读起来是审完才开 PR；实际 #38 在 09:59 开 PR、10:15 才提交轻审修订——一直是先开 PR 再审。

### owner 拍板（2026-09-28 对话，卡片记录）

- 机制清单三条**全要**（逐项挑，三项全选）。
- 修订卡**只问一次整体**「改 / 不改」，不逐条标推荐。
- 评论**审完立即贴一次**；处置照旧记进 spec 末尾「审核修订记录」表，不再回帖。

## 机制清单（本 spec 新增的机制）

| # | 机制 | 解决什么 / 没有它会怎样 |
|---|---|---|
| 1 | **审核结论贴 PR 评论**：审完由主 agent 把审核结论原样贴成 PR 评论；无 PR 贴对话 | 结论有固定、可回溯的落点 / 没有它：结论散在 PR 正文、issue 评论、spec 表三处，PR 上没有一处能直接读到审过什么、还剩什么 |
| 2 | **修订卡**：贴完评论，用一张卡问用户「改 / 不改」；不许自动改，没答不合并 | 改不改由用户定 / 没有它：审完 agent 自己判、自己全改，和「档位用户点」是同一类越权 |
| 3 | **第 4、5 步改成「PR 先开、再过闸」** | 机制 1 贴评论时 PR 一定已经在 / 没有它：照字面走，审核时还没有 PR，评论无处可贴 |
