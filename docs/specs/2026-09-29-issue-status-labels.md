# spec：issue 状态标签备忘录（可选，按需启用）

- 日期：2026-09-29
- Issue：#46
- 状态：待实施

## 背景：要解什么问题

一个项目里每个 issue 都带验收，有些验收要上线后观察很久才能勾，于是大量 issue 长期关不掉：有的做了一半，有的做完了等上线，有的上线了等验收。单一多，owner 记不住每个单卡在哪、该谁动、哪天再看。并不是每个项目都有这个问题，所以做成**可选备忘录**：要用的项目通过〈应用到项目〉打开，不用的项目完全不受影响。

### 现状（2026-09-29 实测 taoxi_system）

- open 的 issue 共 41 个，关闭的 108 个。
- 仓里唯一的状态类标签是「待收尾」（描述：「已开工但没走完,还欠一个已知的具体动作(接着做 / 复现 / 拍板都算)」），2026-09-28 由 owner 集中挂上，现挂 22 个 open 单。
- 这 22 个单粗分下来其实是 6 种状态：

### 调研（2026-09-29 打开核对）

| 说法 | 出处 | 对本 spec 的含义 |
|---|---|---|
| 被卡住的卡片应当原地加标记，不挪进单独的「Blocked」列：挪过去会丢掉它在流程里的位置，而且容易被遗忘 | [ProKanban](https://prokanban.org/blog/whats-wrong-with-having-a-blocked-column)、[Nave](https://getnave.com/blog/kanban-blocked-column/) | 「卡住」做成可叠加的卡点标签，不做成阶段 |
| 「Fixed Pending Verification」：bug 已被 PR 修好、等验证，单独一个状态 | [Salt 项目标签说明](https://docs.saltproject.io/en/latest/topics/development/labels.html) | 「做完但没验完」要有自己的格子，就是「待验收」 |
| RESOLVED（开发做完）与 VERIFIED（QA 确认）是两个先后状态 | [Bugzilla 文档](https://bugzilla.readthedocs.io/en/latest/using/editing.html) | 同上 |
| 状态分固定顺序的大类（Backlog / Unstarted / Started / Completed / Canceled），类内可自定 | [Linear 文档](https://linear.app/docs/configuring-workflows) | 阶段按固定顺序排，一个单只处在一个阶段 |
| 新 issue 自动挂 `needs-triage`，分拣后才换成 `triage/accepted` | [Kubernetes issue triage](https://www.kubernetes.dev/docs/guide/issue-triage/) | 「未开始」要显式挂，没标签就是漏标 |

坑：以上都是团队协作场景的实践，不是针对「一人 + 多 agent」的。本 spec 借的是其中的状态划分原则，不照搬它们的工具与自动化。

## 机制清单（本 spec 新增的机制）

| # | 机制 | 解决什么 / 没有它会怎样 |
|---|---|---|
| 1 | **两类标签**：阶段标签 5 个（一个单只挂一个，按顺序往后走）+ 卡点标签 2 个（可叠加在任何阶段上）；含特殊情况四条（跳过阶段 / 一单多批挂最靠前 / 总单挂进行中 / 关单不摘标签） | 一眼看出单子走到哪一步、卡在谁 / 没有它：继续一个标签装 6 种状态 |
| 2 | **「下次看」行**：「待验收」「受阻」的单，正文第一行写「⏰ 下次看：日期 · 看什么」 | 长线验收的日子有固定、能被机器找到的位置 / 没有它：日期埋在评论里，到了也没人想起来 |
| 3 | **换标签时点**：开单、认领、实施 PR 合并、测试环境验过、上线、验收项全勾、要拍板、被卡住，各对应一个标签动作，由做这个动作的 agent 当场换 | 标签跟着实际走 / 没有它：全靠人记，一周就对不上 |
| 4 | **盘点**：用户说「盘一下 issue」，agent 只读地拉出全部 open 单，到期的排最前、按阶段分组，并列出标签可疑的单 | 一次看全、顺带抓漂移 / 没有它：owner 得自己逐个标签筛，漂了也发现不了 |
| 5 | **应用开关 `issue-status`**：〈应用到项目〉多认一个附加描述，建好 7 个标签、在项目指令里写一段指针（含「实施 PR 合并后不直接关单」） | 按需加载、每个项目一句话启用 / 没有它：每个项目手搭一遍，标签名和颜色各不一样 |

## 标签定义（备忘录正文的核心，实施时照此写）

### 阶段标签（一个单只挂一个）

顺序：未开始 → 进行中 → 待测试 → 待上线 → 待验收 → 关单。

| 标签 | 意思 | 下一步谁动 |
|---|---|---|
| 未开始 | 开了单还没动手；挂账、待复现、待评估都算 | 谁认领谁动 |
| 进行中 | 已动手，改动还没合进主干（含本地单测、PR 在审） | 做的人 |
| 待测试 | 已合进主干，等发到测试环境验 | 做的人（发测试环境、验） |
| 待上线 | 测试环境验过（或这个单不需要测试环境），等发到生产 | owner 同意后发版 |
| 待验收 | 已上线，还剩要等观察期或真实事件才能勾的验收项 | 到「下次看」那天的人 |

### 卡点标签（可叠加在任何阶段上）

| 标签 | 意思 | 什么时候摘 |
|---|---|---|
| 等拍板 | 卡在 owner 做决定 | 拍完就摘 |
| 受阻 | 卡在外部条件：环境不通、依赖别的单、时间窗未到 | 条件满足就摘 |

### 特殊情况

- **不需要某个阶段就跳过**：没有代码的单（排查、运维、调研）可以 未开始 → 进行中 → 关单；项目没有测试环境的，不用「待测试」，合并后直接进「待上线」；仓内即交付、不用部署的（文档、仓内脚本），合并后验收勾完就关单。
- **一单分多批、各批阶段不同**：挂**最靠前**那一批的阶段——下一步动作在那里；其余批次的进度写在正文进度段。
- **总单**：子单没全关前挂「进行中」；子单全关后，按总单自己剩下的验收走。
- **关单**：阶段标签和卡点标签都不用摘；重开时按实际情况重新挂。

### 「下次看」行

- 格式：`⏰ 下次看：YYYY-MM-DD · 看什么`，放在 issue 正文**第一行**。
- **必填**：「待验收」「受阻」。**选填**：其余有明确日子的单（如等拍板但有死线）。
- 等的是「真实事件」、定不了日子时，也写一个复查日（比如一周后看事件发生没有），保证能排序。
- 到期看过、还没完 → 改成下一个日期；用 `gh issue edit <N> --body-file <file>` 改正文。
- 为什么放正文第一行：位置固定，机器能找到；评论只会往下追加，越埋越深。

### 换标签时点

| 事件 | 标签怎么动 |
|---|---|
| 开单（spec-flow 第 6 步，或任何新开的单） | 挂「未开始」 |
| 认领（第 7 步） | 未开始 → 进行中 |
| 实施 PR 合并（第 9 步） | 进行中 → 待测试；不需要测试环境的 → 待上线；不用部署的 → 验收勾完就关单 |
| 测试环境验过 | 待测试 → 待上线 |
| 上线 | 待上线 → 待验收，并写「下次看」行；没有剩余验收项的 → 直接关单 |
| 验收项全勾 | 关单 |
| 需要 owner 拍板 | 加「等拍板」；拍完摘掉 |
| 被外部条件卡住 | 加「受阻」并写「下次看」行；解除后摘掉 |

谁来换：**做这个动作的 agent 当场换**，和回填 issue、勾验收项是同一步。owner 手动换也算数。

### 盘点

- **触发**：用户说「盘一下 issue」「issue 盘点」等。
- **只读**：`gh issue list --state open --limit 1000 --json number,title,labels,body,updatedAt`，不改任何标签。
- **输出顺序**：① 到期（「下次看」日期 ≤ 今天）；② 等拍板；③ 按阶段分组（待验收 → 待上线 → 待测试 → 进行中 → 未开始），卡点标签在单子旁注明。
- **可疑清单**（都能机械判定）：
  1. 没挂阶段标签
  2. 同时挂了两个以上阶段标签
  3. 「待验收」或「受阻」但正文第一行没有「下次看」
  4. 「下次看」行格式不对（日期解析不了）
  5. 同一阶段 14 天没有任何更新（可能已经往前走了、忘了换）
- **修**：盘点只报不改；要批量改标签，先把清单给 owner 过目、同意后再动。
