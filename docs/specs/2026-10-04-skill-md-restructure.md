```markdown
# 复杂活的两段流程

**主线**：需求 → spec → issue → 实施。方案期六步出 spec，实施期三步做实现；每份交付物合并前过同一道闸（摆卡让用户点审核档位）。按顺序走，别跳步、别把两步合成一步。

**段一·方案期**（新需求从这里进）

1. **用户描述需求**
2. **一起确认需求** —— 有岔路就问清，别猜；能自己查、自己判的先做完再问
3. **用户点头之后**才出 spec —— 硬关口：需求没确认就不动 spec 文件
4. **开 PR → 过闸**
5. **按需修订 → 合并**
6. **开 issue** —— spec PR 合并之后开，正文锚 spec 的永久链接

**段二·实施期**（认领 issue 从这里进；spec 已在 main，段一与你无关）

7. **认领 issue** —— 锁 = worktree 分支 `issue-<N>`
8. **在 worktree 里实施**
9. **过闸 → 合并 → 回填** —— 回填 issue、关单、放锁

要用户点的卡见「卡片总表」，能免什么见「豁免总表」，各步细节见「各步要点」。

## 卡片总表

凡要用户拍板都摆选择卡让用户点，不打字问是非题；agent 自己的推荐照给、排第一。

| 卡 | 何时摆 | 选项 | 没点 / 点了别的 |
|---|---|---|---|
| 机制卡 | 方案 / spec 有新增机制（第 2/3 步） | 全要 / 全砍 / 逐项挑 | 不出 spec |
| 闸卡 | 每份交付物合并前（第 4、9 步） | 不审 / 轻审 / 重审 / 重审 + 变异 | 按「不审」走：不阻塞、不追问 |
| 修订卡 | 审核有发现 | 改 / 不改 | 不合并 |
| 改旧 spec 卡 | 要改已合并 spec 的正文（新需求、实施中发现写错都算） | 新开一份 spec / 改旧的 | 不动笔 |
| 合并卡 | 代码 PR 要合进主干 | 合并 / 先不合 | 不合并 |

- 改旧 spec 卡：定稿 spec 被新需求反复改写会越改越乱，新开还是改旧由用户定（依据：rationale R12）。

## 闸（两段共用）

- 每份交付物各过一道，档位当场点，不存在可沿用的档位；摆完卡即算过完（点「不审」也算）。
- **审不审、审哪档，判断权全在用户**：agent 不自动派，也不自己判「这次算不算核心」。
- 档位是**每一份**的强度：

  | 档 | 每一份派什么 | 大致代价 |
  |---|---|---|
  | 不审 | 无；agent 自己拿 diff 对 spec 改动面过一遍，范围外变更停下报告 | 0 |
  | 轻审 | 1 个：spec 期 = 规格符合性 + 两张清单完整性；实施期 = 对抗式找 bug + 范围外对账（依据：rationale R3） | 约 5 分钟 |
  | 重审 | 2 个：规格符合性（含清单 / 对账）+ 对抗式找 bug | 约 10 分钟 |
  | 重审 + 变异 | 重审 + agent 自己跑一次变异：判据换成错的写法、跑全量测试，全绿 = 没护栏 | 约 10 分钟 + 18 秒 |

- ⚠️ **多份按份数叠加**，摆卡时把账算给用户看：「本次 N 份 × 该档 = 约 X 个 agent / Y 分钟」；多份实施 PR 可一张卡盖一批，卡上写明份数与成员清单。
- 项目规矩禁了某档，那档不摆，审核 prompt 里也不要求跑。
- 摆卡前：交付物含文档改动，先跑目标仓的文档检查，卡上固定一行「文档检查：绿 / 红+摘要 / 无入口」。
- 派审核、跑文档检查前读 `references/gate-details.md`。审完结论原样贴 PR 评论，有发现再摆修订卡，处置记进 spec 末尾「审核修订记录」；没做审核不用写免责声明。

## 豁免总表

拿不准算不算豁免，不自判——当作不豁免，或在闸卡上附带一问。

| 免什么 | 条件 | 照样不免 |
|---|---|---|
| 方案期（不出 spec、不开 issue） | 改一行、纯查事实、用户说「直接干 / 别走流程」 | 闸 |
| 开 worktree | 用户当场说「直接改 / 不开 wt」；agent 不自判、不建议 | 声明了真并行的仓，认领 issue 照开锁；流程其他环节 |
| 闸 | 无新内容的机械变更（回填号、状态行、索引、勾验收等）；不进仓的文件（草稿、PR 正文底稿） | 无 PR 可走的实施成果：交付前照摆卡，diff 随卡 |
| 改旧 spec 卡 | 同上机械变更；往末尾「审核修订记录」追加 | — |
| 合并卡 | 只含 spec / 文档的 PR（长期授权） | 闸卡、修订卡 |

## 工作区与锁

- 凡文件变更：先 `git fetch`，从 `origin/main`（或 `origin/master`）开 worktree 再动手，别在主仓改——主仓的工作区、暂存区、HEAD 全仓共享，多 agent 并行互踩没有兜底。
- 进 worktree 第一件事 `pwd` 重新取基准：编辑工具的绝对路径不跟 cwd 走。
- 认领 issue = 开名为 `issue-<N>` 的 worktree（分支同名）：开得成 = 没人做；被拒 = 有人在做，停（依据：rationale R6）。⚠️ 别拿 issue `open` 当没人认领，只信锁（依据：rationale R7）。
- PR 合并后放锁：删 worktree 和分支。命令、撞锁接手、squash 后删分支、锁的边界见 `references/worktree-lock.md`。

## 各步要点

**第 2/3 步·两张清单**（方案期、spec 期都管）

- **机制清单**：每新增一个机制 / 概念 / 抽象（用户事后可能问「这是什么 / 哪来的」的都算）单列一条，一行写「解决什么 / 没有它会怎样」，没有就写「无新增机制」；随方案摆机制卡，不混在正文里让用户批量点头；spec 期写进 spec 文件。
- **自定细节**：spec 没写死、agent 自己定的细节（默认值、判定规则、命名、落点）逐条列在 spec 末尾「自定细节」节；用户扫一眼，不逐项问；该列不列 = 违规。
- spec 期审核核对两张清单都在、与正文对得上；清单外有机制 = 漏报。

**第 5 步·修订**：⛔ 改一条判据 / 定义 / 常量 / 术语，必须全文搜它的所有落点逐一同步——机制节、实现节、实施步骤、验收标准、跨文档引用、历史记录；只改那一句，照 spec 施工等于白改（依据：rationale R1）。动手前读 `references/spec-revision-sync.md`。

**第 6 步·开 issue**：spec PR 合并之后、实施之前开——spec 没定稿就开会两边互相引着改（依据：rationale R2）。正文只放 spec 永久链接 + 改动面 + 验收要点（checkbox 先不勾），不贴全文。

**第 9 步·回填**：spec 头部元信息（Issue 号、状态）随实施 PR 一起改，不单开 PR；合并后勾掉 issue 里已满足的验收项、评论一句「代码已合」、关单、放锁。
```
