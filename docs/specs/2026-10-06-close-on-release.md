# spec：上线即关单（「待验收」收窄并改名「待验证」）

- 日期：2026-10-06
- Issue：#59
- 状态：已实施（实现见 PR #60；spec 期轻审 4 条，全数处置，见文末「审核修订记录」）

## 背景：要解什么问题

issue 状态标签备忘录（09-29 定稿，见 `docs/specs/2026-09-29-issue-status-labels.md`）给「已上线、还剩验收项」的单设了「待验收」，专收「等观察期或真实事件」。实际用下来，这一格把功能单拖得很长，而且和「受阻」「待上线」的边界说不清，agent 会挂错。

### 现状（2026-10-06 实测 taoxi-system）

- **#588（开放平台客户建档）**：9-29 21:36 写路由已发生产；剩下没勾的验收项（OA「未指派」列表肉眼确认、企微分配提醒真发、台账抽查）都要等某家合作方第一次真实调用，而「先不开通、等合作方明确要接再开」是 owner 9-29 拍的板。该单先后挂过「受阻」和「待上线」，10-06 当天才被改成「待验收」，「下次看」滚到 10-13。
  - 挂错的根子：「受阻」写「等外部条件」，「待验收」写「等真实事件」，「等合作方来接」两边都套得上；「待上线」写「等发到生产」，没说「给某家开通」算不算上线，而这张单的方案恰好把开通步骤列在「生产上线」底下。
  - owner 原话：「凭据不应该作为收阻项，如果这样，那大部分开放平台的 issue 都会受阻，因为开发了不一定马上有人用」。
- **挂过「待验收」的单共 8 个，现已全部关闭**；其中 #588、#590、#532 是 10-06 当天用 owner 账号关的（13:05–13:16）。当前 open 单的阶段标签：未开始 34、等拍板 6、进行中 1、待上线 1，没有「待验收」。
- 09-29 设「待验收」的依据，是当时 3 个「已上线，等观察期 / 真实事件」的单：#458（观察到 10-04）、#490（改表后观察 7 天）、#431（部分批次要回放 ≥30 晚）。本 spec 推翻的就是「为观察期留单」这一条。

### 调研（2026-10-06 打开核对）

| 说法 | 出处 | 对本 spec 的含义 |
|---|---|---|
| 「When you merge a linked pull request into the default branch of a repository, its linked issue is automatically closed.」 | [GitHub 文档](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue) | 平台默认：交付了就关单 |
| 发布后发现问题：「create a new Bug and link it to the original Story」；GitLab 提议功能单所在里程碑已过就「Create New」 | [Atlassian 社区采纳答案](https://community.atlassian.com/forums/Jira-questions/How-to-reopen-a-released-closed-issue-in-Jira/qaq-p/1139414)、[GitLab #24157](https://gitlab.com/gitlab-org/gitlab/-/issues/24157) | 上线后的问题开 bug 单挂链接，不重开、也不为它留着功能单 |
| 「separating [feature] release from [code] deployment」 | [Fowler《Feature Toggles》](https://martinfowler.com/articles/feature-toggles.html) | 「上线」= 代码进生产；之后给某家开通是另一件事，不归功能单 |
| 「Blocked work is prevented from moving forward due to unforeseen circumstances」，排队等待是正常流转，不算受阻 | [Nave](https://getnave.com/blog/blocked-work-in-kanban/) | 等外部方来接 ≠ 受阻 |
| smoke test 在「Immediately after deploying to a staging or production environment」时跑 | [CircleCI](https://circleci.com/blog/smoke-tests-in-cicd-pipelines) | 只能在正式环境验的项，上线后当场由我方主动去验，不挂着观察 |
| 反方：看板加「Validated」列，「Knowing whether the story was a good idea to have been done in the first place」才算做完 | [Lean Startup, Kanban, and Validation](https://www.flashover.blog/posts/lean-startup-kanban-and-validation/) | 未采纳：业务价值复盘是产品层面的事，塞进功能单正是单子被拖长的根源 |
| 模型认得出歧义，但答题时提问率普遍不到 5%，答题率高于 95% | [Knowing but Not Showing（arXiv 2605.25284）](https://arxiv.org/html/2605.25284v1) | 分拣靠一句客观问句，不靠 agent「拿不准就问」 |

坑：前五条都是团队协作工具的惯例，不是「一人 + 多 agent」场景的实测；本 spec 借的是「交付即关单、问题另开单」的原则。

## 机制清单（本 spec 新增的机制）

| # | 机制 | 解决什么 / 没有它会怎样 |
|---|---|---|
| 1 | **上线时分拣**：上线那一刻，对每条没勾的验收项问一句「这条现在能不能由我们自己动手验？」能 → 留下；不能（要等外部方、观察期、真实流量）→ 转出。没有留下的就关单，有留下的转「待验证」 | 功能单不再被观察期和外部方拖长 / 没有它：单子挂几周，「下次看」每周往后滚 |
| 2 | **「待验收」收窄并改名「待验证」**：只收上线后留下的、我方能主动验的项，验完就关单 | 标签名从「等别人来收」变成「我们自己去验」 / 没有它：等外部的项又会塞回这一格 |
| 3 | **转出项写进关单评论，上线后的问题另开 bug 单**：转出的验收项不勾，关单评论写「以下不在本单跟踪：…」并注明什么时候核对；上线后出了问题，开 bug 单挂原单链接，不重开原单 | 转出的项有据可查 / 没有它：转出项凭空消失，或者 agent 重开旧单接着拖 |

「受阻」行加一句「上线后的等待不算」，是在说明定义怎么用，不算新机制。

## 规则正文（实施时照此改 `references/issue-status-labels.md`）

### 阶段标签（替换原表与顺序行）

```markdown
顺序：未开始 → 进行中 → 待测试 → 待上线 → 待验证 → 关单。多数单上线后直接关单，不经过「待验证」。

| 标签 | 意思 | 下一步谁动 |
|---|---|---|
| 未开始 | （不变） | （不变） |
| 进行中 | （不变） | （不变） |
| 待测试 | （不变） | （不变） |
| 待上线 | （不变） | （不变） |
| 待验证 | 已上线，还剩只能在正式环境、由我们自己动手验的验收项（见〈上线时分拣〉） | 做的人，到「下次看」那天去正式环境验 |

为什么切在这五步：每步的交接人不一样（认领 / 改代码 / 过测试 / 发版 / 去正式环境验），阶段标签就是把「下一步该谁动」写成一行字——切错地方，标签就指错人。
```

### 「受阻」行（只改「意思」列）

```markdown
| 受阻 | 卡在外部条件：环境不通、依赖别的单、时间窗未到。上线后等外部方或观察期不算受阻，按〈上线时分拣〉转出 | 条件满足就摘 |
```

### 新增一节〈上线时分拣〉（插在原「三、换标签时点」之前，编为「三、」）

```markdown
## 三、上线时分拣：剩下的验收项怎么办

功能单的使命到上线为止：上线后观察期、外部方什么时候来接、上线后出的问题，都不归它。

上线那一刻，对每条没勾的验收项问一句：**这条现在能不能由我们自己动手验？**

| 回答 | 怎么办 |
|---|---|
| 能（典型：测试环境验不了、只能在正式环境验的第三方对接，比如企微真发） | 留下：单子转「待验证」，写「下次看」行；验完勾掉，全勾就关单 |
| 不能（要等外部方来接、等观察期、等真实流量） | 转出：不勾，不留单；关单评论写「以下不在本单跟踪：…」，每条注明什么时候核对（比如「首个合作方接入时」） |

- 没有留下的项 → 上线即关单。
- 上线后出了问题 → 开 bug 单，挂原单链接，不重开原单。原单只在关错了（分拣判错）时重开。

为什么只问这一句：一句话的客观问句，agent 每次都会照着问；「拿不准就问用户」这种软规则，agent 几乎从不触发。
```
