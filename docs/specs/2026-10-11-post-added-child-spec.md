# spec：后加子 spec 的总纲地图与依赖台账同步参考

- 日期：2026-10-11
- Issue：#64 / 实施 issue #66
- 状态：spec 已合入 main（PR #65）；实施 issue #66 实施中

## 背景：要解什么问题

一份大 spec 拆成子 spec、各份 issue 已经开出后，可能又来一个需要落在同一施工面的新需求。这个“后加的份”可能从已经完成的子 spec 手里接走文件 owner、交付物或依赖边；如果只开新 issue、不更新总纲的交付物地图和依赖台账，后面读总纲的人拿到的是旧快照。

finance-workspace 的一次真实案例中，第 13 份子 spec 接走了第 3 份已经完工的两项地盘，实施没有返工，但总纲必须额外记录这次转移才能继续作为设计权威。本仓 #62 刚把地图和台账升为拆分时的权威记录，因此这个边界需要留下可查的参考做法。

本 spec 只处理“拆完之后插入一份子 spec”这一时序和记录问题。它不重新定义拆分依赖闸，也不把一次成功案例直接升成主流程硬规则。

本 spec 对应 #64 岔路里的 **A1**：A 案（立这条规矩）降一档——只在拆分备忘录里留一条参考做法并登记 rationale，不进 `SKILL.md` 硬规则、不设硬闸。#64 正文只写作“A 但降一档”，没有“A1”字样，本文件是全仓唯一的 A1 定义处，供 R16 和后续重审引用。

## 调研结论

互联网资料支持“依赖关系要有方向、能随关系变化而更新、能显出阻塞点”，但没有支持为一次单例另造一条强制闸。外部资料还显示，已接受的架构决策发生变化时，应留下新的、可评审的决策记录，而不是静默改写旧记录。

| 说法 | 来源 |
|---|---|
| 依赖应明确写成“blocked by / blocking”，关系变化时可新增或移除；显式关系用于暴露瓶颈 | GitHub Docs，[Creating issue dependencies](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies)，2026-10-11 读取 |
| 依赖和接口属于架构上重要的决定；决策记录组成可追溯的 decision log | AWS Prescriptive Guidance，[Architectural decision record process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)，2026-10-11 读取 |
| 已接受的决策保持不可变；新洞见应提出新记录并将旧记录标为 superseded | 同上 |
| 决策记录应带状态并支持链接到其他记录 | MADR，[About MADR](https://adr.github.io/madr/)，2026-10-11 读取 |

## 目标

1. 给“后加的份”一个稳定定义和识别触发条件。
2. 在拆分备忘录里留下“先核对并更新总纲，再开新 issue”的参考顺序。
3. 明确这一步复用既有“改旧 spec 卡”，不新增主文件条款、审核档位或自动检查。
4. 用 rationale 记录单例证据、外部调研和本次取舍，方便以后有更多案例时重审。

## 不解决的问题

- 不把“后加的份”写入 `SKILL.md` 的硬规则。
- 不新增依赖类型、地图字段、台账字段、审核清单或验环工具。
- 不替用户决定“改旧 spec”还是“新开一份 spec”；该选择仍由现有“改旧 spec 卡”负责。
- 不回改 finance-workspace、taoxi_system 或本仓历史 spec；历史案例只作为 rationale 证据。
- 不为“没有改变地图/台账”的普通新 issue 增加额外流程。

## 机制清单

| # | 机制 | 解决什么 / 没有它会怎样 |
|---|---|---|
| 1 | **后加的份参考做法**：在拆分备忘录中定义触发条件和推荐顺序 | 让新增子 spec 不悄悄让总纲快照过期；没有它，仍会靠个人记忆决定是否补账 |
| 2 | **复用既有“改旧 spec 卡”**：总纲已合并时，地图/台账的语义变更先走现有卡 | 防止新参考做法与既有改旧 spec 闸重叠；没有它，两个入口可能给出相反顺序 |
| 3 | **R16 证据记录**：把案例、调研、取舍和未来重审条件写入 rationale | 让单例不被误当成成熟硬规则；没有它，后续只能从零回忆为何降档 |

## 设计

### 1. 定义与触发条件

“后加的份”是指：总纲已经完成拆分、至少一份子 spec 已进入实施或完成阶段后，又因为新需求新增一份子 spec，并且它会改变已有子 spec 的任一项：

- 文件 owner 或“不碰”边界；
- 交付物地图中的产出、消费或波次；
- 依赖台账中的提供方、消费方、产物、就绪条件、验收证据或 owner。

只新增一个不影响上述记录的独立子 spec，不触发本参考做法。发现触发条件后，先按下节处理，再开新增子 spec 的 issue。

### 2. 推荐顺序

1. 在新 spec 草案中列出它将接手的文件、交付物和依赖边，并标明从哪一份已存在的子 spec 转移。
2. 对照总纲的交付物地图和依赖台账，确认本次是否产生语义变更。
3. 总纲尚未合并时，直接在当前草案中补齐地图和台账；总纲已经合并且确需改正文时，先摆既有“改旧 spec 卡”。卡片允许选择改旧 spec 或另开一份 spec；本参考做法不替用户做这个选择。
4. 按卡片结果确认当前权威记录，再更新它：地图和台账应反映新的 owner、产出、消费、依赖边和波次；保留原 spec 的历史可追溯链接。若卡片选择新开一份 spec，需在该 spec 中明确它如何承接或取代原总纲的权威记录，不得留下两个互相矛盾的地图/台账。
5. 完成这次记录更新后，再开新增子 spec 的实施 issue，并在 issue 中链接总纲和新 spec。

这是一条备忘录中的推荐顺序，不是主文件硬闸。它不新增“拆分依赖审核”，不改变现有 issue 生命周期，也不绕过用户对“改旧 spec 卡”和合并卡的选择。

### 3. 与现有机制的边界

| 场景 | 处理 |
|---|---|
| 新份不改变地图或台账 | 按普通 spec → issue 流程；不套本参考做法 |
| 新份改变未合并总纲 | 直接在当前草案补齐地图/台账，再开 issue |
| 新份改变已合并总纲 | 先走“改旧 spec 卡”，再按卡片结果更新当前权威记录 |
| 新份本身要提出新的流程机制 | 另开一份 spec；本参考做法只负责记录拆分地盘和依赖变化 |
| 地图/台账更新只是机械回填 | 仍按现有豁免表判断；本 spec 不扩大机械变更的范围 |

### 4. 预期落点

实施本 spec 时只改两处：

1. `references/split-large-spec.md`：在“还有几条配套的”附近增加“后加的份”参考条目，含〈§1 定义与触发条件〉与〈§2 推荐顺序〉正文，并覆盖〈§3 与现有机制的边界〉表的全部五行——含“新份本身要提出新的流程机制”与“地图/台账更新只是机械回填”两个负向边界。
2. `references/rationale.md`：新增 R16，记录 #64 的仓内证据、互联网调研、A1 轻量参考取舍、来源、主文件不变的落点说明和未来重审条件。

备忘录新条目要覆盖的清单以〈设计 §3 与现有机制的边界〉表为准，共五行：不改变地图/台账、改变未合并总纲、改变已合并总纲、新份要提出新流程机制、地图/台账更新只是机械回填；正文按〈§1 定义与触发条件〉与〈§2 推荐顺序〉写，两处均需落章。

不改 `SKILL.md`、`references/gate-details.md`、审核档位表、issue 模板和既有历史 spec。若实施时发现现行正文有“总纲地图/台账永远不再变”的语义漂移，只同步确实受影响的指向，不扩大改动面。

## 自定细节

| # | 自定细节 | 理由 |
|---|---|---|
| D1 | 术语采用 issue 原文“后加的份” | 与 #64、现有讨论保持可检索的一致叫法 |
| D1-补 | 地图与台账统称“权威记录”：指总纲里承担设计权威的那两张表 | 仓库正文原来用“设计权威”，本 spec 从“它到底指哪份东西”的角度改叫“权威记录”；补这一行避免实施进备忘录后与既有“设计权威”并存、两个词指一物 |
| D2 | 触发条件采用“改变地图/台账任一记录”而非按时间或子 spec 数量 | 避免把所有新增子 spec 都变成额外流程，也不引入未经验证的阈值 |
| D3 | 顺序写成推荐做法，不写成 `SKILL.md` 硬条款 | 单例只有一次且没有返工损失；与 A1 取舍一致 |
| D4 | 总纲已经合并时统一指向既有“改旧 spec 卡”；若选择新 spec，必须在新 spec 里说明权威记录的承接关系 | 复用现有用户决策点，避免两个机制分别规定“先改什么”或留下双重权威 |
| D5 | 实施只改备忘录与 rationale | 控制改动面，避免再次出现 #63 轻审指出的范围外机制变更 |
| D6 | R16 记录外部资料的读取日期与 URL，并写明未来重审触发条件：再出现一例同类插入、发现地图/台账已失真，或既有“改旧 spec 卡”在此场景产生冲突 | 让后续复核能区分仓内案例和互联网参考，并有明确的升档入口 |
