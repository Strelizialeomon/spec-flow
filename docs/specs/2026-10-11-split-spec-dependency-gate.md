# spec：拆分大 spec 的依赖台账与三阶段拆分闸

- 日期：2026-10-11
- Issue：待 spec PR 合并后开
- 状态：草案

## 背景：要解什么问题

把一份大 spec 拆成多份子 spec 后，子 spec 之间仍会偶尔出现隐性依赖：某份先产出接口或数据结构，另一份才能实现；某份虽然没有改同一个文件，却依赖另一份的配置、运行时开关或验收条件。当前拆分备忘录已经覆盖文件 owner、不可触碰范围、施工波次、共享文件 owner、跨份收尾和拆分复核，但“能独立施工”主要按文件地盘判断，无法稳定识别这些语义依赖。

现有备忘录还有两个边界：它把“硬前置 / 可并行 / 必须同批合入”写成拆完后的标注，没有要求为每条关系写提供物、就绪条件和验收证据；“拆完再单独审一次”主要检查文件地盘，依赖图、环依赖和发布边界没有固定检查项。备忘录本身也声明为参考，不是必须执行的流程，因此同样的问题会重复出现。

**现状（2026-10-11 实测）**：2026-09-22 那轮十二份拆分里出过两处——两份额外各写了一遍同一个判定（账号是否启用），口径打架到实施期才暴露；另一处跨份的落库载荷键拆分时没定，靠拆分复核才补出契约表。2026-09-28 那轮九份拆分里出一处——两份争同一个文件的一行注释，谁都不动就卡死。依据见 `rationale.md` R15。

这次要把拆分的最小判断单位从“文件集合”扩展为“交付物 + 依赖边”，让拆分前可以判断三件事：每份能否独立开始、能否独立合入、能否独立发布。无法满足的关系不再被伪装成可并行子 spec，而是退回为单 spec 下的多个实施 issue，或先抽出共同契约 / 基础 spec。

## 目标

1. 每次拆分都有一张可读的交付物地图和依赖台账。
2. 每条跨 spec 依赖都写清提供方、消费方、产物、就绪条件、验收方式和 owner。
3. 将“开始施工、合入主干、发布验收”分开判断，波次由依赖边推导。
4. 在现有规格审核闸中加入拆分依赖核对，不新增审核档位或自动派发路线。
5. 在发现环依赖、无 owner 的共享契约或无法独立发布时，给出明确止损路径。

## 不解决的问题

- 不制定“超过多少行、多少端、多少文件就必须拆”的客观阈值。
- 不把依赖图做成机器可读格式，不新增验环脚本或 CI。
- 不替用户决定“拆子 spec”还是“只拆实施 issue”；规则只提供止损条件和推荐路径。
- 不改现有 worktree 锁、issue 生命周期、审核档位或项目采用名单。
- 不回写历史 spec，不迁移已有拆分案例。

## 机制清单

| # | 机制 | 解决什么 / 没有它会怎样 |
|---|---|---|
| 1 | **交付物地图**：总纲为每份子 spec 登记产出、消费、文件 owner、边界和发布波次 | 把“按施工面切”变成可核对的交付物边界；没有它，子 spec 看似完整但彼此接口不明 |
| 2 | **依赖台账**：以有方向的依赖边记录跨份关系 | 把接口、数据、配置和发布依赖显式化；没有它，文件不相交的依赖会漏掉 |
| 3 | **三阶段就绪判定**：独立开始 / 独立合入 / 独立发布分别判断 | 避免把“能开工”误当成“能合入”或“能上线” |
| 4 | **环依赖与不可独立发布止损**：不满足时退回单 spec + 多 issue，或抽共同契约 / 基础 spec；「必须同批合入 / 发布」不算止损，但要指一个实施批次 / 收尾份并登记依赖边 | 避免强行拆成互相等待的子 spec，造成串行返工；又不误杀备忘录做法 5「跨份的账挂一个收尾份」 |
| 5 | **依赖审查并入规格符合性检查**：拆分时检查地图、台账、就绪条件和环依赖 | 让拆分复核不再只看文件地盘；不新增档位或审核 agent |
| 6 | **子 spec 的上下游声明**：头部固定写上游、下游、合入前提 | 让实施者不用翻完整总纲就知道依赖和阻塞条件 |

## 设计

### 1. 交付物地图

总纲保留为设计权威，新增一张**交付物地图**表（取代备忘录既有的那张“拆分地图”——新表是它的超集：原表的 份 / 文档 / 范围 / 独占 / 发布序 全保留，另补产出、消费与三阶段状态）。每行代表一份子 spec，至少包含：

| 字段 | 要写什么 |
|---|---|
| 子 spec | 子 spec 名称或编号 |
| 产出 | 对外提供的接口、数据、配置、代码或文档结果 |
| 消费 | 需要使用的上游产物；没有写“无” |
| 文件 owner | 独占文件 / 目录 |
| 不碰 | 明确不修改的文件 / 目录 |
| 开始 / 合入 / 发布 | 三阶段是否独立，以及阻塞它的依赖边 |
| 波次 | 由硬依赖推导出的执行波次 |

已有的“独占文件 / 不碰”和“共享件只能有一个 owner”继续保留；交付物地图新增的是产出、消费和三阶段状态，不替代文件边界。

### 2. 依赖台账

依赖台账放在总纲，子 spec 只引用与自身有关的行。每条依赖至少包含以下字段：

| 字段 | 要写什么 |
|---|---|
| 提供方 → 消费方 | 有方向的子 spec 关系；禁止只写“互相依赖” |
| 类型 | 契约、数据、配置 / 运行时、发布 / 验收 |
| 产物 | 具体到接口、字段、事件、配置键、迁移结果、验收项或发布动作 |
| 就绪条件 | 什么事实成立后，消费方才可开始 / 合入 / 发布 |
| 验收证据 | 测试、文件、命令、截图、链接或人工确认 |
| owner | 对产物可用性负责的一份子 spec |
| 波次 | 该边阻塞的阶段和波次 |

“文件共享”仍按原有 owner 规则处理，不把它伪装成一条语义依赖；如果同一文件既有共享冲突又有接口依赖，两类记录都要保留。

依赖类型采用四类：

- **契约**：API、函数签名、事件、CLI 参数、返回结构等调用约定。
- **数据**：数据库表、字段、迁移、文件格式、枚举值、缓存键等数据约定。
- **配置 / 运行时**：配置键、环境变量、特性开关、权限、部署资源或运行时顺序。
- **发布 / 验收**：必须同一批上线、跨端一致、共同验收或必须由收尾份完成的条件。

### 3. 三阶段就绪判定

每份子 spec 在交付物地图中分别给出三项状态：

- **独立开始**：不等另一份代码合入即可开始施工；可以依赖已冻结的契约、明确的 stub 或测试夹具，但这些前提要写进台账。
- **独立合入**：合入主干时不需要另一份未合入的实现；若依赖兼容层、stub 或先行契约提交，必须把它列为就绪条件和验收证据。
- **独立发布**：单独发布后不会产生未满足的调用、数据、配置或验收条件。若必须和另一份同批发布，则本项不满足——此时**登记一条发布依赖边、点名一个收尾份**（承备忘录做法 5），而不是当成止损（见 §4）。

波次按硬依赖推导：前置产物未满足时只能排在后续波次；没有硬依赖的份可并行。软协调关系可以记在台账里，但不能伪装成硬前置，也不能阻塞不相关的波次。

### 4. 拆分止损规则

遇到以下任一情况，拆分不得直接进入子 spec 实施：

1. 依赖图出现环，且无法通过抽出共同契约 / 基础 spec 消除。
2. 一个跨份产物有多个 owner，或没有任何 owner。
3. 任一子 spec 无法独立合入，且既没有兼容层 / stub / 先行提交，也没有明确的同批合入安排（同批合入的份共用一个实施批次、一次过闸）。
4. 任一子 spec 无法独立发布，**且没有点名承担发布的收尾份**。
5. 依赖只写“等另一份完成”，没有具体产物、条件和验收证据。

“必须同批合入 / 同批发布”本身不是止损条件——它是一条登记在案的依赖边：合入的指定一个实施批次（一卡盖批），发布的指定一个收尾份（承备忘录做法 5）。**甩不掉**这些安排的，才按下面顺序止损：

- 能抽出稳定契约的，先建立共同契约 / 基础 spec，再拆消费者。
- 不能抽出稳定契约、但实施可以分工的，保留一份总 spec，只拆多个实施 issue。
- 依赖仍不明确的，暂停拆分，回到需求确认，不开子 spec issue。

### 5. 子 spec 固定声明

每份子 spec 头部增加三行：

```text
上游依赖：本子 spec 开始 / 合入 / 发布前必须满足的台账条目；无则写“无”。
下游影响：本子 spec 产出的契约、数据、配置或验收会被哪些子 spec 消费；无则写“无”。
合入前提：本子 spec 合入和发布所需的具体条件；不得只写“依赖总纲”。
```

子 spec 不复制总纲的设计正文；涉及依赖时引用总纲的台账行，避免总纲和子 spec 各自维护两份定义。

### 6. 审核接法

拆分依赖审查属于现有“规格符合性”检查的一部分，不新增审核档位、agent 数或独立收费。只要本次交付物包含多份子 spec，审核按以下清单核对：

- 地图中的每份子 spec 都有产出、消费、owner、边界和三阶段状态。
- 台账每条边都有方向、类型、具体产物、就绪条件、验收证据和 owner。
- 波次与硬依赖一致，没有把硬前置写成可并行，也没有把软协调写成阻塞。
- 图中没有未解释的环；不能独立合入 / 发布的份已走止损路径，或已指定同批批次 / 收尾份并登记成依赖边。
- 子 spec 的上游、下游和合入前提与总纲台账逐条对得上。

“不审”档不新增审核 agent；主 agent 仍需按现有规则自查，发现地图或台账缺项时停下报告，不把不确定依赖带进实施。

## 规则正文（实施时写入主文件）

```markdown
**拆分大 spec 时**：总纲必须有交付物地图和依赖台账。每份子 spec 写清产出、消费、独占文件、不碰、上游 / 下游和合入前提；每条跨份依赖写明提供方、消费方、产物、类型、就绪条件、验收证据、owner 和波次。分别判断能否独立开始、独立合入、独立发布；「必须同批合入 / 发布」的指定实施批次或收尾份、登记成依赖边，不算止损。有环依赖、无 owner、甩不掉这些安排的无法独立合入 / 发布时，退回单 spec + 多实施 issue，或先抽共同契约 / 基础 spec。拆分依赖审查并入现有规格符合性检查，不新增审核档位或派发路线。旧六条只管文件地盘，跨份的语义依赖不写下来就会漏到实施期（依据：rationale R15）。
```

## 不做清单

- 不新增一套独立审核档位，不擅自派“依赖审核 agent”。
- 不自动从文件 import、API 名称或目录相交推断依赖；依赖台账由方案阶段明确填写。
- 不设固定的子 spec 数量、文件数、行数或依赖边数量阈值。
- 不把所有跨份关系强行变成串行；只有硬依赖阻塞对应阶段，软协调关系仍可并行。
- 不把“同批发布”写成“可独立发布”；必须同批发布的，唯一出口是**点名收尾份并登记一条发布依赖边**，不许含糊过去（也不判成止损）。
- 不在子 spec 里复制总纲契约正文，避免改一处漏一处。
