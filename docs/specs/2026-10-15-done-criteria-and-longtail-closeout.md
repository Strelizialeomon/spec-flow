# spec：完成标准与长尾验收（观察式收尾默认不进单）

- 日期：2026-10-15
- Issue：#71
- 状态：已实施（实现见 PR #72；spec 期轻审 11 条全数处置，见文末「审核修订记录」）

## 背景：要解什么问题

10-06 定「上线即关单」时，判据（观察期不归功能单、上线那刻怎么分拣）写进了**选修**的 issue 状态标签备忘录。用下来露出两个口子：

1. **判据住在选修里，没采用标签的仓读不到**。规矩的分量取决于有没有人选修一套标签机制——这与它主张的「功能单的使命到上线为止」不匹配。
2. **方案期（写 spec / 写验收）没有任何对应约束**。观察式条目（「上线后观察 N 天」）照旧能写进 spec 和 issue 的验收；拦住它的只有上线那一刻的一句问句，而那句问句只存在于选修备忘录里。没采用标签的仓，连这一道都没有。

另外，10-06 的判据在采用仓里被**复述**进了它们自己的 `AGENTS.md`（见现状第 3 条）——第二份判据，真身一改就会漂。

## 目标

1. **完成标准 = 有限承诺**，写进正文：约定功能实现、正常 / 异常 / 边界 / 回归测试通过、无未处理的已知阻断缺陷、证据齐全；「没有 bug」按这个读，不是保证以后不出错。
2. **观察式收尾默认不进单**：不写进验收项、不当关单条件、也不自动换成一张观察单；要留线索的记一句。上线后出问题照旧开 bug 单。
3. **留一个有依据的例外口子**：真实时间 / 合规要求 / 必要的持续负载测试，且模拟时间或数据回放替代不了的，方案期摆「例外卡」写清四问，用户点头才纳入；纳入的挡关单直到出结论。
4. **判据与选修分家**：判据进 `SKILL.md` 正文（所有采纳仓可见，不带任何标签词）；标签、时点表、「下次看」、盘点仍整块留在选修备忘录里；备忘录里**复述判据的句子**换成指回正文的指针。

## 不解决的问题

- **盘点不会主动提醒**：备忘录 §五 已写明「要主动提醒得另加定时任务，本备忘录不含」——本次不动。
- **已开的单 / 老单不自动重分**：同备忘录 §六 口径，从规矩生效之日起向后执行。
- **不替采用仓改它们的 `AGENTS.md`**：本 skill 不维护采用名单、也不登记哪个仓禁了哪一档（本仓 `AGENTS.md` 第 1、2 条）；采用仓自己那行复述怎么改，是它们自己的事，本 spec 只点名后果。
- **不动闸、不加审核档位、不改采纳形态**。

## 调研

| 说法 | 出处 | 对本 spec 的含义 |
|---|---|---|
| DoD 是「一件事被算作完成之前必须满足的一串判据」，且**必须显式写出来**——「如果它只是共识、没写出来贴在墙上，大半效力会流失；它的价值很大一部分在于它是全队都知道的显式契约」 | [Agile Alliance 术语表 Definition of Done](https://agilealliance.org/glossary/definition-of-done/) | 支持第 1 条：完成标准要写成**正文里的显式公式**，不是留在各人脑子里的「没问题了」 |
| 「individual features or user stories may have specific "done" criteria in addition to the ones that apply to work in general」——单条可以另有自己的 done 判据，**附加在通用清单之上** | 同上页面（2026-10-15 抓取核对） | 支持「通用底线（第 1 条）＋本单验收项（第 2 条）」分层写；注意这句讲的是**分层**，不是 DoD 与验收项的分工论述——原写法夸大了 |
| 交付即关单、上线后的问题另开 bug 单挂链接；发布 ≠ 部署；smoke test 在部署后立刻跑 | 10-06 已核过的四条外部依据（原文与链接见 `docs/specs/2026-10-06-close-on-release.md` 调研表） | 本次不重新调研这套原则，沿用；本 spec 补的是它的**上游**：什么能写进验收 |
| 「观察期不归功能单」是 owner 10-06 亲自拍的，原话「有的单子甚至要等半个月观察期，太扯淡了」；当时推翻的正是 09-29「为观察期留单」 | `docs/specs/2026-10-06-close-on-release.md:35` | 第 2 条不是新主张，是把**已拍过的判据**从选修层提上来；第 3 条的例外口子只放行三类有依据的，并与「不能为及时关单跳过必要验证」成对 |

## owner 拍板（2026-10-15 对话）

- 三条建议（有限承诺 / 禁止观察式收尾 / 有依据的例外）由用户转来并问「你综合考虑」；范围卡用户选「**三条全收**」。
- 方案两度被打回、逐字改到定稿，原话：「不好，我觉得应该把写在issue label部分的哪个长尾约束提出来放到正文，然后出处和入处都需要进行总体上的丝滑衔接，而不是生硬的放进去」「我们的备忘录都是选修机制，不能直接把备忘录写进正文里，你可以看看 taoxi_system 或者是 茉莉抽奖是怎么组织的」。定稿形态 = **判据进正文、选修产物一个字不进正文、备忘录复述处改指路**。
- 例外卡设计经确认：「要不要验收应该要用户确认，是这个意思吗」→ 回答澄清为「默认自动拦，只有破例才点卡」，用户未再改。
- 用户下令「出 spec」即本条。

## 机制清单（本 spec 新增的机制）

| # | 机制 | 解决什么 / 没有它会怎样 |
|---|---|---|
| 1 | **完成标准 = 有限承诺**（正文） | 关单有了说得出嘴的判据，「没有 bug」不再被读成无限承诺 / 没有它：要么永远关不了单，要么含糊关单 |
| 2 | **观察式收尾默认不进单**（正文） | 在写验收的源头拦住，且不依赖任何选修机制 / 没有它：方案期照写，只有上线那一刻一道关，没采用标签的仓连这道都没有 |
| 3 | **例外卡 ＋ 批准项的收尾**：方案期摆卡（点「纳入 / 不纳入」，没点＝不纳入）；批准过的项在上线那刻查批准记录、挡住关单、「下次看」＝批准的结束日 | 给真实时间 / 合规 / 持续负载留合法出口，且不许 agent 自判；批准与收尾两头都有据 / 没有它：要么偷偷留单，要么为及时关单跳过必要验证，要么批了没人记着什么时候结 |
| 4 | **判据与选修分家**（正文持判据，备忘录只留动作＋指路） | 所有采纳仓都能读到判据，且全仓只有一份 / 没有它：判据随选修缺席（现状 1），或被采用仓复述成第二份（现状 3） |

```markdown
**完成标准与长尾验收**（第 3 步出 spec、第 6 步写验收、第 9 步关单都管）
```

- 不改采纳形态（还是只指向式）。
- 不删备忘录任何标签机制；「下次看」格式、盘点、采用步骤一字不动。
- 不给采用仓改它们的 `AGENTS.md` 复述行；不攒采用名单。
- 不为「观察单」增设新载体（不开、不换、不登记，只留一句线索）。

## 自定细节（spec 没写死、我定的）

1. 新段标题定为「**完成标准与长尾验收**」，放在〈各步要点〉「第 2/3 步·两张清单」块之后（它最早在方案期起作用）。
2. 卡名「**例外卡**」，加在卡片总表「改旧 spec 卡」之前（方案期摆）。
3. 例外三类照用户建议原文：真实时间 / 合规要求 / 必要的持续负载测试；四问照原文：验什么、为何不能用模拟时间或数据回放替代、多久结束、怎样算通过。
4. 「不能」分支拆成两行（批准过 / 没批准过），问句原样保留——「为什么只问这一句」段的理由不受影响。
5. 压缩的是「拆分大 spec 时」段而不是「工作区与锁」段：前者的细则本来就整份躺在必须读的 `split-large-spec.md` 里，压缩不丢信息；后者的判据句（开得成 = 没人做）没有别的家。
6. spec 文件路径与 slug：`docs/specs/2026-10-15-done-criteria-and-longtail-closeout.md`。
7. R 编号取当前最大 R17 的下一位 = **R18**。
