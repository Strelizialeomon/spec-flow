## 1. 背景与现状

### 1.1 要解决的问题

spec-flow 目前有多个“可选备忘录”：

- `references/adr-decision-records.md`：长期决策记录；
- `references/documentation-lifecycle.md`：现状文档、spec、ADR、issue / PR 的分工；
- `references/issue-status-labels.md`：issue 阶段、卡点标签和盘点。

三个备忘录都声明“默认不启用，用户明确要求或项目规则已声明采用时才执行”，并且 `apply-to-project.md` 已经有 `adr`、`doc-lifecycle`、`issue-status` 三个附加描述动作。

但当前缺少一份统一的“备忘录采用契约”来回答：

1. 一个新备忘录如何声明自己是选修、一次性采用还是项目级采用；
2. 项目级采用后，项目指令里最少必须留下什么；
3. agent 在什么时点读取备忘录、执行什么动作；
4. 哪些部分必须有机械检查或 dogfood 证据；
5. 新备忘录只写进 `references/`、没有登记和采用动作时，如何明确判定为“尚未生效”。

没有这份契约，后来新增一个备忘录很容易变成“仓库里有正文，但 agent 平时不知道它存在”，或者每个项目各自发明入口，最后出现入口漂移。

### 1.2 当前实现证据

| 位置 | 当前口径 | 缺口 |
|---|---|---|
| `SKILL.md` 总规则 | 标记为可选的参考文件，在用户明确要求或项目规则已声明采用时读取 | 参考表中的 ADR 行只写“用户明确要求本次写 ADR 时也读”，没有逐行明确“项目已声明采用” |
| `adr-decision-records.md` | 已区分未启用、一次性、项目级采用；要求项目落持久入口 | 没有与所有选修备忘录共用的采用契约和验收形状 |
| `documentation-lifecycle.md` | 已要求项目指令留指针和现状文档读序 | 这条是该备忘录独有规则，未抽成所有备忘录的通用接口 |
| `issue-status-labels.md` | 已指向 `apply-to-project` 的 `issue-status` 采用动作 | 标签、指针、测试环境问答、旧标签处置均是该备忘录自有动作，缺少统一登记字段 |
| `apply-to-project.md` | 已有三个注册修饰词，并规定新增修饰词要同时改本文件和 `SKILL.md` | 没有统一规定一个修饰词必须声明哪些采用元数据、执行时点和验收方式 |
| 项目 `AGENTS.md` | 采用项目留本地入口，项目自己选择落点 | 不同备忘录的入口节形状不完全一致，新增备忘录没有统一最低要求 |

### 1.3 设计原则

- **选修仍然是选修**：备忘录文件存在，不代表默认启用；项目没有声明采用时，agent 不读取、不执行、不追问。
- **一次性采用与项目级采用分开**：用户说“这次读一下”只影响当前任务；用户说“项目采用”才写持久入口。
- **入口比正文短**：项目只留指针、本仓落点和本仓差异，不复制备忘录正文。
- **有入口才有生效**：中央登记、采用动作、项目持久入口三者缺一不可；只新增正文不算可用机制。
- **语义由 agent 判断，载体由检查器兜底**：脚本不猜用户意图，只拦缺字段、断链、入口和格式错误。
- **不维护采用项目名单**：项目是否采用仍由项目自己的指令声明，中央仓只维护采用动作和模板。

## 2. 目标与非目标

### 2.1 交付目标

1. 在 `SKILL.md` 中明确所有选修备忘录的统一读取条件：用户本次明确要求，或项目持久规则声明已采用。
2. 定义备忘录的两种运行模式：本次按需读取、项目级持久采用。
3. 为项目级采用定义统一最低契约：中央登记、采用动作、项目指针、执行时点、验收证据。
4. 让 `apply-to-project` 成为项目级采用的标准入口；新增备忘录不得只增加正文而没有采用动作或明确声明“不支持项目级采用”。
5. 按统一契约核对现有 `adr`、`doc-lifecycle`、`issue-status` 三个修饰词，补齐缺失或歧义的入口描述。
6. 增加可复跑的正反 dogfood，证明选修默认关闭、本次采用不污染项目、项目采用能跨会话生效、未知修饰词不会被猜测。

### 2.2 明确不做

- 不把任何选修备忘录提升为所有任务默认必读。
- 不建立中央“哪些项目采用了哪些备忘录”的登记名单。
- 不把所有备忘录的正文合并进 `SKILL.md`。
- 不强制所有备忘录都拥有 CI、生成器或脚本；只有能机械证明且风险值得的部分才由项目或备忘录自带检查。
- 不自动迁移已有项目、不自动给项目补入口；采用动作仍由用户明确触发。
- 不为一次性读取创建项目文件、模板或规则页。
- 不修改三个采用项目的业务代码、issue、标签历史或文档正文，除非后续用户另行授权采用 / 对齐；dogfood 一律在临时假仓执行，对真实采用项目只做只读核对。

## 3. 统一采用契约

### 3.1 两种运行模式

每个选修备忘录都必须明确支持哪种模式：

| 模式 | 触发 | 持久化 | agent 行为 |
|---|---|---|---|
| 本次按需读取 | 用户明确要求“本次读 / 按这份备忘录做” | 不写项目规则 | 只在当前任务读取并执行，任务结束不改变项目制度 |
| 项目级持久采用 | 用户明确要求项目启用，或项目指令已声明采用 | 写项目指令入口和本仓落点 | 后续相关任务自动按该备忘录执行；不再重复询问是否启用 |

备忘录没有项目级采用动作时，必须在中央登记中明确写“仅支持本次按需读取”，不能让 agent 误以为放进 `references/` 就自动生效。

### 3.2 每个备忘录必须声明的最小元数据

备忘录正文开头增加统一的“采用口径”区块，字段按备忘录实际情况填写：

```md
## 采用口径

- 默认：选修，不因项目复杂自动启用
- 本次按需读取：用户明确要求本次按本备忘录执行时读取
- 项目级采用：通过 `apply-to-project` 的 `<modifier>`，或项目指令明确声明已采用时生效
- 项目入口：采用后由 `apply-to-project` 写入项目指令的指针节
- 执行时点：<开工 / 拍板 / 实施 / 收尾中实际适用的时点>
- 验收：<机械检查、dogfood 或“不适用”的理由>
```

这一区块只说明采用和触发，不复制备忘录主体规则。主体规则仍由该备忘录自己负责。

`<modifier>` 必须是稳定的 ASCII 标识，例如 `adr`、`doc-lifecycle`、`issue-status`；同一备忘录只能有一个注册修饰词。

### 3.3 `SKILL.md` 中央登记

`SKILL.md` 的参考表每个选修备忘录都写清四件事：

| 字段 | 必须回答 |
|---|---|
| 默认状态 | 是否默认关闭 |
| 读取条件 | 用户本次明确要求 / 项目已声明采用 / 其他明确条件 |
| 采用动作 | 是否有 `apply-to-project` 修饰词 |
| 用途 | agent 读取后解决什么问题 |

标准行形状：

```md
| `references/<memo>.md` | 选修，默认关闭；用户本次明确要求或项目规则声明已采用时读取；采用走 `<modifier>`；<一句话用途> |
```

当前三行必须全部明确写出“项目规则声明已采用”，消除只写“用户明确要求本次”的歧义。

### 3.4 `apply-to-project` 采用动作

`references/apply-to-project.md` 增加一段通用契约，所有注册修饰词都按同一顺序处理：

1. 检测项目当前是否已有该制度、规则页和入口；
2. 判断项目采用目标文件和项目自有落点；
3. 写项目指令里的短入口；
4. 需要时新建项目规则页或项目资产；
5. 输出采用结果、跳过项、发现的旧物和后续验收；
6. 保证重复执行幂等。

每个注册修饰词的登记表至少包含：

| 字段 | 内容 |
|---|---|
| 修饰词 | 稳定标识，例如 `adr` |
| 语义变体 | 用户可能说的等价表达 |
| 项目入口 | 写入哪个指令文件、哪一节 |
| 项目资产 | 是否需要规则页、目录、标签或其他对象 |
| 执行时点 | 后续任务何时读取 / 动作 |
| 验收方式 | 脚本、dogfood 或“不适用” |
| 幂等规则 | 再次采用时如何校验、不重复创建什么 |
| 旧物处置 | 发现副本、旧规则、重叠资产时只报告还是可修改 |

不认识的修饰词继续当场询问，不猜成已有备忘录。新增修饰词必须同时更新 `SKILL.md` 参考表和 `apply-to-project.md` 登记表；这两处是注册契约，不再只靠散文说明。

### 3.5 项目持久入口

项目级采用动作写入项目自己的指令入口，最低包含：

1. 已采用哪个备忘录；
2. 规则正文唯一链接；
3. 项目本地落点；
4. 后续任务必须做的动作；
5. 本仓差异或验收命令；
6. “不复制正文、不建第二份真相源”的边界。

入口必须写成指令，而不是“这里有一份文档”的说明。例如：

```md
## 已采用：<备忘录名称>

本仓已采用 spec-flow 的 `<memo>`（用户于 YYYY-MM-DD 拍板）。规则正文不在本文件复述。

- 规则正文：`<中央备忘录链接>`
- 本仓落点：`<项目路径>`
- 执行型 agent 在 `<时点>` 必须 `<动作>`。
- 本仓差异：`<项目自有规则 / 检查命令 / 无>`
```

项目入口只留本仓落点和动作，不把备忘录主体抄进来。

### 3.6 执行时点契约

每个项目级备忘录至少要声明一个真实执行时点，否则采用后仍可能没人读：

- **开工前读取**：已有规则会影响当前任务；
- **用户拍板后读取 / 写入**：本次决定会产生长期规则；
- **出 spec 时读取**：spec 需要引用该备忘录的分工或现状；
- **实施期读取**：代码 / 文档施工需要按备忘录约束；
- **收尾读取**：验收、回填、关单或状态变更受备忘录影响。

“执行时点”不是把所有备忘录都塞进两段流程；只声明该备忘录实际需要的时点。没有固定时点的备忘录可以只支持本次按需读取，并在登记表标明。

### 3.7 验收契约

每个项目级备忘录必须提供至少一种可复跑验收：

- 机械检查：能明确断言入口、字段、结构或状态；
- dogfood：用一条真实任务验证 agent 会读取并执行；
- 明确不适用：写出为什么无法机械验证，以及项目收尾如何报告。

验收只证明“采用后的载体和动作存在”，不冒充能理解用户自然语言。语义是否命中仍由 agent 按备忘录规则判断。

## 4. 现有三个备忘录对齐

### 4.1 ADR

对齐内容：

- `SKILL.md` 参考表明确“项目规则已声明采用时也读取”；
- `adr-decision-records.md` 增加统一“采用口径”区块；

- 真实需要三时点 Gate、固定 spec 元数据、ADR 结构检查的项目由项目自己采用升级，不把重型机制默认推广给所有 ADR 项目；
- `adr` 的 dogfood 覆盖：默认不启用、本次一次性、项目级采用、重复采用、已有项目自带 ADR 规则页、未知修饰词。

### 4.2 文档生命周期

对齐内容：

- `SKILL.md` 参考表明确项目声明采用时读取；
- `documentation-lifecycle.md` 现有“项目指令一条指针 + 一行现状文档读序”纳入统一采用契约；
- `apply-to-project.md` 的 `doc-lifecycle` 登记补齐项目规则页已有 / 没有时的落点判断、执行时点和验收方式；
- 不新建第二份规则页；已启用 ADR 的项目把现状文档落点补进既有规则页；
- dogfood 验证执行型 agent 在默认读序中会读现状文档和生效 ADR，并且不会把 spec / 调研当作当前事实正文。

### 4.3 Issue 状态标签

对齐内容：

- `SKILL.md` 参考表明确项目声明采用时读取；
- `issue-status-labels.md` 的 `apply-to-project` 采用动作、标签创建、测试环境问题、幂等和老单不迁移口径保持不变；
- `apply-to-project.md` 的 `issue-status` 登记补齐标签资产、执行时点、验收和旧标签处置；
- dogfood 验证：默认不建标签；采用后同名标签不覆盖；没有测试环境时不会使用待测试；重复采用不重复创建。

## 5. Dogfood 与验收

### 5.1 采用模式矩阵

| 场景 | 输入 | 预期 |
|---|---|---|
| 默认关闭 | 项目未声明任何备忘录，用户提出普通复杂需求 | 不读取选修备忘录，不新增入口，不追问是否启用 |
| 本次按需 | 用户说“本次按 ADR 备忘录执行” | 当前任务读取并执行；不修改项目指令、不新建规则页、不改变后续任务 |
| 项目级采用 | 用户说“把 spec-flow 应用到本项目，同时启用 ADR” | 写 ADR 入口、规则页和目录落点；后续会话能从项目指令到达规则 |
| 重新采用 | 项目已经采用 ADR，再次说启用 ADR | 校验入口形制，不重复追加、不重复建规则页、不重复建资产 |
| 项目自带制度 | 项目已有 `docs/adr/README.md` | 不新建 `docs/decisions/`；入口指向项目自己的规则页 |
| 未知修饰词 | 用户给出未登记名称 | 当场询问，不猜、不写入口、不创建资产 |
| 无项目级动作 | 新备忘录只在 `references/` 中新增，未登记 modifier | 保持选修；不会被默认读取；维护检查报告缺采用契约或标明“仅本次按需” |

dogfood 一律在**临时假仓**里跑（本仓先例 `docs/specs/2026-09-22-apply-to-project.md:80`），不碰任何真实采用项目；每条场景在实施 PR 正文留一行可核记录，形状 = 场景 / 输入 / 实际动作 / 证据（命令 + 输出摘要）/ 结论（先例 `docs/specs/2026-09-23-two-segments-one-gate.md:111`）。

### 5.2 维护检查

在 `scripts/check-docs.sh` 里增加一节针对“备忘录采用契约”的静态检查（不另起脚本：闸跑的就是仓自报的这个文档检查入口，另起脚本除非同时写进 `AGENTS.md` 的自报行，否则闸上永远跑不到它），检查以下可机械项：

- `SKILL.md` 参考表里的每个选修备忘录都有默认状态和读取条件；
- 需要项目级采用的备忘录都有注册 modifier；
- `apply-to-project.md` 的 modifier 登记与 `SKILL.md` 参考表一一对应；
- 每个 modifier 登记含入口、资产、执行时点、验收和幂等字段；
- 新备忘录若明确“仅本次按需读取”，不要求 modifier，但必须写出限制；
- 代码围栏、历史 spec 和示例不被误判为登记项。

检查脚本只维护 spec-flow 仓自身的中央契约，不扫描外部项目，也不维护外部项目采用名单。

## 7. 机制清单

| 机制 | 解决什么 / 没有它会怎样 | 本次处置 |
|---|---|---|
| M1 备忘录采用契约 | 让新增选修备忘录知道怎样从“仓内正文”变成“项目可执行制度”；没有它，新增备忘录可能只被放进 references 而无人读取 | 新增统一契约 |
| M2 两种运行模式 | 区分本次按需读取与项目级持久采用，防止一次性要求污染项目，或项目采用只活在当前会话 | 新增统一模式表 |
| M3 modifier 登记表 | 把 `SKILL.md` 与 `apply-to-project` 的注册关系机械化，防止入口只改一处 | 新增中央登记字段 |
| M4 采用契约检查 | 拦缺入口、缺执行时点、缺验收和注册漂移；没有它，维护者会继续靠人工对照 | 新增 spec-flow 仓维护检查（并进 `scripts/check-docs.sh`） |
| M5 执行时点契约 | 声明备忘录在哪个时点被读取 / 执行；没有它，采用后仍可能没人读（§3.6） | 新增时点清单 |
| M6 验收契约 | 声明每个项目级备忘录靠什么验收；没有它，采用只有载体、没有能判通过的标准（§3.7） | 新增验收三选一 |
| M7「采用口径」区块 | 每个备忘录正文开头的统一采用声明；没有它，新备忘录形状各异、agent 无从判断是否启用（§3.2） | 新增统一区块 |
| M8 项目持久入口模板 | 项目侧入口的最小形状；没有它，各项目自造入口、口径漂移（§3.5） | 新增入口模板 |

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 选修备忘录被误读成默认必读 | 所有入口都显式写“默认关闭”；dogfood 加默认关闭负例 |
| 中央登记变成采用项目名单 | 登记只记录备忘录与 modifier，不记录任何项目名称 |
| 每个新备忘录都被迫配重型脚本 | 采用契约允许“不适用”；只有机械可判的高风险项才加检查 |
| 项目入口复制正文造成漂移 | 指针模板只写规则链接、项目落点、执行时点和差异，不复制正文 |
| `SKILL.md` 与 `apply-to-project` 再次一边改、一边漏 | modifier 登记表 + 维护检查双向对照 |
| 本次改造扩大成所有项目迁移 | 采用动作仍需用户触发；不自动迁移、不维护项目名单、不回写历史项目 |
