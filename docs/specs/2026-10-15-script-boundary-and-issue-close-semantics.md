## 1. 背景与现状

### 1.1 要解决的问题

当前有两个会让 spec-flow 产生隐形副作用的风险：

1. 备忘录采用或应用到项目时，agent 可能顺手新增脚本、CI、Hook、Workflow、生成器或机器人，把原本的 Markdown 规则升级成项目代码变更；
2. PR 正文如果写 `Closes #N`、`Fixes #N` 或 `Resolves #N`，GitHub 会在 PR 合并时自动关闭 issue，绕过 spec-flow 第 9 步的验收回填、阶段判断和显式关单。

这两件事都不应该靠用户事后发现：第一件扩大了项目维护面，第二件改变了 issue 生命周期。

### 1.2 当前规则证据（口径按 `main@1261022` 实测）

| 位置 | 当前口径 | 需要补的边界 |
|---|---|---|
| ADR 备忘录 | 最小版默认不加 CI、生成器、编号器、检查脚本；真实出现问题后再升级 | 需要上升为所有选修备忘录和 `apply-to-project` 的默认低副作用边界 |
| `apply-to-project` | §十 采用契约已落地（两种运行模式、通用处理顺序、修饰词登记表每张八项字段、含「项目资产」字段），并与 `SKILL.md` 参考表由 `check-docs.sh` 机械核对 | 需要明确：默认集合之外不新增 / 修改脚本、CI、Hook、Workflow、生成器或机器人，即便某个备忘录正文提到它们 |
| `SKILL.md` 第 9 步 | 合并后回填 issue、勾验收项、评论、关单、放锁 | 需要禁止 PR 正文提前使用 GitHub 自动关单关键词 |
| issue-status 备忘录 | 采用后按阶段和验收决定何时关单；有长尾时可能先转“待验证” | 自动关单会在合并瞬间跳过这套分拣 |
| PR 正文约定 | 当前没有中央默认的 issue 关联写法 | 需要统一为“关联 issue”，默认不触发 GitHub 自动关单 |

## 2. 目标与非目标

### 2.1 交付目标

1. 把“Markdown-first、默认无脚本副作用”写成 spec-flow 的中央默认边界。
2. 让 `apply-to-project` 默认只写 Markdown 指针、规则页、项目落点和 §十 登记表已声明的项目资产。
3. 某个备忘录确实需要脚本、CI、Hook、Workflow、生成器或机器人时，先停下来报告，不擅自创建；用户明确同意后再走单独实施。
4. 统一 PR 正文的 issue 关联写法，默认禁止 `Closes`、`Fixes`、`Resolves` 等自动关单关键词。
5. 保留 spec-flow 第 9 步的显式回填、验收分拣、阶段标签和关单动作。
6. 用正反 dogfood 证明两类副作用都被挡住，且不增加新的脚本来做这道拦截。

### 2.2 明确不做

- 不修改已合并的 PR #74 / #76 内容，不把本 spec 的需求回写进它们的 spec 或评论。
- 不删除已有项目脚本，不修改项目现有 CI / Hook / Workflow。
- 不禁止项目在用户明确授权后使用脚本；本 spec 管的是默认自动添加和隐式副作用。
- 不把所有 issue 关单都改成永不自动关闭；用户明确要求本 PR 合并即关单时，允许按用户指令执行，并在 PR 正文中如实体现。
- 不新增“防脚本脚本”、关键词扫描脚本或 GitHub Action；默认约束通过 Markdown、AGENTS、PR 正文模板和 dogfood 落地。
- 不改变 issue-status 备忘录已声明的标签创建、阶段标签和长尾分拣动作；只阻止 PR 关键词绕过这些动作。

## 3. 方案

### 3.1 Markdown-first 默认边界

落点在 `main@1261022` 上已存在的三处，都在既有节里补，不另建文件：

- `references/apply-to-project.md` **§十 采用契约**：在〈通用处理顺序〉与〈修饰词登记表〉附近补一段「默认项目资产边界」；
- `SKILL.md`：〈应用到项目〉段或〈项目体例与参考〉总则补一句边界（字数账见 §3.7）；
- 三个选修备忘录的「采用口径」区块与 §十 登记表保持同一口径，不改它们已声明的资产。

边界句：

> spec-flow 默认通过 Markdown、项目指令、模板、PR / issue 正文和收尾报告约束行为；不因为一个选修备忘录被采用，就自动新增脚本、CI、Hook、Workflow、生成器、机器人或其他可执行资产。

“应用到项目”的默认交付物只能来自两类：

- **文档入口**：项目 `AGENTS.md` / `CLAUDE.md` 的指针节、项目规则页、目录与本仓差异；
- **§十 登记表「项目资产」字段明确列出的资产**：例如 `issue-status` 的 7 个 GitHub 标签、`adr` 的 `docs/decisions/` 目录与规则页。

**登记表里没写的资产一律不在默认集合**：脚本、CI、Hook、Workflow、生成器、机器人即使某个备忘录正文提到，也不能因为“正文里写了”就自动创建——要进默认集合，先按 §十〈新备忘录怎么进来〉改动登记表，并过用户。

### 3.2 脚本升级闸

如果 agent 判断某个备忘录的项目级采用无法只靠 Markdown / 模板 / 收尾报告完成，必须停止采用动作，给用户一份短的升级说明：

```text
需要新增可执行资产：<路径 / 类型>
解决的问题：<不加它会漏什么>
触发方式：<何时运行 / 谁运行>
维护成本：<项目新增什么长期负担>
Markdown-only 替代方案：<能否接受；代价是什么>
```

只有用户明确同意新增该资产后，才继续；同意只授权本次明确列出的路径和用途，不扩展为长期任意脚本写入权，并在收尾报告里列出获准的路径与维护成本。

如果用户不同意：

- 采用动作回落到 Markdown-only 版本；
- 在项目入口写明哪些部分是人工执行；
- 在收尾报告写明“未加脚本，因此没有机械拦截”；
- 不把“脚本没加”伪报成“检查已通过”。

该升级闸不新增脚本来自动执行；它本身只是一条 Markdown 规则和用户确认点。

### 3.3 `apply-to-project` 的具体边界

落点：`references/apply-to-project.md` **§十 采用契约**——在〈通用处理顺序〉六步的基础上补一条，放在第 3 步（写项目指令短入口）之前：

- 写入或创建前，先列本次会新增 / 修改的文件和远端资产；
- 默认集合中不得出现脚本、CI、Hook、Workflow、生成器、机器人；
- 若 modifier 的项目资产包含这些类型，先走 3.2 的升级闸；没有用户明确同意就停在“材料备好”；
- 已存在的项目脚本可以按项目现有规则读取或运行，但本次不新增、不改写、不扩展其扫描面；
- `issue-status` 的标签创建仍按其已声明动作执行——标签写在 §十 登记表的「项目资产」字段里，不是脚本，不因此被禁止；
- 报告中列出跳过的脚本 / CI / Hook 资产，避免用户以为它们已经安装。

重复应用时继续遵循幂等：不重复写入口、不重复建规则页、不重复创建已存在资产；发现项目自带规则与中央模板冲突时只报告并停在用户裁决点。

### 3.4 PR 正文的 issue 关联与关单

spec-flow 生成或建议的 PR 正文默认使用中性关联语句：

```md
关联 issue：#N

本 PR 合并后按 spec-flow 第 9 步回填验收、更新阶段并决定是否关闭 issue。
```

默认禁止在 PR 正文中使用会触发 GitHub 自动关闭的关键词组合，包括：

- `Closes #N` / `Close #N` / `Closed #N`；
- `Fixes #N` / `Fix #N` / `Fixed #N`；
- `Resolves #N` / `Resolve #N` / `Resolved #N`；
- 同义的带仓库限定写法和同一行中的多个自动关闭关键词。

可使用普通链接、`关联 issue`、`Refs #N` 或项目约定的非自动关闭关联写法。项目自己的 PR 模板若已有自动关闭关键词，spec-flow 不擅自改写；执行前报告其副作用并按项目规则 / 用户决定处理。

### 3.5 真实关单时点

默认生命周期：

1. spec PR：只交付 spec，不关联一个尚未建立的实施 issue；
2. 实施 issue：spec PR 合并后建立，正文锚 spec 永久链接；
3. 实施 PR：正文只关联 issue，不自动关闭；
4. PR 合并后：按第 9 步回填验收证据、评论、阶段标签和长尾分拣；
5. 回填完成后才显式关闭 issue。

项目采用 `issue-status` 时，按其“上线时分拣”决定是直接关单、先转“待验证”还是保留卡点；没有采用时，按主流程有限承诺和项目规则决定是否关闭。

如果用户明确要求“本 PR 合并后自动关闭 #N”，agent 必须先说明这会绕过第 9 步回填，再由用户确认；确认后才允许使用自动关单关键词，并在 PR 正文和收尾报告中记录这是一次明确例外，写明因此跳过的回填动作。

### 3.6 与已落地实现（#74 / #75）的关系

不再有「重做 #74」的问题——它和它的实施都已合并。三条口径：

- **采用契约的形状以 §十 为准**：两种运行模式（本次按需读取 / 项目级持久采用）、通用处理顺序、修饰词登记表（每张八项字段、含「项目资产」）。`SKILL.md` 参考表的「选修，默认关闭」是同一件事的登记侧说法，本 spec 不再另造第三套措辞；
- **`check-docs.sh` 里新增的采用契约一节（rationale R20）不是本 spec 要拦的东西**：它并进既有入口、不另起脚本，也不属于「脚本、CI、Hook、Workflow、生成器、机器人」这类可执行资产，无需重新授权或回退；本 spec 自身不新增检查脚本；
- **#75 已声明的项目资产照旧生效**：`issue-status` 的 7 个标签、`adr` 的 `docs/decisions/` 目录与规则页都写在 §十 登记表的「项目资产」字段里，属于默认集合；本 spec 只要求「登记表里没写的资产不得自动创建」。

### 3.7 `SKILL.md` 字数账（审核修订新增）

`scripts/check-docs.sh` 口径实测（2026-10-15，`main@1261022`）：正文 **4,995 / 5,000（余量 5 字）**，警示符 **3 / 3（⚠ 2 + ⛔ 1）**。

- 本条边界要往 `SKILL.md` 加句子时，必须**同批腾挪**，净增 ≤ 5 字，**不上调预算**（`BUDGET_CHARS`）、**不加警示符**（`MAX_ALERTS`）；
- 腾挪落点先看 rationale R19 已用过的那三处还剩多少，不够就另找并逐字符实测；腾挪必须保持原规则语义，不许为了腾地方弱化文字；
- 腾不出 5 字就**停下问用户**：要么换落点，要么把边界句整句落 `apply-to-project.md` §十、`SKILL.md` 一字不加；
- 账目（加了多少、从哪腾、终值）写进 `references/rationale.md` 的新 R 号，并在实施 PR 正文贴实测数字。

## 4. Dogfood 与验收

**跑法与产物（沿用既定形状）**：两组 dogfood 一律在**临时假仓**里跑，不碰任何真实采用项目（对真实项目只做只读核对）；产物是实施 PR 正文里的场景记录，形状 = 场景 / 输入 / 实际动作 / 证据（命令 + 输出摘要）/ 结论（同一形状见 `references/apply-to-project.md` §十〈验收契约〉与 rationale R20，本 spec 不另造）。

### 4.1 脚本边界

| 场景 | 输入 | 预期 |
|---|---|---|
| 普通采用 | 用户要求应用 `adr` | 只写入口、规则页和 ADR 目录，不新增脚本 / CI / Hook |
| 标签采用 | 用户要求应用 `issue-status` | 按 modifier 明确动作创建标签；不新增脚本 |
| 需要脚本 | 备忘录实现需要 CI 才能拦漏项 | agent 停止并报告脚本升级说明，不直接创建 |
| 用户同意脚本 | 用户明确同意某个具体脚本路径和用途 | 只创建获准资产，并在收尾报告列出获准路径与维护成本 |
| 用户拒绝脚本 | 用户不授权脚本 | 回落 Markdown-only 采用，报告人工执行边界 |
| 既有脚本 | 项目已经有文档检查脚本 | 可以按项目现有规则读取 / 运行，不修改、不新增 |

### 4.2 PR 关单边界

| 场景 | PR 正文 | 预期 issue 状态 |
|---|---|---|
| spec PR | 无实施 issue 自动关闭关键词 | 不触发自动关单 |
| 普通实施 PR | `关联 issue：#N` | 合并后由第 9 步回填再关单 |
| issue-status 项目有长尾 | `关联 issue：#N` | 合并后按阶段标签和“待验证”分拣，不被合并动作直接关闭 |
| 用户明确例外 | 用户确认合并即自动关单 | 允许关键词，PR 正文与收尾报告记录例外及跳过的回填动作 |
| PR 模板已有关键词 | 项目模板自带自动关单 | agent 先报告副作用，不伪装为 spec-flow 默认行为 |

### 4.3 完成标准

- [ ] `SKILL.md` 和 `references/apply-to-project.md` §十 明确 Markdown-first 默认边界。
- [ ] `apply-to-project` 默认不会新增 / 修改脚本、CI、Hook、Workflow、生成器或机器人；默认集合与 §十 登记表「项目资产」字段一致。
- [ ] 需要可执行资产时，采用动作会停在升级闸，用户未明确同意不能继续；同意后报告列出获准路径与维护成本。
- [ ] `issue-status` 的标签资产不被错误禁止，且没有脚本副作用。
- [ ] spec-flow 默认 PR 正文使用“关联 issue”，不出现自动关单关键词。
- [ ] 第 9 步的显式回填、阶段分拣和关单时点与 issue-status 采用口径一致；例外场景写明跳过的回填动作。
- [ ] 用户明确例外时可使用自动关单关键词，并在 PR 正文和收尾报告留下例外记录。
- [ ] `SKILL.md` 改动后 `scripts/check-docs.sh` 仍绿（字数与警示符都在预算内，见 §3.7）。
- [ ] 新增规则按仓规 3 进 `references/rationale.md` 编新 R 号；两份 README 的 R 区间同批同步（仓规 5）。
- [ ] 两组 dogfood 在临时假仓跑完，产物落在实施 PR 正文（场景记录形状）；验证不新增脚本。
- [ ] 已合并的 #74 / #75 内容未被改写；本 spec 的边界落在它们的既有节上。

| 6 | 以 main（`1261022` 及以后）为准做一次落点对表 | 不重写 §十 已定形状，不留下两套相反默认规则 |

实施前必须先 `git fetch`，从最新 main 开新 worktree，改动落在已合并的节上，不另起平行结构。

## 6. 机制清单

| 机制 | 解决什么 / 没有它会怎样 | 本次处置 |
|---|---|---|
| M1 Markdown-first 采用边界 | 防止选修备忘录一落项目就带来脚本、CI、Hook 等维护负担 | 新增中央默认边界 |
| M2 可执行资产升级闸 | 某些备忘录确实需要脚本时，让用户知道成本并明确授权 | 新增用户确认点，不新增脚本实现 |
| M3 PR 关联而非自动关单 | 防止 GitHub 合并动作绕过验收回填和 issue-status 分拣 | 新增核心流程规则 |
| M4 自动关单例外记录 | 保留用户明确要求自动关单的出口，同时不把例外变成默认 | 新增例外记录要求 |
| M5 脚本升级说明模板（五字段） | 升级闸没有固定问法时，用户拿不到判断成本所需的信息 | 新增固定形状，随 M2 落 |
| M6 中性关联文案「关联 issue：#N」 | 不给默认写法，agent 会各自发明，自动关单关键词就回来了 | 新增固定文案，随 M3 落 |
| M7 默认关单时点（五步生命周期） | 只禁关键词、不说清何时关单，实施方仍会在合并瞬间顺手关单 | 新增时点规则，随 M3 落 |
| M8 `SKILL.md` 字数账 | 中央规则有字数与警示符预算，不先算账就会撞检查、或为腾地方弱化规则 | 新增实施约束，见 §3.7 |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 只靠 Markdown 约束，漏写无法机械拦截 | 用固定 PR 文案、采用报告和 dogfood 暴露遗漏；不伪装成硬检查 |
| `SKILL.md` 余量只剩 5 字，边界句加不进去 | §3.7 字数账：同批腾挪、不上调预算、不加警示符、腾不出停下问用户并考虑整句落 §十 |
| 用户明确要脚本时被默认规则挡住 | 提供脚本升级闸，列清路径、用途、维护成本和替代方案后让用户授权，同意后报告列出获准项 |
| `Closes #N` 已存在于项目 PR 模板 | 不擅自修改；先报告自动关单副作用，由项目 owner 决定是否改模板 |
| 落点与 #75 已落地的 §十 / 参考表 / 检查节错位 | 实施前以 main 为准逐条对表（§5 批次 6）；只新增边界，不重写已定形状 |
| issue-status 的阶段分拣与普通关单规则打架 | 本 spec 只禁止自动关单，不改 issue-status 自身阶段判据；两者在第 9 步统一执行 |
| 例外被滥用成默认 | 每次例外必须是用户针对本次具体 PR 的明确指令，且记录在 PR / 收尾报告 |
| dogfood 在真实项目上跑，动了别人的仓 | 一律临时假仓；对真实采用项目只做只读核对 |

## 8. 自定细节

本 spec 未由用户逐项指定、由 agent 为实现完整性暂定的细节：

1. 默认中性 issue 关联文案使用“关联 issue：#N”，不绑定某个项目自己的 PR 模板。
2. 默认禁止的自动关单关键词按 `Closes` / `Fixes` / `Resolves` 三组及其常见时态、大小写和仓库限定写法理解。
3. 项目已有 PR 模板不自动改写；它的副作用由 agent 报告，是否改由项目 owner 决定。
4. `issue-status` 创建 GitHub 标签属于 §十 登记表已声明的远端资产，不归入本 spec 禁止的“可执行资产”。
5. 本 spec 不新增检查脚本；验收用 Markdown、PR 正文和受控 dogfood 完成。
6. 基线是 main 上的实际文本（本次 `1261022` 及以后）；#74 / #75 已落地内容按 §3.6 处置，不再按旧稿的「等 #74 合并」执行。
7. `SKILL.md` 改动按 §3.7 的字数账办：净增 ≤ 5 字、不上调预算、不加警示符、腾不出就停下问用户。
8. dogfood 一律在临时假仓跑，产物落实施 PR 正文的「场景 / 输入 / 实际动作 / 证据 / 结论」记录。
9. 机制清单按 #74 同批先例补到 M5–M8（具名构件各自一行）；若用户认为 M2 / M3 已覆盖 M5–M7，可退回合并。
10. 「默认项目资产边界」的正文落 §十 而非另建参考文件——与 R19 同理由：另建要再付参考表行、两份 README、rationale 三笔账。
