## 1. 要解什么问题

用户要的不是「加一份代码地图文档」，而是**代码地图成为流程的一部分**：agent 在用地图的那个动作上就该想到它，而不是被提醒「这里有一份文档」。

### 1.1 两种做法实测对比（口径同 `check-docs.sh`）

|---|---|---|
| **加一块**（原设想） | **212 字符** | 正文多一节「代码地图」——孤立的单元 |
| **织进去**（本 spec） | **124 字符** | 总则一句 + 三处挂点，长在已有动作上 |

**编织省 88 字符，且不新增章节。** 这是本 spec 的核心设计选择。

## 2. 设计：四类挂点，零新章节

代码地图不成为一节，而是四个小句，每个都长在**本来就存在的动作**上。

| # | 挂在哪 | 现在那句 | 织进去的动作 | 字符 |
|---|---|---|---|---|
| 1 | **主线总则** | 「需求 → spec → issue → 实施」 | 动笔前先看地图：改哪、谁受影响 | 46 |
| 2 | **第 3 步** | 「用户点头之后才出 spec」 | 改动面先查图再落笔 | 19 |
| 3 | **闸·不审档** | 「agent 自己拿 diff 对改动面过一遍」 | 受影响者用地图查 | 10 |
| 4 | **参考表** | — | 新增 `code-map.md` 一行（细则入口） | 46 |
| | | | **合计** | **121** |

**为什么是这四处**（不是随便选的）：

- **总则**——九步共同的前提，地图是「动笔前」的事，不是某一步的事；
- **第 3 步**——spec 要写改动面，这是改动面第一次需要证据的地方；
- **闸的「不审」档**——那是 agent 唯一自己拿 diff 对账的档位，正是地图「谁受影响」最能帮上忙的时刻；
- **参考表**——细则的入口，与既有 `gate-details.md` / `worktree-lock.md` 同形。

### 2.1 不挂在哪，为什么

| 步 | 为什么不挂 |
|---|---|
| 第 1、2 步 | 需求还没成形，此时查图先于需求，是浪费 |
| 第 7、8 步 | 实施期查图有价值，但**同一套动作已在总则覆盖**；重复挂会稀释 |
| 新开一节 | 正是用户点名不要的「孤零零一个单元」 |

## 3. 新建 `references/code-map.md`

正文只留动作，细则全部在此。内容：

1. **安装方式 C**：二进制装在电脑里（`brew tap JordanCoin/tap && brew install codemap`，`ast-grep` 随 formula 自动带上）；**项目里不装、不跑 `setup`**——`setup` 会写 `.claude/settings.local.json`、`.codex/hooks.json`、`.mcp.json`、`.codex/config.toml` 并拉常驻 daemon，属可执行资产，须另行授权。
2. **项目入口四要素**：工具名 + 命令 + 扫描范围 + **声明的版本基线**。写进项目自己的 `AGENTS.md`。
3. **版本基线判定**：低于声明基线 → 按「分析不完整」处理，如实报告。
4. **覆盖率怎么读**：`complete` / `partial` / `unavailable` 三档，以及 `authoritative` / `mixed` / `fallback` / `timeout` / `unavailable` / `failed` 来源状态；超时返回的是**带来源的空结果**，不是空图。
5. **降级报告形状**：缺工具 / 版本旧 / 语言不支持 / 分析不全时，如实报「本仓库代码地图不可用 / 不完整」并回落源码搜索，**不得报成「检查通过」**。
6. **关闭句**：项目 `AGENTS.md` 写「本仓不适用代码地图」即关闭。
7. **已知边界（诚实标）**：静态 import 之外的关系（事件、数据库约定、运行时注入、跨服务调用）不在图里；地图不替代测试与审核；**它不是索引**——不落盘、每次重扫，省的是「少读几十个文件」，不是查询延迟。
8. **本仓提示**：spec-flow 本身是 markdown 为主的仓，地图增量接近零；别把第一张图花在这里。

### 4.1 必须同时改 `scripts/check-docs.sh`

这是本 spec **唯一的机制改动**，理由要说清：

现行脚本对三行做**逐行字面校验**，要求每行都含「默认关闭」与「声明已采用」（`check-docs.sh` 采用契约一节）。把共通句提到表上方后，三行不再字面含这两串，脚本会判红。

**改法**：把校验从「逐行必须含」改为「三行所在区域含一次」，语义不变——规则仍然是「选修备忘录必须有默认关闭与读取条件」，只是不再要求逐行复述。

**为什么这个改法安全**：检查的目的是「防止某个选修备忘录被漏写读取条件」。区域校验同样能拦：少写就是区域里没有。**逐行校验拦的是「重复」，不是「遗漏」。**

**实测省下 39 字符**（含新增共通说明 63 字符；此前 spec 草稿写的「56」是错的，以实测为准）。

## 8. 机制清单

| # | 机制 | 解决什么 / 没有它会怎样 |
|---|---|---|
| 1 | **编织式挂点**（总则 + 三小句） | 地图成为流程的一部分而非独立文档 / 没有它：正文多一节，读起来仍是一份「文档」 |
| 2 | `references/code-map.md` | 装法、基线、覆盖率、降级形状 / 没有它：细节挤正文，塞不下 |
| 3 | 参考表区域化校验 | 去重不削弱契约 / 没有它：要么重复三遍，要么漏检 |
| 4 | 项目入口四要素 | 项目声明本仓怎么查 / 没有它：agent 不知道敲什么命令 |
| 5 | 「本仓不适用代码地图」关闭句 | 小仓 / 文档仓退出 / 没有它：小项目白付扫描成本 |
| 6 | 版本基线 + 降级报告 | 版本不一致时不会骗人对账 / 没有它：旧版结果被当成查全 |
