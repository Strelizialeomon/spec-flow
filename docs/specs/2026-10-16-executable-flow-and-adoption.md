## 1. 为什么要一起整理

用户的两个目标是：减小技能的常驻正文；让代码地图自然参与需求、实施和交付，而不是增加一份孤立说明。

现在的问题不只是缺少一个启用词。规则生效、项目接入、工具是否就绪、任务里何时执行和交付时如何验证，没有形成一致的使用路径。用户进一步要求核对正文是否还足以驱动 SOP，并加强后补 ADR 制度的老项目的日常唤起。

本次要交付的是可执行的流程契约，不是实施计划。原有两段九步及用户拍板权保留，不再靠逐句补丁逼近字数上限。

### 1.2 本次没有证明什么

- 未证明用户感受到的某一次不顺，必然由上述某一条文字造成；没有拿静态检查替代会话回读。
- 未证明把全部细则移入 reference 会自动省下每次任务的总 token；被实际读取的细则仍有成本。
- 未证明所有客户端、模型和压缩后的新会话均会正确读取入口。链接存在、脚本全绿和一次成功执行，都不是永久保证。
- 未把四处有查图句子、没有新增章节，等同于完整使用路径已经验证。

## 2. 目标与不变边界

### 2.1 要达到的结果

1. 用户能够清楚区分技能安装、项目接入、工具就绪和日常任务执行；不必猜一个内部修饰词才能开始。
2. 新项目应用、老项目显式升级和单独配置代码地图，共用既有接入检查，不维护互相独立的流程副本。
3. 正文保留硬关口和动作路由，必须细则在使用当刻读取；reference 的存放位置不决定其是否可忽略。
4. 代码地图的结果用于确定改动面、受影响者和验证线索；工具不可用或不覆盖目标时诚实回落源码调查。
5. 已采用 ADR 的项目，无需用户提醒查旧决定或写新决定；新需求、认领旧 issue 和实施中形成的新决定均有对应动作。
6. 用受控使用场景检验 SOP，而不只是验证字符串、字数和文件存在。
7. 在不删硬判据、不把规则复制到另一份常驻指令的前提下，交付正文实测净缩短。

### 2.2 用户已经选择的边界

- **老项目显式升级一次。** 普通业务任务不得因缺少代码地图入口就顺手修改项目规则或补持久配置。
- 正文逐条保全、已采用 ADR 的日常唤起、完整场景验收三项共同纳入。
- 不新增流程步骤、审核档位或业务项目脚本；不自动安装工具、运行 setup、创建 Hook、MCP 或 daemon。
- 本轮只修改中央流程契约。真实采用项目只读核对，不因中央规则更新就批量改项目或回写历史规格。

## 3. 内容职责：按效力和动作分，不按目录猜

| 内容 | 职责与效力 |
|---|---|
| `SKILL.md` | 两段主线、硬关口、卡片与豁免，以及在什么动作前读取哪份细则；每条硬规则至少保留核心判据 |
| 执行细则 | 随动作触发，命中时必须读取并执行；用于闸、锁、修订、完成标准、拆分依赖、地图和项目接入，不因位于 references 而降为选修 |
| 选修能力 | ADR、文档生命周期、issue 状态标签仍须用户或项目明确采用；一旦采用，相关任务到达触发点就执行，不每次重新问是否启用 |
| 历史说明 | rationale、采纳演进和细则中的历史案例解释来由，不自行创建新义务；与现行规则冲突时不能拿旧案例替代现行契约 |

读取指针须直接从主文件可达，并标明真实动作。触发时没有读过所需细则，不得声称已按该细则完成；长会话中也不能把早先读过、如今已不可见当作仍掌握全部细节。

不新增一套通用插件框架、适配器、制度登记平台或第二份规则入口。沿用现有文件和采用契约，只校正它们各自负责的内容。

## 4. 一条主线中的动作与结果

| 既有时点 | 必须执行的相关动作 | 结果去向 |
|---|---|---|
| 进入任务 | 读取真实项目入口与适用的域规则，辨别新需求、已有 issue 或显式接入请求，确认已采用哪些选修能力 | 决定本次应执行的规则，不持久改项目制度 |
| 第 2 步确认需求 | 有明确任务方向后按需核对现状与相关代码；已采用 ADR 时搜索相关现行决定 | 支撑业务岔路、范围与已有约束，不无目标全仓扫描 |
| 第 3 步出 spec | 需求确认后写范围和验收；地图可用时使用其证据；消化已采用项目的 ADR 约束与本次已拍板决定 | spec 只保留相关证据、链接和本次处理结果 |
| 第 4/5 步过闸与修订 | 读取闸及修订细则，执行原有卡片、检查和同步规则 | PR 评论、修订处置，不增加审核档位 |
| 第 6 步开 issue | 锚已合并规格的永久链接，沿规格到达相关 ADR | 保持现有 issue 正文边界，不复制图或 ADR 正文 |
| 第 7/8 步实施 | 认领隔离工作区；读取当前任务的获批 spec；在自己的代码状态上核对影响和当前 ADR | 实施范围、验证项与证据；旧规格缺 ADR 字段不能免查 |
| 第 9 步交付 | 对实际 diff、受影响者、批准范围和验证结果对账；已采用 ADR 时核对引用与本次新决定是否落地 | 现有 PR 和验收证据，不建立额外流水账 |
| 合并后回填 | 按完成标准与项目已采用的收尾规则回填、决定关单并放锁 | 元信息和 issue 反映实际状态，不跳过验证阶段 |
| 下一任务 | 重新核对当前代码和现行决定 | 不把历史地图或旧会话摘要当成当前系统状态 |

地图作为调查手段的核心要求，与项目是否已配置完成分开。两段的所有相关任务均适用，不把地图限定在不审档；审核档位不决定是否需要查明影响。

未涉及代码依赖的文档任务、小范围且图没有净收益的任务、项目已声明不适用地图的任务，沿用合理跳过与如实说明，不制造固定扫描开销。

## 5. 项目接入：新旧同路，持久变更显式授权

### 5.1 用户能直接说出的三个入口

- 「把 spec-flow 应用到本项目」：首次应用；已应用过时按同一契约校验，不重复追加。
- 「更新本项目的 spec-flow 接入」：显式升级已有入口，补本次相关的缺项；不自动开启尚未采用的选修能力。
- 「为本项目配置代码地图」或「启用 code-map」：识别为代码地图的配置请求，不当作不认识的描述，也不为迎合现有检查把核心配置伪装成第四个选修制度。

动作和采用条件由现有接入细则统一说明。登记、模板、中央指针与检查保持一致，不再出现只加一张登记表、对应入口不变却宣称可通过的方案。

### 5.2 接入的共同要求

1. 先检查项目真实入口、已有制度与工具、符号链接和目标文件位置。指向仓外的共享指令仍必须停下报告，不能污染其他项目。
2. 明确本次准备写哪些项目文档、非可执行配置和本机 Git 元数据，哪些不做；已有配置优先读取和复用，不静默覆盖或扩大扫描面。
3. 入口仍为短指针加项目落点。代码地图要有工具、已验证版本基线、可实际执行的命令、与命令一致的扫描范围；只在文字中声明范围不算完成。
4. 已采用 ADR 的项目保留自己的唯一规则页、目录、命名和体例；补齐真实动作入口，而不是另建第二份制度。
5. 新工具安装、setup、Hook、MCP、后台进程及新增项目脚本不在默认授权内；确实需要时走原有可执行资产升级闸。
6. 报告分清规则入口已更新、工具是否可用、配置是否就绪、本次验证是否执行及限制。不能用一句启用成功掩盖后面三项未做。
7. 重复执行须幂等；现行旧副本检测、只报告不自动删改及不猜未知描述的边界保留。

### 5.3 普通任务遇到缺项

普通业务任务不主动应用、升级或补写项目入口。可以只读识别工具及已有配置；发现地图未就绪、版本不满足或查询会产生未经说明的写入时，说明原因并回落源码，不先执行扫描来试探它会不会写入。

缺工具本身不阻断所有任务。回落后若仍无法确定关键范围或既有决定，暂停受影响部分，只询问真正需要用户决定的业务问题。

项目已采用 ADR 但入口不可达时，同样报告真实缺口，不静默降级成未采用，也不借业务任务顺手建立新规则页。需要持久修复的交给显式升级；能只读找到原规则和现行决定时仍应遵守。

## 6. 代码地图：结果可信的最低条件

- 核对实际分析的工作区、代码状态、扫描范围和差异基准。影响查询必须对应真实交付 diff；不能因为工具默认比较 main，就在 master 或其他 PR 基准上照用。
- 同时看整体覆盖率、目标是否被索引、来源状态与诊断、排除项及输出截断。complete 仅描述工具对其分析范围的声明，不保证目标已覆盖或仓外业务依赖不存在。
- `not_indexed: true`、缺失目标、范围不一致、未覆盖的新文件或不完整 diff，都不能解释为无依赖；相关部分回落源码核对。工具未提供某项证据时如实注明，不自行补出成功状态。
- 保留现有缺工具、低于版本基线、语言不支持和分析不完整时的诚实回落。未知的新版本行为不能只凭版本号更高就认定兼容。
- 不跑 setup 不代表零写入。常规命令可能创建本地配置或修改 Git 忽略；首次使用及升级须交代这些已知副作用，不能仅凭 git status 干净声称没有写入。
- 项目规则中的扫描范围必须由实际参数或已说明的配置实现，并验证目标覆盖；不默许每条命令各扫不同范围。
- 记录本次采用的命令、工作区与基准、重要发现和限制，放进现有需求或交付证据。只保留任务相关摘要，不提交全量图、不维护手工影响总台账。
- 静态依赖图不替代事件、数据库约定、跨服务契约等调查，不替代测试、审核或业务批准；发现范围外影响先报告，不自动夹带修复。

## 7. 已采用 ADR 的唤起与老项目兼容

### 7.1 开工：先搜索，才能知道是否命中

确认项目已采用 ADR 后，在任务有明确方向时按业务词、表名、接口名、组件名及已知决定 ID 搜相关现行决定，读取命中的完整记录与取代关系。不能等到已经知道命中某条 ADR，才决定是否搜索。

新需求与认领旧 issue 都经过这一步。旧规格没有 ADR 字段、不在本轮新建 spec、直接进入实施，都不意味着当前项目没有长期约束。

搜索只围绕当前任务，不要求每次通读全部 ADR。不命中时保留实际检索词与结论；不把没找到当作已经证明系统没有任何旧决定。

后补制度的项目默认不倒灌全部历史。当前任务确实遇到旧决定时，核对项目指定的现状文档、当前任务规格与可核的用户来源；不能从现有实现倒推出用户已经拍板。来源不明的保留不确定性，必要时问业务边界，不伪造生效 ADR。

### 7.2 拍板后：判断长期影响，不让用户提醒流程动作

用户已拍板且命中现有写入条件时，在继续相关设计或实现前新增或取代 ADR；不再问用户要不要写 ADR。灰区只问适用范围、有效期或对外契约等业务边界。

尚未拍板的候选不写成生效决定。局部命名、普通实现细节、客观事实和进度不因为加强唤起而全部变成 ADR。

沿用新增、双向取代、只链不抄和同一文档交付的现有规则；没有新建 spec 的任务不为补字段重写历史规格，相关处理记录放当前任务的现有 PR 或 issue。引用旧决定与形成新决定要区分。

### 7.3 收尾：核的是本次结果，不是再设一道打卡

核对本次引用是否仍指向现行决定，取代的两端是否一致，已拍板的新长期决定是否有真实记录。已知缺项按原有修订和业务批准规则处理，不能用这条绕过修订卡、改旧 spec 卡或用户决策权。

新规格须能区分所遵守的现行决定与本次新增、取代或无需记录的原因；优先复用项目已有字段和名称，不强迫所有采用项目改成同一模板。旧任务在当前交付载体补证据，不批量回写旧规格。

未采用 ADR 的项目仍不增加这些动作、字段、目录或提醒；一次性要求写一条仍不升级为永久制度。项目明确禁止为治理本身创建 ADR 的，也不能借加强唤起越过该边界。

### 7.4 现状、当前需求和历史分开

- 现状文档及实测回答系统现在是什么。
- 当前任务的获批 spec 与验收约束本次要改成什么，实施前必须读。
- 已采用项目的现行 ADR 约束跨任务决定；当前需求若要改变它，须用户拍板并按取代规则处理。
- 历史规格只在追溯时按需读。不能把这一默认读序套到当前施工规格，也不能拿当前实现不一样为由自行改写获批需求。

## 10. 机制清单与已确认取舍

用户在本轮机制卡选择全要；显式升级的权限边界另由选择卡确认。

| 机制或既有机制的调整 | 解决什么 / 没有它会怎样 |
|---|---|
| 按动作必须读取的细则约定 | 把常驻判据与按需细则接起来；否则文件齐全也可能被按参考忽略 |
| 同一接入契约中的显式升级 | 新旧项目可重复接入且不夹带业务变更；否则老项目只剩不可用报告或自动补规则两种相反行为 |
| 已采用 ADR 的开工、拍板后、收尾动作及旧任务兼容 | 用户只拍业务，agent 负责消费与记录；否则旧任务或无字段任务可能绕过现行决定 |
| 静态保全与使用场景双轨验收 | 证明文字之外的真实动作；否则四处插句和脚本全绿继续被当作闭环已成 |

主要取舍：每个老项目多一次显式升级指令；任务按需读取细则仍有 token 和查询成本；新会话行为验证需要实际客户端条件。换来的是日常任务不暗改制度、规则不靠全文常驻、未覆盖的分析不再被称作通过。
