## 1. 为什么要一起整理

用户的两个目标是：减小技能的常驻正文；让代码地图自然参与需求、实施和交付，而不是增加一份孤立说明。

现在的问题不只是缺少一个启用词。规则生效、项目接入、工具就绪、任务执行和交付验证，没有形成一致的使用路径。用户进一步要求核对正文是否还足以驱动 SOP，并加强后补 ADR 制度的老项目唤起。

本次交付可执行的流程契约，不出实施计划。原有两段九步及用户拍板权保留，不靠逐句补丁逼近字数上限。

## 2. 目标与不变边界

### 2.1 要达到的结果

1. 区分技能安装、项目接入、工具就绪与日常执行；用户不用猜内部修饰词。
2. 新项目应用、老项目显式升级及单独配置地图，共用既有接入检查，不造流程副本。
3. 正文保留硬关口和动作路由，细则在使用当刻读取；位置不决定其可否忽略。
4. 地图结果用于改动面、受影响者与验证线索；不可用或不覆盖目标时诚实回落。
5. 已采用 ADR 的项目，无需用户提醒查旧决定或记录已拍板的新决定；新需求、旧 issue 和免方案期任务均有动作挂点。
6. 用实际场景检验触发与执行，而不只验字符串、字数和文件存在。
7. 正文不超过 4,700 字符、整份不超过 5,200，分别较基线至少净减 289 与 190；保全判据，不靠 frontmatter 或第二份常驻副本转移规则。

### 2.2 用户已经选择的边界

- **老项目首次补齐走显式升级。** 后续仍可显式升级，重复操作须幂等；「一次」是首次接入成本，不是终身只能升级一次。普通业务任务不顺手修改项目规则或补持久配置。
- 正文逐条保全、已采用 ADR 的日常唤起、完整场景验收共同纳入。
- 不新增流程步骤、审核档位或业务仓脚本；配置请求不自动授权安装工具、setup、Hook、MCP 或 daemon。
- 本轮只修改中央契约；真实采用项目只读核对，不批量更新项目或历史规格。

## 3. 内容职责与触发面

| 内容 | 职责与效力 |
|---|---|
| `SKILL.md` 正文 | 两段主线、硬关口、卡与豁免、动作路由及必读细则；硬规则至少保留核心判据 |
| 执行细则 | 命中动作就必须读、执行；不因位于 references 而降成选修 |
| 选修能力 | ADR、文档生命周期、issue 标签须明确采用；采用后相关动作自动执行，不每次重问启用 |
| 历史说明 | rationale、采纳演进及历史案例只解释原因，不自行创设新义务 |

读取指针从主文件直接可达并标明动作。使用所需细则已不可见、被压缩丢失或版本已变时，在动作前重新读取；不能拿早先读过冒充当前仍掌握。无须每次全量重读全部参考。

frontmatter 的 `description` 负责技能尚未加载时的触发摘要，必须覆盖复杂需求、认领 issue、应用、更新接入和配置地图等意图；README 同步用户可用的说法。命中关键词不是已正确调用的证明，须用技能未预载的新会话验证。

允许为触发摘要增加必要文字，但不得将硬规则、表格或正文搬进 frontmatter 来省预算。只加入口语义，不藏执行细则；按 §9.1 同时验正文、frontmatter 和整份，不把 body 变小冒充总上下文成本下降。

不新增通用插件框架、适配器、制度平台或第二份常驻入口。

## 4. 动作挂点：不增加第 0 步或第 10 步

下面是既有段落和步骤的动作映射，不是新增编号、固定打卡或额外闸。「下一任务」是重新使用同一入口，不是上一任务的第十步。

| 既有落点 | 相关动作 | 结果去向 |
|---|---|---|
| 主线说明与应用到项目段 | 辨别新需求、已有 issue、显式接入；读取适用项目和域入口，确认已采用能力 | 分别进入段一、段二或既有接入动作 |
| 第 2 步调查与确认 | 按任务核对现状、代码；已采用 ADR 时搜索相关现行决定 | 支撑业务岔路、范围和约束，不无目标扫全仓 |
| 第 3 步出 spec | 确认需求后写范围与验收；使用可用地图依据，处理沿用及已拍板的新决定 | 任务相关证据、链接及本次处理 |
| 第 4/5 步过闸与修订 | 按原卡片、文档检查及同步要求执行 | PR 原文评论、用户处置，不增加档位 |
| 第 6 步开 issue | 锚已合并规格，沿规格到达相关 ADR | 不复制图或 ADR 正文 |
| 第 7 步认领、首次实施前 | 从 issue 进入也先读获批 spec，已采用 ADR 时实际检索现行约束 | 不因无第 2 步、旧 spec 缺字段而免查 |
| 第 8 步实施、免方案期的首次实施前 | 在自己的工作区核对影响和相关现行决定；实施中出现已拍板长期决定仍按条件记录 | 约定范围和验证证据，不重启整套方案期 |
| 第 9 步交付与回填 | 对实际 diff、范围、验证和已采用约束对账，核本次 ADR；合并后按完成标准和收尾规则回填、决定关单、放锁 | 现有 PR、验收与 issue，不加流水账 |
| 另一任务再次使用主线入口 | 重新核对其代码与现行决定 | 不沿用上一任务的图或旧会话摘要作现状 |

地图是调查手段，不是一个因登记为选修才存在的制度；适用且就绪时两段均使用，不由审核档位决定是否查清影响。纯文档、不涉及代码依赖、项目已声明不适用或小任务没有净收益时，合理跳过并如实说明，不制造固定扫描成本。

## 5. 新旧项目接入与具体授权

### 5.1 能被识别的入口意图

下列句子是 agent 拟定的可用示例，不是必须逐字输入的口令。按语义识别相同意图；真正未知描述仍问清，不猜成已有修饰词。

- 「把 spec-flow 应用到本项目」：首次应用；已有入口时按同一契约校验。
- 「更新本项目的 spec-flow 接入」：显式升级已有入口，补本次相关缺项，不自动开启未采用的选修。
- 「为本项目配置代码地图」「启用 code-map」：核心配置请求，不当成未知描述，也不为凑登记表把它伪装成第四个选修制度。

这些意图须同时到达 description、正文路由、接入细则和 README。演练不得先替 agent 加载技能，再宣称入口能自动唤起。

### 5.2 接入共同要求

1. 查真实入口、已有制度和工具、符号链接及目标文件；指向仓外共享指令仍停下报告，不污染其他项目。
2. 先说明准备修改的文档、非可执行配置和 Git 本地元数据的具体范围；说明不是授权，需有本次明确同意或可核的项目既有授权。不覆盖自有配置、不扩大范围。
3. 地图保留工具、已验版本基线、实际命令、扫描范围四要素。范围的权威来源须可入仓复现：项目入口中的明确参数，或仅含非敏感策略的版控配置。忽略掉的本地缓存不能是唯一来源；工具某命令不支持参数时，必须验证它实际读取哪份配置，不能写假命令。
4. 已采用 ADR 时复用项目自己的规则页、目录、命名和结果字段；不新建第二份制度。显式升级同时校验相关旧入口与模板，特别是接入细则 §四 的 ADR 动作和 §八 的文档读序。
5. 工具安装是机器级变更。除用户已明确要求这一次安装外，须另行说明来源、版本、依赖和机器影响并取得同意；配置项目不等于允许 brew 安装，也不套用只问项目路径的资产表单。
6. 项目内 setup、Hook、MCP、daemon 和新脚本仍走原有可执行资产升级闸；本需求不默认添加。需要版控配置时只纳入已获准的精确配置文件，不把缓存、日志、凭据或整个忽略目录强行入仓。
7. 已批准的首次查询副作用按 §5.4 留可核入口，版本、命令、路径、范围或作用域变化时重新核对，不把一次批准扩成任意写入权。
8. 收尾分清规则入口、工具、配置及本次验证分别是否完成，列未做和限制；不以启用成功掩盖后续未就绪。
9. 重复应用和再次升级幂等；旧副本仍只报告、不擅删改。

### 5.3 普通任务遇到缺项或旧规则冲突

普通任务不主动应用、升级或补写项目入口。可以只读识别工具和已有配置；地图未就绪、版本未验证或查询需要未获准写入时，说明原因并回落源码，不先扫描来试探副作用。

缺工具本身不阻断全部任务；回落仍无法支撑关键范围时暂停受影响部分。已采用 ADR 但入口不可达，报告真实缺口，不静默降级为未采用；能只读找到原规则和决定时仍应遵守，持久修复交显式升级。

旧模板的「历史 spec 只追溯时读」不包括当前任务施工规格。若项目自有明确条款与此冲突，不由 agent 宣布中央覆盖项目，也不擅改项目；说明具体冲突并停止依赖该冲突的实施，交用户确认或显式升级。已升级项目须实际验证旧读序入口已对齐，不能只测一个全新项目。

### 5.4 授权载体与多工作区

「文档提过副作用」不等于已获准。接入时在项目地图短入口保留可核的授权来源、允许的文件或元数据路径、用途和触发条件；可以链接本次接入 PR 或用户确认记录，不必另建文档。后续任务读取该入口判断权限，不能靠会话记忆。

授权可以明确包含本项目同一 clone 的主检出及未来标准 linked worktree 的同类首次写入；没有明确包含时不能自行外推。未授权的共享 `.git` 元数据或其他工作区写入一律不做，回落源码。

配置与运行状态分开核对。已验证的 codemap 4.6.0 在主检出有配置时可为标准 linked worktree 复用它，同时分析该工作区的代码；不要求每个工作区另造一份配置。主检出没配置、在临时工作区才首次配置、独立 clone 和新机器分别验证，不用上述正例替代。

临时工作区被删除后，本仓范围声明必须仍可从版控来源恢复；若本地派生配置缺失，只能按已明确授权、已验证的约定重建，否则报告未就绪并回落。这里仅允许复现已显式配置的派生文件，不授权普通任务补缺失的制度入口、权威范围或新的配置策略；A04 的未就绪场景仍须零写入。不能依赖一个即将删除的工作区中的忽略文件作为永久设置，也不能把 complete 当作配置持久化证明。

## 6. 地图结果的可信条件

- 核对工作区、代码状态、实际范围和 diff 基准；影响查询对应真实交付 diff，不在 master 或其他 PR 基准上盲用默认 main。
- 同时看覆盖率、目标是否被索引、来源诊断、排除项和截断。complete 只是工具对其分析范围的声明，不保证目标覆盖或仓外依赖不存在。
- 未索引、缺目标、范围不符、漏新文件或不完整 diff 都不能解释为无依赖；相关部分回落源码。工具未提供的证据不由 agent 补成成功。
- 缺工具、低于已验基线、语言不支持、分析不全时保留诚实回落。高于基线但本项目尚未验证兼容性的版本同样按未验证处理：只读报告版本差异并回落，不拿新版本查询结果作已通过证据；通过显式升级在假仓验证契约和副作用后才更新基线。
- 首次查询与后续新工作区执行按 §5.4 的具体权限判断；不跑 setup、工作区干净都不能证明无写入。
- 命令与版控范围一致，并验证四类查询实际读取的参数或配置；不得默许各扫不同范围。查结构与查某个目标可以选择不同输出，但不能隐瞒实际分析边界。
- 记录本次命令、工作区、基准、相关发现及限制，放现有需求或交付证据；不提交整图、不维护手工影响总台账。
- 静态图不替代事件、数据库约定、跨服务契约、测试或审核；发现范围外影响先报告，不自动夹带修复。

## 7. 已采用 ADR 的唤起

### 7.1 开工：先搜才知道是否命中

确认项目已采用后，在需求调查、从 issue 认领后或免方案期任务首次实施前，按业务词、表名、接口名、组件名和已知 ID 搜相关现行决定，读取命中记录及取代关系。不能等到已知命中才搜。

旧 spec 无字段、不新建 spec、用户说改一行直接干，都不免当前项目已采用约束。只搜本任务，不要求通读全部 ADR；不命中时留检索词与结论，不把没找到当作证明历史没有决定。

后补制度的项目不默认倒灌历史。实际触及旧决定时，核对现状、当前规格和可核用户来源；不从实现倒推用户已拍板。来源不明就保留不确定性，必要时确认业务边界，不伪造生效 ADR。

### 7.2 拍板后：记录已经明确的决定

用户已明确拍板且命中既有长期影响条件时，在继续相关设计或实现前新增或取代 ADR，不让用户提醒要不要写记录。

「不问要不要写 ADR」不禁止确认用户是否正式作出决定。倾向、先试试、先这样等表态无法确定承诺范围或是否定稿时，可用现有选择卡确认正式决定还是临时试用及其边界；不自行猜成长期生效。只有这种真实歧义才问，不每次加固定卡。

记录须有当场可核的来源、日期和用户原话或永久链接；模拟拍板只能用于假仓演练，不能变成真实业务决定。未拍板候选、局部命名、普通实现、事实和进度不因加强唤起全部变成 ADR。

沿用新增、双向取代、只链不抄和同一文档交付；没有新 spec 时，结果放当前 PR 或 issue，不为补字段重写历史。沿用约束与本次形成决定分开。

### 7.3 收尾与轻重边界

核本次引用是否现行、取代两端是否一致、新的已拍板长期决定是否真实落地。缺项按原修订和业务批准规则处理，不绕过修订卡、改旧 spec 卡或用户决策权。

新规格区分沿用与新增、取代或无及原因，复用项目已有语义字段；旧任务在当前载体补证据，不回写冻结正文。

这三个动作嵌入已有时点，拍板写入仍受长期影响条件限制，收尾只核本次涉及内容；不等于每任务新增三道固定 Gate、固定报告或检查脚本。实施须同步 ADR 细则 §六 的限定、§八 的重型升级项和 §九 误用说明，分清轻量日常动作与故障触发的重型固定检查，不能只补一处再让两种解释并存。

未采用的项目不加动作、字段、目录或推销；一次性写一条不升级制度。项目禁止为治理本身写 ADR 的，不借此越界。

### 7.4 现状、当前需求、现行决定与历史

- 现状文档及实测回答现在是什么。
- 当前获批 spec 与验收约束本次要改成什么，实施前必须读。
- 现行 ADR 约束跨任务决定；改变它须用户拍板及按取代规则处理。
- 历史规格才是追溯时按需读；不能把该默认读序套在当前施工规格，或用现状不同自行抹掉获批目标。

### 7.5 审核侧也按已采用约束核对

主 agent 始终负责准备相关已采用规则、现行 ADR 链接及本次处理证据。未选审核时自己对账，不据此增派 agent。

用户选择审核后，将这些证据给相应审核路线：规格符合性核当前需求与现行约束、两张清单及已有文档分工；实施对抗检查针对具体违反获批约束的行为；范围外对账仍只报越界，不扩成泛泛质量意见或逼实施方加防御层。

发现规格绕过现行 ADR，报告具体冲突和来源，不替用户裁业务、不自动修决定，也不新增档位。轻审规格阶段也适用，不必等用户选重审才核对。

### 9.3 最低客户端矩阵与通过判据
