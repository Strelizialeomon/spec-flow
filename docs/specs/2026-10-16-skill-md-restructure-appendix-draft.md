### 草案 · 〈各步要点〉

```markdown
## 各步要点

**第 2/3 步·两张清单**（方案期、spec 期都管）

- **机制清单**：每新增一个机制 / 概念 / 抽象（用户事后可能问「这是什么 / 哪来的」的都算）单列一条，一行写「解决什么 / 没有它会怎样」；随方案摆机制卡，不混在正文里让用户批量点头；spec 期写进 spec 文件。
- **自定细节**：spec 没写死、agent 自己定的细节（默认值、判定规则、命名、落点）逐条列在 spec 末尾「自定细节」节；用户扫一眼，不逐项问；该列不列 = 违规。
- spec 期审核核对两张清单都在、与正文对得上；清单外有机制 = 漏报。

**完成标准与长尾验收**（第 3 步出 spec、第 6 步写验收、第 9 步关单都管）

- **完成标准 = 有限承诺**：约定功能实现，相关正常 / 异常 / 边界 / 回归测试通过，无未处理的已知阻断缺陷，证据齐全。
- **观察式收尾默认不进单**、**例外须方案期批准**：判据与例外卡形状见 `references/done-criteria.md`（依据：rationale R18）。

**拆分大 spec 时**：总纲须有交付物地图和依赖台账，列定义见 `references/split-large-spec.md` 第 1~2 节。每份分别判断能否独立开始、独立合入、独立发布；「必须同批合入 / 发布」登记成依赖边不算止损，有环依赖、无 owner、甩不掉的才止损：退回单 spec + 多实施 issue，或先抽共同契约 / 基础 spec。审查并入现有规格符合性检查，不新增档位或派发路线（依据：rationale R15）。

**第 5 步·修订**：⛔ 改一条判据 / 定义 / 常量 / 术语，必须全文搜它的所有落点逐一同步——机制节、实现节、实施步骤、验收标准、跨文档引用、历史记录；只改那一句，照 spec 施工等于白改（依据：rationale R1）。动手前读 `references/spec-revision-sync.md`。

**第 6 步·开 issue**：spec PR 合并之后、实施之前开——spec 没定稿就开会两边互相引着改（依据：rationale R2）。正文只放 spec 永久链接 + 改动面 + 验收要点（checkbox 先不勾），不贴全文。

**第 9 步·回填**：spec 头部元信息（Issue 号、状态）随实施 PR 一起改，不单开 PR；PR 正文写「关联 issue：#N」，别用 `Closes` / `Fixes` / `Resolves`（自动关单会绕过回填；依据：rationale R22）；合并后勾掉 issue 里已满足的验收项、评论一句「代码已合」、关单、放锁。
```
