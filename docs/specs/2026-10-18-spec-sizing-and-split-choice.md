- 日期：2026-10-18

- 状态：实施中；规格期 PR #103（轻审 0 条发现），实施 PR #105
- 生效 ADR：本仓未声明采用 ADR，本次不新增采用机制

## 背景与已确认需求

用户要求：把大体量 spec 拆成中小体量的 spec 和配套 issue，尽可能让 agent 并行开发；并行不是硬门槛，允许必要的先后依赖。

用户报告的两类旧问题是“拆出来的两个 spec 互相依赖”和“拆出来的 spec 依然有很多阶段”。这是用户的使用反馈，不冒充本次重跑的实验结论。

当前仓内可核的缺口：

- `SKILL.md`〈拆分大 spec〉和 `references/split-large-spec.md`〈止损规则〉允许 agent 退回一份大 spec、只拆实施 issue。
- 备忘录〈悬而未决的〉仍把“拆 spec 还是只拆 issue”和体量判断留为未定；现行入口是在已经决定拆子 spec 后才读细则。
- 已有交付物地图、依赖台账与开始 / 合入 / 发布就绪判断，但没有开执行单前的结构选择，也没有检查子 spec 是否仍是多阶段大包。
- 子 spec 与 issue 尚无共用的稳定组名、子件编号和父子归组要求。

本次已确认：agent 在 spec 草案成形后判断体量，推荐拆或不拆并提供两种选项；多阶段必须提醒，最终由用户决定。识别方式选择“稳定编号 + 父子 issue”，随后机制卡选择“全要”。

## 互联网依据与边界

以下官方原文于 2026-10-18 实际读取，不把通用建议说成已有的 spec 标准。

| 结论 | 官方依据 |
|---|---|
| 小变更应自包含、聚焦一件事、带相关测试；可按完整功能切分，也可先用共享接口或 stub 解耦；没有通用的硬性行数上限 | [Google Engineering Practices：Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html) |
| 并行工作适合边界清楚的独立任务；同文件编辑和大量依赖会增加协调成本 | [Anthropic：Agent Teams 的适用场景与最佳实践](https://code.claude.com/docs/en/agent-teams) |
| 父子 issue 表达工作归属，并可在 GitHub 中查看子单进度 | [GitHub Docs：Adding sub-issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues) |
| blocked by / blocking 表达有方向的阻塞，区别于父子归属 | [GitHub Docs：Creating issue dependencies](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies) |

Google 讲的是代码变更，不是 spec；Anthropic 文档中的团队能力属于其客户端，不因引用而启用。“一份执行 spec 对应一张执行 issue”和开单前选择是本次工作流取舍，不是外部规范。

本机 `gh issue create --help` 实测没有官方网页所列的 `--parent`、`--blocked-by` 参数。实施关系操作时必须核对当时可用的 CLI 或官方 API，不能照网页假定本机已支持，也不为此擅自升级工具。

## 目标与不做

唯一交付目标：让 spec 的体量、实施单元和归组关系在开执行单前已经由用户选定，避免开单后才发现大包、多阶段或互相等待。

- 尽可能增加可并行的部分；真实的串行依赖如实保留，不以并行度不足拒绝拆分。
- 不强制所有 spec 都拆，不承诺所有子件能同时开始或独立发布。
- 不把一份 spec 限成一次会话、一次提交或一个 PR；普通编码、测试和提 PR 不是多个实施阶段。
- 不新增调度器、脚本、Hook、标签体系、选修机制或实施计划；不改锁名、完成标准、审核档位或历史 spec 正文。

## 机制清单

| 机制 | 解决什么 / 没有会怎样 |
|---|---|
| 开单前体量评估与拆分卡 | 把结构决定放在开单前；否则多阶段和大包仍进入执行单后才暴露 |
| 单交付粒度与子件再评估 | 一份执行 spec 聚焦一个可验收成果；否则只是把原大包换成几个仍有多阶段的包 |
| 依赖说明与拆法修正 | 尽可能解开互相等待，允许必要先后；否则会假并行或由 agent 自动退回只拆 issue |
| 稳定组名、子件编号与父子单 | 从文件和 issue 标题即可认出归属，父单汇总；否则同组关系仍靠猜标题或翻旧会话 |

## 规则设计

### 1. 何时评估与由谁决定

在既有第 3 步内，需求确认、spec 草案成形后，agent 结合实际改动面评估体量并摆拆分卡；在第 6 步开单前核对决定仍适用。结构未变不重复问。结构发生实质变化时重新评估，不能沿用已经过期的选择。

每次评估说明：交付目标与实施阶段、受影响范围、真实依赖、能否形成中小交付单元，以及推荐理由。不设仅凭行数、文件数、固定工时或会话长度触发的硬阈值。

“多阶段”指多个需要分别推进、验收或重新安排节奏的交付里程碑；没有写“阶段”字样但实际如此，也算。编码、测试、提 PR 的普通步骤，以及开始 / 合入 / 发布三项就绪判断，本身不算多阶段。出现多阶段必须提醒，通常推荐拆；若确实不可分，推荐不拆时要解释原因，不能静默跳过。

拆分卡同时提供“拆”和“不拆”，推荐项在前。拆分建议先列候选子件、各自成果、仍需保留的阶段与依赖、哪些可并行和哪些必须先后；不能只给一个没有拆法的空选项。

卡上说明实际产物数量与管理代价：拆成 N 份时为 1 份总纲、N 份执行 spec、N 张执行 issue 和 1 张仅跟踪的父 issue；不拆时为 1 份执行 spec 和 1 张执行 issue，并说明保留的阶段。不得把估计工期当作实测数字。

用户未选择时不定最终结构、不开执行单；不得默认拆或不拆。此卡不替代机制卡、改旧 spec 卡和审核档位卡。

### 2. 选择后交付什么

选拆：保留总纲作为总体目标、共享约定和交付物地图 / 依赖台账的入口；实施目标、边界和验收分别落在中小子 spec，每份执行 spec 配一张执行 issue。总纲不再重复承担所有子件的实施正文，也不再开一张重复执行全部范围的大单。

每份子 spec 默认聚焦一个完整可验收成果，保留相关实现与测试，不按文档章节或机械地按前后端拆。子件仍有多个实施里程碑时，继续提醒并让用户明确选择再拆或保留；可在同一轮结构选择中逐份说明，不为同一决定重复摆卡。

选不拆：保留一份 spec 和一张执行 issue，记录这是用户明确决定、仍保留哪些阶段及原因；不能自动改成一份大 spec 下的多张阶段执行单。用户选择不拆不豁免已知阻断问题、验收或必要依赖的说明。

本次结构覆盖的总纲和执行 spec 均定稿、按份过闸并合并后，才创建父 / 子 issue；所有执行单都锚对应 spec 的永久链接，正文保留改动面和未勾的验收要点，不复制 spec 全文。无需等待前置 issue 实施完成才创建后续 issue，实际开工仍按就绪条件。

### 3. 尽可能并行，但不把并行变成准入条件

沿用总纲交付物地图和有方向的依赖台账，分清契约、数据、配置 / 运行时和发布 / 验收，文件归属与“不碰”边界同样明确。

分别说明能否开始、合入和发布，不能将三项混成一个“可并行”。共同接口或测试替身已经明确时，消费者可并行开发；确有前置产物时允许先后实施。运行时互相调用不自动等于实施互相等待，须按具体就绪条件判断。

遇到 A 等 B、B 又等 A，或 owner、就绪条件不清时，先重划边界、确定唯一 owner，或抽清共同契约 / 基础 spec。基础 spec 也必须有具体产物和验收，不能成为另一份包罗全部前置工作的巨型 spec。无法给出可行拆法时报告卡点，由用户重选结构或调整范围，不自行退回“单 spec + 多实施 issue”。

保留明确的同批合入、共同发布和收尾份安排，不因此宣称各份独立合入 / 发布，也不把它们一概判为不可拆。每份自带本份测试和验收；跨份验收点名归某份，不能都甩给没有执行范围的父单。

### 4. 如何一眼识别与追踪

同一拆分组采用一个仓内唯一、稳定的组标识，子件编号如 S01、S02；编号是身份，不是波次，不因排期改变重编号，取消后不复用。项目已有命名体例优先，新增约定只补同组识别，不批量重命名旧文件。

总纲与子件头部写明组标识、角色、子件编号和总纲链接；既有地图的子 spec 栏承载标识与文件链接，开单后机械回填 issue 链接，不另建重复的进度台账。子件保留上游、下游与合入 / 发布前提声明，共享约定只指向唯一正文。

示例组标识为 `2026-10-18-order-export`：总纲标题 `[2026-10-18-order-export/总纲] 订单导出`，执行 spec 与 issue 同用 `[2026-10-18-order-export/S02] 下载结果`；父 issue 标为 `[2026-10-18-order-export/总览] 订单导出（仅跟踪）`。文件名含相同组标识与子件编号，目录结构沿用项目体例。

每组增加 1 张父 issue，仅链接总纲、归组子单与显示进度，不认领为执行任务、不额外开 worktree。父子关系表达“属于哪组”；真正需要另一单完成才能推进的关系才用 blocked by / blocking，不因同组或编号顺序就全部串起来。仅挡合入 / 发布、或只等上游部分产物的，仍以 spec 中的具体条件为准，不误标为必须等待整个上游单关闭。

平台权限或工具能力不足时，保留编号和双向链接并明确报告原生关系尚未建立，不宣称原生归组已完成，不自动安装或升级工具。父单不承载额外开发或观察任务，待各子单按既有完成标准完成、已分配的跨份验收满足后关闭，不改变子单生命周期。

### 5. 本次规格自身的体量判断

本次只有一个交付目标：调整开单前的规格结构决定。改动虽涉及主文件、细则、依据与双语说明，但它们共同定义同一条工作流，不是多个实施里程碑；本 spec 没有分阶段实施安排。

agent 推荐本次不拆：保留 1 份执行 spec、合并后开 1 张执行 issue，无需跟踪父单。可选拆法是把“体量选择与交付粒度”和“同组编号与父子关系”拆成 2 份执行 spec，另留 1 份总纲、开 2 张执行单和 1 张父单；但两份都改同一组入口与细则，会增加协调成本。用户本次已在结构卡选择不拆，按 1 份执行 spec、1 张执行 issue 交付；上述拆法仅保留为比较记录。

## 验收标准

- [ ] 草案成形后主动评估并给真实拆法、推荐理由和拆 / 不拆选择；决定缺失时不开执行单，结构实质变化后重新确认。
- [ ] 多阶段是必须提醒的信号，不是强制拆分；普通编码 / 测试 / PR 步骤与三项就绪不误判为多个实施阶段。
- [ ] 选拆得到中小执行 spec 与对应执行 issue，子件仍多阶段时再次提醒；选不拆保留用户决定，不自动变成多张阶段执行单。
- [ ] 尽可能并行不是准入条件；清楚的单向依赖和同批发布安排允许存在，循环等待、归属 / 前提不清要修拆法，不由 agent 自动回退只拆 issue。
- [ ] 总纲和子件边界、验收与依赖清楚，共享约定只有一个正文 owner，跨份验收有明确执行归属。
- [ ] 标识能贯通文件、spec 头部、总纲地图和 issue 标题；编号不随波次改变，父单仅跟踪，归属与阻塞不混用。
- [ ] 父 / 子执行单创建仍晚于本次结构定稿与相关 spec 合并，执行单锚永久链接；工具不支持原生关系时如实报告，不擅自升级。
- [ ] R28 与旧口径取代标记齐全，双语 README 同步；历史 spec 正文、锁命名、完成标准、审核档位及未采用机制不改。
- [ ] 实际变更通过 `bash scripts/check-docs.sh` 和 `git diff --check`，预算不上调；另逐项核对下列语义场景，区分文字自查与真实客户端行为证据。

| 场景 | 预期 |
|---|---|
| 小而自洽的 spec | 推荐不拆，同时提供选择；未答不开执行单 |
| 明写多阶段，或虽未命名但有多个交付里程碑 | 主动提醒并给候选拆法，不等用户指出 |
| 仅列编码、测试、PR，或开始 / 合入 / 发布状态 | 不仅凭这些名称推荐拆 |
| 用户明确保留多阶段；子件仍有多阶段 | 前者记录不拆决定；后者也提醒并由用户决定，不自动过关或强拆 |
| A 先产出、B 后消费；或接口定好后两份可并行 | 接受有序依赖，尽可能并行，不因无法全并行拒拆 |
| A 等 B、B 又等 A | 查具体产物并重划边界 / 抽契约，不自动保留大 spec 只拆 issue |
| 同组但无硬前置；只在发布时有关联 | 建归属、不假造全串行阻塞；如实保留发布条件 |
| 选择后范围实质变化；原生关系无权限或 CLI 不支持 | 前者重新评估、未定不新开单；后者保留标识与链接并报告缺口 |

## 自定细节

| 细节 | 理由 |
|---|---|
| 复用原有第 3/6 步，不另加编号步骤或实施计划 | 用户要的是开单前确定体制，不是再加一套调度流程 |
| 稳定组标识默认用日期 + 主题短名，子件用 S01 形式 | 文件和 issue 创建前即可确定，不依赖尚不存在的 issue 号；项目体例优先 |
| 一组可在一次结构选择中逐份表明保留的阶段 | 保留用户决定权，同时避免对同一决定反复提问 |
| 父 issue 仅跟踪，默认每份执行 spec 对应一张执行 issue | 不让总纲和父单成为另一份重复的大实施包；不强制一 spec 只能一个 PR |
| 本次实施只改六份现行文档，R28 沿用既有依据体例 | 完整记录调研和取舍，不新增采用名单、脚本或跨项目资产 |
