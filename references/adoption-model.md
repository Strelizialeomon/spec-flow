# 备忘录：spec-flow 的采纳模型（三层）

> ⚠️ **这是备忘录，不是规程，不是流程，不是必须遵循的东西。**
> 它只记录「spec-flow 怎么被一个项目采用」的设计与历次演进（2026-09-16 定稿、2026-09-22 演进），以及当时否掉了什么。
> 主文件 `SKILL.md` 不依赖本文件；没读它，两段流程照走。

## 三层模型（owner 2026-09-16 拍板）

- **严格遵循的项目**：同步一份 spec-flow 进项目 + 指向真身（`~/code/spec-flow`）→ 项目里照全套执行。**⚠️ 已被 2026-09-22 演进取代**——标准动作改为只指向式（见文末〈2026-09-22 演进〉）；本行只对存量副本仓仍适用。
- **不要的项目**：不同步、不指向 → spec-flow 天然管不着，无需登记。
- **偶尔用一次**：当场手动引用 → 那个任务走全套。

同步 + 指向 = 镜像，不是分叉：副本声明真身、可刷新。注意同步要真有刷新动作（手动再同步一次，或一行脚本），否则副本过段时间又变旧。

## 当时否掉了什么（来龙去脉）

- **「防撞走项目自己的规矩」**（2026-09-16 中午随 PR #1 废掉）：格式两处打架（`issue-<N>` vs `feat/issue-N`）出过一次事故，根因是规矩多源。
- **常设豁免名单**（同日下午随 PR #2 立、同日被 owner 否掉）：把 py-script、llm_auto_report 登记进 SKILL.md 的名单。owner 判语：「全局默认适用 + 登记不适用者」是默认设反了；一个全局 skill 点名具体仓本身就是怪味。名单整张删除，无替代物。
- **按仓分**（讨论中被否）：仓级「并行 / 单干」牌子写进各项目 CLAUDE.md。被否理由：把流程状态外包给项目。
- **跨机 push 认领、`claude --worktree` 禁令**（同日互联网调研提出，未采纳）：调研方向不是 owner 要的方面，未落地，仅在此留痕。

## 设计原则

**spec-flow 只写规则，不写「自己在哪适用」的行政档案。** 规则单源在中央仓，采纳动作（**只指向式** / 同步 + 指向 / 不引用 / 当场引用）发生在项目侧和用户手里，两边都不越界。

## 历史教训（为什么副本必须「同步 + 指向」）——**已被 2026-09-22 演进取代**

spec-flow 2026-09-16 建仓前活在三处静止副本里，零历史，追一条规矩的来历追到 2026-08-24 断档（见本仓 README「这个仓为什么存在」）。静止副本 = 分叉；同步 + 指向 = 镜像。差别就在「副本是否声明真身、是否有刷新动作」。

## 2026-09-22 演进：严格遵循层的标准动作改为「只指向式」

**「严格遵循的项目」层的标准动作，从「同步一份 + 指向真身」演进为「只指向式」**——由 `SKILL.md`〈应用到项目〉功能产出：目标项目里**只放指针块，不放任何流程副本、不做任何同步机制**。

**为什么改**：副本会静默过期，而「记得重拷」是纯人肉动作。2026-09-22 逐仓实测：neuron-entry 的副本停在 `2c329cd`（2026-09-21，当天即落后），xhs-analysis 停在更旧的 `98c2c43`（2026-09-16）。只指向式**压根没有第二份**，规则永远单源——它此前已在 5 个仓（taoxi-bd-workbench / taoxi_system / go_wechat_robot / finance-workspace / xhs-monitor）验证可行，零同步事故。

**存量副本仓（neuron-entry / xhs-analysis）维持现状、不追改**——owner 2026-09-22 拍板。它们继续走「同步 + 指向」（上面第 9、13 行与本节上方那段的说明**对它们仍然有效**），只是**不再往新仓复制这一形态**。

**三层模型的分类本身不变**——仍是「严格遵循 / 不要 / 偶尔用一次」三层，变的是第一层的标准动作。本文上方的旧表述保留原样、就地标了「已被取代」，是刻意留痕，不是第二份权威。

**与「不引用 / 当场引用」两层的区别没变**：只指向式仍是「严格遵循」层——项目里落了持久入口、照全套执行；只是那个入口指向真身，不再夹带一份副本。
