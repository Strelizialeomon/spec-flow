# 备忘录：把 ADR 作为项目的可选长期记忆

> ⚠️ **这是备忘录，不是六步流程，默认不启用。**
> 只有用户明确要求项目启用 ADR、明确要求本次写 ADR，或项目现有规则已声明采用时，才读取并执行。
> agent 不得根据「项目看起来很复杂」自行引入，也不主动追问用户是否启用。

ADR（Architecture Decision Record，这里指「跨任务长期决策记录」）保存的不是某次任务怎么施工，而是：
用户已经怎么拍板、为什么这么定、否决了什么，以及出现什么新事实时才允许重新讨论。

## 一、三种使用状态

| 状态 | 怎么判定 | agent 怎么做 |
|---|---|---|
| 未启用（默认） | 用户没提 ADR，项目规则也没声明 | 不创建 ADR，不加 ADR 步骤 / 字段 / 检查，不追问是否启用 |
| 本次一次性 | 项目尚未采用 ADR，且用户明确说「这次写一条 ADR」、不要求改项目流程 | 只写本次记录，从当前 spec 链过去；不偷偷把 ADR 升格成项目制度 |
| 项目级采用 | 用户明确说「这个项目启用 / 接入 ADR」，或项目规则已声明 | 首次启用时落下项目自己的持久入口；已启用时直接按项目规则执行 |

先判项目现有规则：已采用 ADR 的项目直接按项目规则执行，不会因用户说「这次写一条」就退回一次性模式；用户明确要求本次豁免或改变项目规则的除外。
尚未采用时，用户只要一条就不扩成制度；用户要项目级采用，就不能只在当前会话口头约定。

一次性 ADR 优先跟项目已有文档体例；没有体例且用户未指定时，可只新建 `docs/decisions/YYYY-MM-DD-<slug>.md`。
不同时新建规则页、模板、项目指令或检查脚本；单个 ADR 文件或 `docs/decisions/` 目录的存在不代表项目已采用 ADR 制度。

## 二、它与其他载体的分工

| 载体 | 回答什么 |
|---|---|
| facts / 实测记录 | 客观上现在是什么 |
| ADR | 用户长期决定了什么，为什么，何时才能重开 |
| spec | 某次需求在当时应当怎么实施 |
| issue | 现在要做什么、谁在做、怎么验收 |

ADR 不取代 spec，spec 也不承担「当前生效决策」的永久入口。载体之间只链接，不复制 ADR 正文。

## 三、项目级采用怎么落

先读项目的真实指令、文档结构、spec / issue 体例与并行方式，再提出接入设计。不把某个重型项目的整套 ADR 机制原样复制过来。

默认从最小版开始：

1. 在项目指令（如 `AGENTS.md`）留一个短入口：项目已启用 ADR、规则页在哪里。
2. 由项目自己选定唯一规则页和存放目录；无现有体例时，默认用 `docs/decisions/README.md` 与 `docs/decisions/`。
3. 一条决定一个文件，有稳定 ID、生效状态、适用范围和取代关系。
4. 新 spec 只链接生效 ADR，不抄正文；issue 默认仍按六步流程只链 spec，从 spec 一跳可达 ADR。
5. 从启用日期向后增量执行；默认不倒灌历史决定、不回写历史 spec。

最小版默认**不加** CI、生成器、中央编号器、消费者台账或全量历史迁移。真实出现漏查、单向取代、多 agent 并行冲突后，再按可复现问题增加检查脚本或固定 Gate。

### 默认命名

项目没有既定格式时，可用：

- 文件名：`YYYY-MM-DD-<slug>.md`
- 稳定 ID：`ADR-YYYYMMDD-<slug>`
- 状态：`生效中` / `已被取代`

不默认用连续数字编号：它需要额外分配中心，多 worktree 并行时还会抢号。

## 四、采用后，什么时候写

必须先满足：**用户已经明确拍板**。尚在讨论的方案只留在 spec / issue 草稿里，不写成生效 ADR。

拍板后命中任一条才写：

- 会影响另一个 issue、spec 或 worktree；
- 会改变对外接口、数据范围 / 结构、组件边界、安全、部署或长期运行约束；
- 明确否决了未来很可能再被提出的合理方案；
- 改变了已有 ADR。

以下不写：可实测的客观事实、局部实现、命名、普通重构、进度、临时排障、尚未拍板的候选方案。

一句话自检：

> 另一个任务的 agent 如果不知道这个裁决，会不会做出不同实现，而且很可能再让用户决策一次？

会，才需要 ADR。

## 五、最小记录格式

项目可按现有风格调整，但至少要能回答「定了什么、管哪里、为什么、付出什么代价、何时能重开」：

```md
# ADR-YYYYMMDD-<slug>：<一句话决定>

- 状态：生效中
- 日期：YYYY-MM-DD
- 决策人：用户
- 适用范围：<域 / 接口 / 机制>
- 取代：无
- 被取代：无
- 决策来源：<spec / issue / 当场可核出处>

## 决定

## 依据

## 否决了什么

## 接受的代价

## 允许重开的条件

## 关联
```

一条 ADR 只回答一个决策问题。「允许重开的条件」写新证据门槛，不写待办清单。

## 六、与六步流程怎么接

ADR 不增加第七步。最小版不让每个任务都跑一遍固定 Gate；只有项目已采用 ADR，且当前任务已引用、改变或形成第四节所述长期决定时，才按需执行下列动作：

| 当前任务情形 | ADR 动作 |
|---|---|
| 已知当前需求命中某类长期决定 | 按业务词、表名、接口名、组件名搜相关现行 ADR |
| 用户在本次拍板，且命中第四节的写入条件 | 在继续设计前新增 / 取代 ADR；走 spec-flow 时与 spec 放同一文档 PR |
| spec 受某条 ADR 约束 | 在 spec 里只列生效 ADR 链接；不复制决定正文 |
| 第 5 步改变旧 ADR | 走取代，并按旧 ID 反查仍在进行的消费者 |
| 第 6 步开 issue | 仍按主流程只链 spec，由 spec 一跳到 ADR；只有项目规则明确覆盖时才在 issue 直链 ADR |

用户明确只要一次性 ADR 时，只做本次有关的写入和 spec 链接，不改项目指令、spec / issue 模板或收尾规则。

## 七、决定变了怎么办

如果照旧 ADR 施工的人现在会做出不同实现，就要取代，不要静默改写旧决定：

1. 新建 ADR，状态为「生效中」，「取代」链接旧 ADR。
2. 旧 ADR 只把状态改为「已被取代」，「被取代」链接新 ADR；决定、依据、代价和重开条件正文不改。
3. 两端放在同一变更中，避免只改一边。
4. 历史 spec / 已完成 issue 不回写；开放任务按新决定停止、更新或重开。

不在 ADR 里手工维护「受影响对象清单」。消费者主动引用稳定 ID，需要时用 `rg` 与项目已有平台 CLI 反查真实引用。

## 八、什么时候才升级成重型机制

只在项目真实出现下列问题时升级，不为「以后可能需要」预装：

- 多个 agent / issue 反复让用户决策同一问题；
- 决定变更后经常找不全消费者；
- 新旧 ADR 状态或取代链接多次写错；
- 多客户端的项目指令存在漂移，导致有的 agent 读得到 ADR 规则、有的读不到。

可按故障逐项增加：对每个任务固定执行的开工 / 拍板 / 收尾三时点 Gate，spec / issue 固定元数据，ADR 结构与取代关系检查脚本，以及跨仓库与平台的固定消费者反查。

## 九、常见误用

- **自动启用**：「这项目很复杂」不是授权；没有用户或项目明确采用就不启用。
- **启用前反复推销**：用户没提 ADR 时，不在每个复杂任务上追问一遍。
- **一次请求偷换成永久制度**：用户说「这次写一条」就不改项目流程。
- **口头启用但不落入口**：项目级采用如果只存在当前会话，下个 agent 就会丢失。
- **所有选择都写 ADR**：局部实现和临时排障会淹没真正的长期裁决。
- **默认抄重型项目全套**：模板、三时点 Gate、反查和检查脚本是升级项，不是小项目的起步价。
