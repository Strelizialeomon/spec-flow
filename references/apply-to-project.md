# 细则：把 spec-flow 应用到项目

> 本文件是 `SKILL.md`〈应用到项目〉一节的展开——**模板全文在这里，`SKILL.md` 只留触发、五步骨架与指向**。
> 用户说「把 spec-flow 应用到（本）项目」（可带附加描述，如「同时启用 ADR」）时读它并照做。
> **它不是两段流程的一步**，没被要求就别对当前仓自作主张应用。
> **§十 是所有修饰词共用的采用契约**（两种运行模式、通用处理顺序、登记表）——改任何修饰词前先读它。

## 一、目标文件判定树

**先做前置检测**（这一步没做完别往下写）：

| 检查 | 命中怎么办 |
|---|---|
| `AGENTS.md` / `CLAUDE.md` 是不是**符号链接**（`ls -l` / `readlink`） | 指向**仓内**另一份指令文件 → **只写被指向的那一份**，别两份都写（否则软链自指、或造出第二份正文）；指向**仓外**文件（如跨仓共用的 `~/.agents/AGENTS.md`）→ **停手报告用户，别写**——写了会污染所有共用那份文件的仓 |
| 目标文件末行有没有换行（`tail -c1`） | 没有 → 追加前先补一个换行，且追加内容**前面留一个空行**。否则模板首行标题会被吞进上一行，`grep '^## '` 都找不到它 |

然后按现状决定写哪些文件：

| 现状 | 动作 |
|---|---|
| 无 `AGENTS.md`、无 `CLAUDE.md` | 新建 `AGENTS.md` 写指针块（§二）。**不新建 `CLAUDE.md`** |
| 无 `AGENTS.md`、有 `CLAUDE.md` | 新建 `AGENTS.md`（指针块）+ 在 `CLAUDE.md` 补一行 `@AGENTS.md`（§三） |
| 有 `AGENTS.md`、无 `CLAUDE.md` | 往现有 `AGENTS.md` 加指针节。不动 `CLAUDE.md` |
| 有 `AGENTS.md`、有 `CLAUDE.md` | 往 `AGENTS.md` 加指针节 + 确认 `CLAUDE.md` 有 `@AGENTS.md` 一行（没有才补） |

**为什么指针本体只写 `AGENTS.md`**：双工具公用仓里它是唯一两家都读的单源文件——kimi 原生读它；Claude Code 2.1.277+ 在项目**没有** `CLAUDE.md` 时也原生读它。写进 `AGENTS.md` = 一份正文两家吃；写进 `CLAUDE.md` = kimi 读不到，还得再抄一份给 `AGENTS.md`，就是分叉。

**写入位置**：追加到文件末尾为主；文件已有明显的分节结构时，就近并进同类节也可以——**但别改写既有正文**。

**幂等规则**（重复应用 / 应用过的仓再应用时）：

- `AGENTS.md` 已有指针节 → **不重复追加**；改为校验它是当前形制（对照 §二），形制过期才就地更新那一节。
  ⚠️ **判定口径是「合取」，不是「任一」**：必须**同时**命中「spec-flow 这个名字」**和**「唯一真相源 / 本文件不复述 / 不放副本」里至少一句。
  只看后一组不行——「唯一真相源」在别的仓有别的用法（用户自己的 `~/.agents/AGENTS.md` 就拿它指自己），单看它会把与 spec-flow 无关的仓判成「已应用」，**结果是用户要的指针永远写不进去**。
- `CLAUDE.md` 已有 `@AGENTS.md` 行 → 不重复追加。
  ⚠️ **判定口径是「生效形态」**：必须**单独一行、不在反引号或代码块里**——用 `^@AGENTS.md$` 这类锚定匹配，**别用字面 `grep '@AGENTS.md'`**。
  被包在反引号 / 代码块里的写法**判为「不存在」、照样补一行**：§三 说得很清楚，包了就静默不导入、不报错不提示——校验侧不防这个，坑会从校验侧原样漏回来。
- 附加描述已生效过（如 ADR 入口节、文档读序节已存在）→ 同样只校验、不重复；ADR 那一侧**先过 §四 的前置判断**，别漏了「项目自带规则页在别处」的情形。

## 二、指针块模板

照抄，按目标项目实际情况替换方括号内容：

```markdown
## 流程规矩：来自 spec-flow

**本仓的复杂活走 spec-flow 的两段流程。**
规则的**唯一真相源**是 spec-flow，**本文件不复述它的步骤**——要看细则就去读真身。

| 项 | 值 |
|---|---|
| 远端真身 | `https://github.com/Strelizialeomon/spec-flow`（`SKILL.md` + `references/`） |
| 本机 skill | `~/.claude/skills/spec-flow`（指向真身的符号链接） |
| 怎么用 | 开工前调 skill `spec-flow`；**认领 issue 做实施也算开工**（从段二进）；**没装 skill 的机器**直接在会话里读上面那个远端的 `SKILL.md` |

### ⚠️ 本仓不放副本、不做任何同步机制

spec-flow 的 `references/adoption-model.md` 记了四种采纳动作：**只指向式**（2026-09-22 起新仓默认）、同步 + 指向（存量副本仓）、不引用、当场引用。
本仓选**只指向式——只指向、不复制**。

理由（也是 spec-flow 自己的历史教训）：**静止副本 = 分叉，会变旧**——它建仓之前活在三处静止副本里、零历史，
追一条规矩的来历追到 2026-08-24 就断档了。本仓不复制，**压根不存在第二份**。

**要改流程规矩 → 去改真身并提交**，本仓自动跟着变，**不用改本文件**。
反过来，哪天发现两处对不上，那就是有人绕过了 git——**别在这边就地修正**。
```

**「本机 skill」一格按应用时本机实际填**（上表填的是默认路径）。目标机器还没装 skill 时，这一格照留——它是给**将来装了**的机器看的，「怎么用」那格已写明没装时怎么读。

## 三、`CLAUDE.md` 导入行

项目已有 `CLAUDE.md` 时，在文件里补**单独一行**：

```markdown
@AGENTS.md
```

⚠️ **这一行不能包进反引号或代码块**——包了就**静默不导入**：不报错、不提示，`AGENTS.md` 整个读不到。这条是 neuron-entry / xhs-analysis 踩过的坑。

补的时候顺手在该文件顶部或这一行附近写一句「根目录 `AGENTS.md` 已用 `@` 导入，两边不用各读一遍」——下一个人看见才知道这条 `@` 是干什么的。

## 四、ADR 入口节模板（附加描述含 `adr` 时写入 `AGENTS.md`）

**写之前先做前置判断**——备忘录 §三 要求「先读项目的真实指令、文档结构…再提出接入设计」「**由项目自己选定**唯一规则页和存放目录」：

| 项目现状 | 动作 |
|---|---|
| 还没启用 ADR | 走 §五 建 `docs/decisions/README.md`，入口节的规则页指向它 |
| **已自带 ADR 制度**（任何路径下已有规则页，如 `docs/adr/README.md`） | **不新建 `docs/decisions/`、不造第二份规则页**——入口节指向**项目自己那份**；路径、命名、状态口径一律随项目，别把本模板的默认值套上去 |

漏掉第二种情形 = 同一制度两份规则页，又是双源。（既有的「ADR 入口节已存在就不重复」幂等条**挡不住**它——自带制度的仓根本没有 spec-flow 形制的入口节。）

入口节落在 `AGENTS.md`，不是 `CLAUDE.md`——两家工具每会话自动注入它，**不靠 agent 自觉去读**。三条动作写成**指令**，不是干声明：

```markdown
## 已启用：决策记录（ADR）

本仓**已启用 ADR**（【应用日期】用户拍板）。

- **规则页（唯一）：`【规则页路径——新建时默认 docs/decisions/README.md；项目自带制度时填它自己那份】`**——什么时候写、命名与状态、取代流程全在那一页，**本文件不复述**。
  已落 ADR 的决策的唯一入口是**规则页所在的那个目录**：一条决定一个文件，ID 形如 `ADR-YYYYMMDD-<slug>`。
- **开工前先搜一遍**：按业务词、表名、接口名、组件名搜**那个目录**里状态为 `生效中` 的 ADR——
  **不搜就可能推翻一条已有裁决**。
- **拍板命中写入条件时，继续设计前就写**：新增 / 取代 ADR，并与 spec 放**同一个文档 PR**。
  生效 ADR 的唯一来源是**用户已拍板**，agent 不得自行把某条定为「已决」。
- **spec 只列生效 ADR 链接、不复制正文**；同一条决策上 ADR 与 spec 正文不一致时，**以 ADR 为准**。
```

## 五、`docs/decisions/README.md` 规则页骨架（附加描述含 `adr`、且**项目还没自带 ADR 制度**时创建）

连同 `docs/decisions/` 目录一起建；**项目已自带规则页就别建**（§四 的前置判断）。

**按 ADR 备忘录§三的最小版四条**——只留「启用声明 + 载体分工一句话 + 命名默认 + 其余全链备忘录」。
⚠️ **别把备忘录的规则正文抄进来**（什么时候写的那几条、取代流程的那几步）：抄了就是每个应用仓各存一份**不会跟着真身更新的残缺第二正文**——那正是这套流程要消灭的分叉，也是 D7 专门禁的。

```markdown
# 决策记录（ADR）· 规则页

> 本仓**已启用 ADR**（【应用日期】用户拍板）。本页是本制度的**唯一规则页**；
> `docs/decisions/` 下的一条条 ADR 是已落 ADR 的决策的唯一入口。
>
> **完整口径不在本页复述**——什么时候写、唯一来源、取代流程、升级到重型机制的条件，
> 见 [ADR 备忘录](https://github.com/Strelizialeomon/spec-flow/blob/main/references/adr-decision-records.md)。本页只留本仓落点。

## 载体分工

| 载体 | 回答什么 |
|---|---|
| `docs/specs/` | 某次需求在当时应当怎么实施 |
| issue | 现在要做什么、谁在做、怎么验收 |
| **`docs/decisions/`（本目录）** | **长期决策定了什么、为什么、何时才能重开** |
| 代码 / 实测记录 | 客观上现在是什么 |

**ADR 不取代 spec；同一条决策上 ADR 与 spec 正文不一致时，以 ADR 为准。**

## 本仓落点

- 一条决定一个文件，放本目录；文件名 `YYYY-MM-DD-<slug>.md`，稳定 ID `ADR-YYYYMMDD-<slug>`，状态 `生效中` / `已被取代`。
  **不默认用连续数字编号**——那要多一个分配中心，多 worktree 并行时还会抢号。
- **什么时候写、唯一来源、取代流程、升级到重型机制的条件：见上面链的 ADR 备忘录**——本页不复述。
  （刻意如此：细则双源 = 重演副本烂账，那正是这套流程当年踩过的坑。）
```

（`docs/decisions/README.md` 本身就是一份 markdown，**不**算指令文件，不需要往 `AGENTS.md` 里 `@` 导入它。）

## 六、附加描述处理规则

用户那句话里除「把 spec-flow 应用到本项目」之外的部分，就是附加描述：

| 描述 | 处置 |
|---|---|
| 空 | 只应用流程指针（§一~§三） |
| `adr` / 「同时启用 ADR」「加上 adr」等**说法变体** | **按语义判定**，不按字面匹配；执行 §四 + §五 |
| `doc-lifecycle` / 「同时采用文档生命周期备忘录」等**说法变体** | **按语义判定**，不按字面匹配；执行 §八 |
| `issue-status` / 「同时启用 issue 状态标签」等**说法变体** | **按语义判定**，不按字面匹配；执行 §九 |
| 不认识的描述 | **当场问用户**，不猜、不自行解释成一个已注册修饰词 |

**已注册修饰词清单**：当前 `adr`、`doc-lifecycle`、`issue-status`，字段与落点见 §十 登记表。新增修饰词 = 改 §十 登记表 + `SKILL.md` 参考表对应行，两处同改（`scripts/check-docs.sh` 核对两处一一对应）。

## 七、旧副本 / 旧流程段检测口径

应用前扫一遍目标项目，命中任一条就是要报告的「旧物」：

| 旧物 | 判定口径 |
|---|---|
| 逐字 / 整段摘抄副本 | 项目里有文件（通常是 `docs/spec-flow.md` 或同名同类）**命中真身的特征句**——**命中任一条**即判为副本。特征句是**分散在真身全文各处**的一组标志句（分散是为了让「只抄中间一段」的摘抄也撞得上；其中 `# 复杂活的六步流程` 是**旧版 H1**、现行真身里已无此句——刻意留着当**停在旧版的副本**的抓手，别当残留删掉），当前 12 条：`^name: spec-flow$`、`# 复杂活的六步流程`、`# 复杂活的两段流程`、`按顺序走，**别跳步`、`摆卡时**必须把账算给用户看**`、`改一条「判据 / 定义 / 常量 / 术语」时`、`**命名 = 锁**：分支和 worktree 目录同名`、`**「变异」不是 subagent**`、`**主线**：需求 → spec → issue → 实施`、`档位是**每一份**的强度`、`拿不准算不算豁免，不自判`、`**第 5 步·修订**：⛔ 改一条判据 / 定义 / 常量 / 术语`。其中 `按顺序走，**别跳步`、`摆卡时**必须把账算给用户看**`、`**「变异」不是 subagent**` 三句 2026-10-04 主文件重构后只在旧版真身里，`改一条「判据 / 定义 / 常量 / 术语」时`、`**命名 = 锁**：分支和 worktree 目录同名` 两句重构后只在参考文件里——与旧版 H1 一样，刻意留着抓停在旧版的副本 |
| 复述流程的指令段落 | 指令文件（`AGENTS.md` / `CLAUDE.md`）里已有**复述流程正文**的段落——列出步骤、写了审核档位表、或大段照抄流程细则。⚠️ **只提 spec-flow 名字、说「本仓走两段流程」（存量旧块写「六步流程」同理）的指针句不算**——那是 §二 自己的产物，算进去会每次重应用都把自己报成旧物 |

⚠️ **别用「相似度阈值」判副本**（行数比例、diff 相似度那类）。2026-09-22 实测：真·过期副本（停在 `2c329cd`）与当前真身**行数差 28%**——按阈值会被判成「不像」，**漏掉的恰好是这套功能要抓的那个案例**。特征句口径不看长度：过期多久都命中，摘抄只要长到覆盖住其中任一句也会被抓。

⚠️ **口径的边界（标签不许比口径承诺得多）**：只抄零星一两句、或只搬一张表而不带周围正文的碎片，**不算副本**——那也不构成第二份「真相源」。所以第一行标签是「整段摘抄」，不是「任何摘抄」。

⚠️ **指针块不会被自己误报**：§二 的指针块 12 条特征句一条都不含，也只在「提 spec-flow 名字」那一档、够不上「复述正文」。实测：5 份已应用指针的样本，两行口径全零命中。

**处置一律是「报告 + 用户定夺」**：

- 把命中的文件 / 段落**列出来**，说明「副本会静默过期」（附它停在哪、落后多少也可），给出建议——但**不自动删除、不改写**。
- 用户说要清才清。**默认维持现状**：存量副本仓按 owner 2026-09-22 拍板不追改（见 `references/adoption-model.md`〈2026-09-22 演进〉）。
- 误报的代价只是多问一句，**漏报的代价是两个「真相源」并存**——宁可多报。

## 八、文档读序节模板（附加描述含 `doc-lifecycle` 时写入 `AGENTS.md`）

[文档生命周期备忘录](documentation-lifecycle.md) §三 要求采用时在项目指令留「**一条指针 + 一行现状文档落点与默认读序**」；本节就是那一行的落点。**没被要求就别写**——该备忘录默认不启用。

**写之前先确认两件事**——现状文档在哪、有没有文档规则页：

- **现状文档**：项目已有一份就填它的路径；没有的，先问用户要建在哪，**别替它挑**。
- **文档规则页**：项目已有的（自带制度那份，或 §五 建的 `docs/decisions/README.md`）→ 落点与 owner 一律随项目，别套本模板的默认值；**没有的** → 把各载体落点就地写进**下面模板里那一节**，**别为此新建一份文件**（备忘录 §三 只要求写清落点，没要求多一份文档）。
  - 同一项目还启用了 ADR（§四 / §五）时：往那份规则页的载体分工表补**一行**——**载体**列填「现状文档（唯一正文）：`【路径】`」，**回答什么**列填「系统现在是什么、现在怎么操作」；那张表默认只有 spec / issue / ADR / 代码·实测四行，且**没有 owner 列**，owner 写在条目里或表下的注里。（备忘录 §一 列的「issue / PR」，在表里对应 issue 行与「代码 / 实测记录」行。）

```markdown
## 已采用：文档生命周期备忘录

本仓**已采用** spec-flow 的[文档生命周期备忘录](https://github.com/Strelizialeomon/spec-flow/blob/main/references/documentation-lifecycle.md)（【应用日期】用户拍板）。**规则正文不在本文件复述**——要细则去读那一份。

- **现状文档（唯一正文）：`【路径】`**——系统现在是什么、现在怎么操作看它；各载体（现状文档 / spec / ADR / issue / PR）的实际位置与 owner 见【文档规则页路径；没有单独规则页时就地写在本节】。
- **默认读序**：执行型 agent 只读现状文档和生效中的 ADR（若启用）；spec、调研、事故复盘只在追溯「为什么、当时怎么定的」时才读。
- **spec / 调研 / 事故复盘与现状文档冲突时，以现状文档与实测为准**；读现状文档先看它头部的最后核对时间。
```

⚠️ **只写这几行，别把备忘录的 §一~§四 抄进来**：抄了就是每个采用仓各存一份不会跟着真身更新的残缺第二正文——那正是这套流程要消灭的分叉（同 §五 对 ADR 规则页的禁令）。上面那行读序是备忘录 §四 点名要进指令入口的，**其余一律链接**。

**幂等**：`AGENTS.md` 已有文档读序节 → 只校验形制（对照本节模板），过期才就地更新，不重复追加。

## 九、issue 状态标签（附加描述含 `issue-status` 时）

[issue 状态标签备忘录](issue-status-labels.md) 默认不启用；本节是它的采纳动作。**没被要求就别做**。用户说「应用 `issue-status`」即授权**新建**下面 7 个标签；改、删已有标签，或给已有 issue 挂标签，都不在这次授权内，要另问。

**1. 先查既有标签**：`gh label list --limit 200`。

- 同名标签已存在 → **不覆盖**颜色和描述，只在报告里列出差异。
- 语义重叠的旧状态标签（如「待收尾」「in progress」「blocked」）→ 列出来报告给用户，**不删、不改、不迁**；老单要迁移另开 issue，迁移清单先给用户过目。
- 「待验证」已存在、且描述正是本 skill 的旧文本 `阶段：已上线，剩只能在正式环境由我方验的项；正文首行写下次看`（2026-10-15 前建的）→ 报告，并给出对齐命令 `gh label edit "待验证" --description "阶段：已上线，剩现在能由我方主动去正式环境验的项，或方案期批准的长尾项；正文首行写下次看"`；改已有标签要用户另行点头。描述是别的文本（项目自己写的，照上面第 1 条只报告差异）→ 不归本条。
- 旧名「待验收」已存在（2026-10-06 前采用的项目）→ 报告，并给出改名命令 `gh label edit "待验收" --name "待验证" --description "阶段：已上线，剩现在能由我方主动去正式环境验的项，或方案期批准的长尾项；正文首行写下次看"`（改名会保留已挂的单）；改名属于改已有标签，要用户另行点头。改名后，原挂「待验收」且还开着的单要按备忘录〈上线时分拣〉重分（等观察期、等外部方的多半转出关单），重分清单先给用户过目再改，同备忘录 §六 迁老单的口径。

**2. 建 7 个标签**（同名已存在的跳过；旧名「待验收」已存在时「待验证」也跳过，由第 1 步的改名代替——先建了新的，改名会因重名失败）：

```bash
gh label create "未开始" --color EDEDED --description "阶段：开了单还没动手（含挂账、待复现、待评估）"
gh label create "进行中" --color 1D76DB --description "阶段：已动手，改动还没合进主干"
gh label create "待测试" --color 5319E7 --description "阶段：已合进主干，等在测试环境验"
gh label create "待上线" --color 0E8A16 --description "阶段：测试已过（或不需要），等发到生产"
gh label create "待验证" --color C2E0C6 --description "阶段：已上线，剩现在能由我方主动去正式环境验的项，或方案期批准的长尾项；正文首行写下次看"
gh label create "等拍板" --color D93F0B --description "卡点：等 owner 做决定，拍完摘掉"
gh label create "受阻"   --color B60205 --description "卡点：等外部条件；正文首行写下次看"
```

**3. 问一句测试环境**：项目有没有测试环境，从项目指令和文档判不出来的就问用户，不猜。

**4. 往 `AGENTS.md` 写指针节**（符号链接、末行换行等前置检测与写入位置，同 §一）：

```markdown
## 已采用：issue 状态标签

本仓**已采用** spec-flow 的[issue 状态标签备忘录](https://github.com/Strelizialeomon/spec-flow/blob/main/references/issue-status-labels.md)（【应用日期】用户拍板）。**规则正文不在本文件复述**——标签定义、换标签时点、「下次看」行、盘点都去读那一份。

- 本仓【有 / 没有】测试环境【没有时加：不用「待测试」，合并后直接进「待上线」】。
- 实施 PR 合并后先换阶段标签；上线后按备忘录〈上线时分拣〉走；**哪些验收项能进单、长尾例外怎么批，照 `SKILL.md`〈完成标准与长尾验收〉**。
```

只写这几行，别把备忘录正文抄进来（理由同 §八）。项目要改盘点的停滞阈值（默认 14 天）等细节，就在这一节加一行。

**5. 幂等**：7 个标签已全在（旧名「待验收」在，算「待验证」在）→ 跳过第 2 步；`AGENTS.md` 已有该节 → 只校验形制（对照上面模板），过期才就地更新，不重复追加。

结尾照惯例报告：建了哪些标签、跳过了哪些（同名已存在及差异）、发现了哪些语义重叠的旧标签。

## 十、采用契约（所有修饰词共用）

**中央登记在 `SKILL.md`〈项目体例与参考〉参考表；采用动作、登记表在这里。** 改任何修饰词前先读本节——两份合起来才是完整注册契约，只改一处就是注册漂移。

### 两种运行模式

| 模式 | 触发 | 持久化 | agent 行为 |
|---|---|---|---|
| 本次按需读取 | 用户明确要求「本次读 / 按这份备忘录做」 | 不写项目规则 | 只在当前任务读取并执行，任务结束不改变项目制度 |
| 项目级持久采用 | 用户明确要求项目启用，或项目指令已声明采用 | 写项目指令入口和本仓落点 | 后续相关任务自动按该备忘录执行，不再重复问是否启用 |

备忘录没有项目级采用动作时，必须在中央登记里写明「**仅本次按需**」这个标记短语（`scripts/check-docs.sh` 认的就是它，别写成别的说法），不能让 agent 以为放进 `references/` 就自动生效。

### 项目持久入口的最低要求

项目级采用写进项目自己的指令入口（`AGENTS.md`，判定与写入位置同 §一），最低包含六项：

1. 已采用哪个备忘录；
2. 规则正文唯一链接；
3. 项目本地落点；
4. 后续任务必须做的动作（写成指令，不是「这里有一份文档」的说明）；
5. 本仓差异或验收命令；
6. 「不复制正文、不建第二份真相源」的边界。

§四／§八／§九 的三份入口模板就是这三个修饰词各自的那一份，按项目实际情况替换方括号；别另造形状。

### 通用处理顺序（所有修饰词同序）

1. 检测项目当前是否已有该制度、规则页和入口；
2. 判断项目采用目标文件和项目自有落点；
3. 先列本次会新增 / 修改的文件和远端资产，逐项过〈默认项目资产边界〉——可执行资产不得进默认清单；
4. 写项目指令里的短入口；
5. 需要时新建项目规则页或项目资产；
6. 输出采用结果、跳过项、发现的旧物和后续验收；
7. 保证重复执行幂等。

不认识的修饰词**当场问用户**，不猜成已有备忘录，不写入口、不创建资产。

### 默认项目资产边界

采用动作的默认交付物只有两类：**文档入口**（项目指令的指针节、项目规则页、目录与本仓差异）和**〈修饰词登记表〉里该词条「项目资产」字段写明的资产**。字段里没写的，一律不在默认集合。

脚本、CI、Hook、Workflow、生成器、机器人（下称**可执行资产**）不因一份备忘录被采用就自动创建——即便备忘录正文提到它们。项目原有的脚本可以按项目现有规则读取 / 运行，但采用动作不新增、不改写、不扩展其扫描面；报告里要列出跳过的可执行资产，别让用户以为它们已经装上了。

### 可执行资产升级闸

某词条的采用确实无法只靠 Markdown / 模板 / 收尾报告完成时，**停在「材料备好」**，先给用户这份短说明：

```text
需要新增可执行资产：<路径 / 类型>
解决的问题：<不加它会漏什么>
触发方式：<何时运行 / 谁运行>
维护成本：<项目新增什么长期负担>
Markdown-only 替代方案：<能否接受；代价是什么>
```

只有用户明确同意才创建，授权只覆盖本次列出的路径与用途，不扩展为长期任意脚本写入权；收尾报告列出获准路径与维护成本。用户不同意时：回落 Markdown-only、在项目入口写明哪些部分人工执行、报告里写明「未加脚本，因此没有机械拦截」——不把「脚本没加」伪报成「检查已通过」。

### 备忘录正文开头的最低元数据

每个选修备忘录正文开头写统一的「采用口径」区块，字段按实际情况填，只说明采用与触发、**不复制主体规则**：

```md
## 采用口径

- 默认：选修，不因项目复杂自动启用
- 本次按需读取：用户明确要求本次按本备忘录执行时读取
- 项目级采用：通过 `apply-to-project` 的 `<modifier>`，或项目指令明确声明已采用时生效
- 项目入口：采用后由 `apply-to-project` 写入项目指令的指针节
- 执行时点：<开工 / 拍板 / 实施 / 收尾中实际适用的时点>
- 验收：<机械检查、dogfood 或「不适用」的理由>
```

`<modifier>` 是稳定的 ASCII 标识；**同一备忘录只能有一个注册修饰词**。

### 执行时点契约

每个项目级备忘录至少声明一个真实执行时点，否则采用后仍可能没人读：开工前读取（已有规则会影响当前任务）／用户拍板后读取或写入（本次决定会产生长期规则）／出 spec 时读取／实施期读取／收尾读取（验收、回填、关单或状态变更受它影响）。

**不是把所有备忘录都塞进两段流程**：只声明该备忘录实际需要的时点；没有固定时点的可以只支持本次按需读取，并在中央登记里标明。

### 验收契约

每个项目级备忘录至少提供一种可复跑验收，三选一：

- **机械检查**：能明确断言入口、字段、结构或状态；
- **dogfood**：用一条真实任务验证 agent 会读取并执行；
- **明确不适用**：写出为什么无法机械验证、项目收尾如何报告。

验收只证明「采用后的载体和动作存在」，不冒充能理解用户自然语言；语义是否命中仍由 agent 按备忘录规则判断。

**dogfood 的跑法与产物**：一律在**临时假仓**里跑，不碰任何真实采用项目（对真实项目只做只读核对）；产物是实施 PR 正文里的场景记录，形状 = 场景 / 输入 / 实际动作 / 证据（命令 + 输出摘要）/ 结论。

### 新备忘录怎么进来

新备忘录只写进 `references/` 不算可用机制。要生效，按它是否有项目级采用动作二选一：

- **有项目级采用**：给它一个稳定修饰词，写进本节登记表（八项字段齐全）+ `SKILL.md` 参考表对应行；采用动作照 §十 通用顺序实现。
- **只支持本次按需**：在 `SKILL.md` 参考表那行写明「仅本次按需」，不要求修饰词；agent 不得据此自动启用。

三种既有备忘录的「采用口径」区块与本节登记表是同一份契约的两面：区块给 agent 读（这个备忘录什么时候读），登记表给采用动作读（这个修饰词落地时要写什么）。
