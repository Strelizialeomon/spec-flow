# 备忘录：让文档、spec 和 ADR 各管一件事

> 这是可选备忘录，不改变 spec-flow 两段流程。只有用户明确要求采用，或项目规则已经声明采用，才按它执行；不因项目文档多就自动启用。项目自己决定目录、模板和检查方式，本仓不维护采用项目名单。

## 一、先分清四种记录

| 载体 | 回答的问题 | 什么时候更新 |
|---|---|---|
| 现状文档（含运维说明） | 系统现在是什么、现在怎么操作 | 事实或操作发生变化时，改唯一 owner；其他地方只链接 |
| spec | 这一次批准了什么需求、准备怎样验收 | 批准前可评审和修订；基线形成后保留当时约定 |
| ADR（项目已启用时） | 用户作了什么跨任务、长期有效的决定，为什么 | 决定改变时新增 ADR 取代旧 ADR，不静默改正文；细则见 [ADR 备忘录](adr-decision-records.md) |
| issue / PR | 这次实施做到哪了、改了什么、验证证据在哪 | 随实施持续更新 |

调研和事故复盘记录证据与经过，不自动成为现状依据。一个事实或决定只设一个正文 owner；其余地方放链接和必要的一句话上下文，不复制整段内容。

spec、调研、事故复盘定稿后都是**历史记录**：在头部用一行写明它是哪天的快照、现状看哪里，例如「历史快照（2026-09-20）：现状见 X」；被取代时，新旧两份互相链接。项目已有归档或状态标头体例的，沿用原体例，只要这一行的信息齐全。有了这一行，就不再为了和现状一致去改历史记录的正文。

## 二、spec 的冻结点

spec 是**获批需求的快照**，不是跟着代码持续更新的活文档。草稿和评审阶段可以修订；**spec 的文档 PR 合并、实施 issue 建立后**，该版本成为基线。此后不把实施进度、上线现状、排障日志或后来提出的新需求写进它的正文。正文与当前系统不同时，先判断是“当时就写错”还是“后来发生变化”，不要为了表面一致直接改历史。

基线后的处理：

- 实施中的小修正，若**不改变获批范围与验收含义**，在 issue / PR 记下修正、原因、验证和 spec 链接；只有旧 spec 当时的文字或事实确实写错、会误导读者时，才在其头部加带日期的勘误链接，不重写原约定。
- 新增、取消、改变获批范围或验收含义：暂停受影响的实施，另起后续 spec，写明与原 spec 的关系，重新取得批准；获批后按项目既有 issue 规则更新或另开实施 issue，并指向新基线。不要把它伪装成旧 spec 的“维护”。
- 触及长期跨任务决定，且项目已启用 ADR：按 ADR 规则新增或取代 ADR。**不是每次需求变化都写 ADR**；ADR 也不代替后续 spec。
- 实施后形成的当前事实，更新现状文档的 owner，并从 issue / PR 链过去。旧 spec 仍回答“当时批准了什么”。

项目若已有归档或状态体例，沿用原体例；“冻结”约束的是获批正文，不禁止状态、勘误标记和链接等少量元数据更新。历史 spec 不做批量迁移。

## 三、项目怎样采用，怎样让执行型 agent 不容易漏

项目级采用时，只需在项目指令留**一条指向本备忘录的入口**，并在项目自己的文档规则页写清：现状文档、spec、ADR（若启用）、issue / PR 各自的实际位置与 owner；已有规则不复制到这里。新规则从采用之日起向后执行。

派实施任务时，在 issue 或任务说明里写出**允许改的文件 / 文档 owner**。没给文档 owner 时，执行型 agent 先报告发现和建议，不自行新建“第二份真相”；若发现需求与基线不符，按上面的边界分流，边界或新需求尚未获用户确认时暂停受影响实施并问清楚。ADR 是否需要写，仍按项目已采用的 ADR 规则判断，不与后续 spec 二选一。

优先用少量机械检查兜住高风险、能明确判定的错误，例如既有获批 spec 正文被改、同一事实出现第二份正文、活文档引用已归档记录却未标注。检查只对新变更生效；无法可靠判定的“文档是否真实”仍需实测和人工判断。不要为了落实本备忘录默认增加模板、全仓迁移或一套大型 CI。

## 四、让现状文档少而新

现状文档是四种记录里唯一要跟着系统改的一层；它越少、越短，腐化和返工就越少。

- **一个子系统一份现状文档**：同一子系统的现状只写在一份正文里，不再按「机制 / 数据 / 升级」拆成几份各讲一部分。脚本、工具旁的使用说明留在代码旁，由这份现状文档链接过去。
- **写明核对时间**：头部写最后一次对照实物核对的日期和方式；项目也可以改用工具按最后修改时间提醒，二选一，别两套并存。超期没核对的，读者先实测再用。
- **易变的数字不写死**：行数、表数、版本号、地址、进度这类会变的事实，正文写能查到它的命令、SQL 或生成来源，不手抄数值；正文只写相对稳定的结构、机制与约束。
- **agent 默认读序**：执行型 agent 默认只读现状文档和生效中的 ADR（若启用）；spec、调研、事故复盘只在追溯「为什么、当时怎么定的」时才读，和现状文档冲突时以现状文档与实测为准。项目采用时，把这条读序写进项目指令入口——只写在文档规则页里，平常干活的 agent 读不到。
