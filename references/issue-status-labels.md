# 备忘录：用标签记住每个 issue 卡在哪

> 这是可选备忘录，不改变 spec-flow 两段流程的步骤与顺序（采用后第 9 步的「回填」多两件小事：换阶段标签、按阶段决定关不关单，见 §四），默认不启用。只有用户明确要求采用，或项目规则已经声明采用，才按它执行；不因项目 issue 多就自动启用。采用动作见 [〈应用到项目〉§九](apply-to-project.md)，本仓不维护采用项目名单。

适用场景：每个 issue 都带验收，单一多，就记不住每个单卡在哪、该谁动、哪天再看——有的做了一半，有的等上线，有的等验证。上线后的观察期不归功能单，见〈上线时分拣〉。本备忘录用两类标签 + 一行日期回答这三件事。

## 一、两类标签

### 阶段标签（一个单只挂一个）

顺序：未开始 → 进行中 → 待测试 → 待上线 → 待验证 → 关单。多数单上线后直接关单，不经过「待验证」。

| 标签 | 意思 | 下一步谁动 |
|---|---|---|
| 未开始 | 开了单还没动手；挂账、待复现、待评估都算 | 谁认领谁动 |
| 进行中 | 已动手，改动还没合进主干（含本地单测、PR 在审） | 做的人 |
| 待测试 | 已合进主干，等发到测试环境验 | 做的人（发测试环境、验） |
| 待上线 | 测试环境验过（或这个单不需要测试环境），等发到生产 | owner 同意后发版 |
| 待验证 | 已上线，还剩只能在正式环境、由我们自己动手验的验收项（见〈上线时分拣〉） | 做的人，到「下次看」那天去正式环境验 |

为什么切在这五步：每步的交接人不一样（认领 / 改代码 / 过测试 / 发版 / 去正式环境验），阶段标签就是把「下一步该谁动」写成一行字——切错地方，标签就指错人。

「未开始」要显式挂：没挂阶段标签的单一律当漏标，不当「没开工」——否则分不清是没开工还是忘了标。

### 卡点标签（可叠加在任何阶段上）

| 标签 | 意思 | 什么时候摘 |
|---|---|---|
| 等拍板 | 卡在 owner 做决定 | 拍完就摘 |
| 受阻 | 卡在外部条件：环境不通、依赖别的单、时间窗未到。上线后等外部方或观察期不算受阻，按〈上线时分拣〉转出 | 条件满足就摘 |

为什么卡点不做成阶段：被卡住的单挪进单独一格，就丢了它原本走到哪一步，而且容易被遗忘；原地加标记，阶段信息和「卡住了」两样都在。

### 特殊情况

- **不需要某个阶段就跳过**：没有代码的单（排查、运维、调研）可以 未开始 → 进行中 → 关单；项目没有测试环境的，不用「待测试」，合并后直接进「待上线」；仓内即交付、不用部署的（文档、仓内脚本），合并后验收勾完就关单。
- **一单分多批、各批阶段不同**：挂**最靠前**那一批的阶段——下一步动作在那里；其余批次的进度写在正文进度段。
- **总单**：子单没全关前挂「进行中」；子单全关后，按总单自己剩下的验收走。为什么不能提前：子单还开着，总单的活就没干完，挂后面的阶段是假进度。
- **关单**：阶段标签和卡点标签都不用摘；重开时按实际情况重新挂。为什么留：重开时还得知道它上回走到哪，摘了重开就只剩一个空单。

## 二、「下次看」行

- 格式：`⏰ 下次看：YYYY-MM-DD · 看什么`，放在 issue 正文**第一行**（第 6 步说正文只放三样，采用本备忘录时多这一行——正文节序本就归项目定，见 `SKILL.md`〈项目体例与参考〉）。
- **必填**：「待验证」「受阻」。**选填**：其余有明确日子的单（如等拍板但有死线）。
- 受阻等的条件定不了日子时，也写一个复查日（比如一周后看条件满足没有），保证能排序。
- 到期看过、还没完 → 改成下一个日期；用 `gh issue edit <N> --body-file <file>` 改正文。

为什么放正文第一行：位置固定，机器能找到；评论只会往下追加，日期越埋越深，到了也没人想起来。

## 三、上线时分拣：剩下的验收项怎么办

功能单的使命到上线为止：上线后观察期、外部方什么时候来接、上线后出的问题，都不归它。

上线那一刻，对每条没勾的验收项问一句：**这条现在能不能由我们自己动手验？**

| 回答 | 怎么办 |
|---|---|
| 能（典型：测试环境验不了、只能在正式环境验的第三方对接，比如企微真发） | 留下：单子转「待验证」，写「下次看」行；验完勾掉，全勾就关单 |
| 不能（要等外部方来接、等观察期、等真实流量） | 转出：不勾，不留单；关单评论写「以下不在本单跟踪：…」，每条注明什么时候核对（比如「首个合作方接入时」） |

- 没有留下的项 → 上线即关单。
- 上线后出了问题 → 开 bug 单，挂原单链接，不重开原单。原单只在关错了（分拣判错）时重开。

为什么只问这一句：一句话的客观问句，agent 每次都会照着问；「拿不准就问用户」这种软规则，agent 几乎从不触发。

## 四、换标签时点

| 事件 | 标签怎么动 |
|---|---|
| 开单（spec-flow 第 6 步，或任何新开的单） | 挂「未开始」 |
| 认领（第 7 步） | 未开始 → 进行中 |
| 实施 PR 合并（第 9 步） | 进行中 → 待测试；不需要测试环境的 → 待上线；不用部署的 → 验收勾完就关单 |
| 测试环境验过 | 待测试 → 待上线 |
| 上线 | 按〈上线时分拣〉：有留下的 → 待上线 → 待验证，写「下次看」行；没有 → 关单，转出项写进关单评论 |
| 验收项全勾 | 待验证的项验完（转出项不算）→ 关单 |
| 需要 owner 拍板 | 加「等拍板」；拍完摘掉 |
| 被外部条件卡住 | 加「受阻」并写「下次看」行；解除后摘掉 |

谁来换：**做这个动作的 agent 当场换**，和回填 issue、勾验收项是同一步。owner 手动换也算数。

为什么绑在动作上：标签靠人事后想起来补，一周就和实际对不上；绑在已有的回填动作里，换标签只多一条 `gh issue edit <N> --add-label … --remove-label …`。

采用本备忘录的项目，第 9 步照旧回填（勾验收项、评论一句「代码已合」、放锁），但两段流程总述里那句「合并后**关单**」改按上表走：还有阶段没走完的，不关单，只换阶段标签；上线后按〈上线时分拣〉，转出的项不挡关单。

## 五、盘点

- **触发**：用户说「盘一下 issue」「issue 盘点」等。
- **只读**：`gh issue list --state open --limit 1000 --json number,title,labels,body,updatedAt`，不改任何标签。
- **输出顺序**：
  1. 到期：「下次看」日期 ≤ 今天
  2. 等拍板
  3. 按阶段分组：待验证 → 待上线 → 待测试 → 进行中 → 未开始；卡点标签在单子旁注明
- **可疑清单**（都能机械判定）：
  1. 没挂阶段标签
  2. 同时挂了两个以上阶段标签
  3. 「待验证」或「受阻」但正文第一行没有「下次看」
  4. 「下次看」行格式不对（日期解析不了）
  5. 同一阶段 14 天没有任何更新（可能已经往前走了、忘了换）；项目可在自己的指针节改这个天数
- **修**：盘点只报不改；要批量改标签，先把清单给 owner 过目、同意后再动——改远端 issue 是对外可见的操作。

盘点要用户开口才跑，不会到期主动提醒；要主动提醒得另加定时任务，本备忘录不含。

## 六、项目怎样采用

- 通过〈应用到项目〉的附加描述 `issue-status` 采用：建 7 个标签、问清有没有测试环境、在项目指令留一段指针。步骤、标签颜色与描述、指针节模板见 [〈应用到项目〉§九](apply-to-project.md)。
- 项目指令里只留指针和本仓的差异（有没有测试环境、盘点阈值），不复制本备忘录正文。
- 从采用之日起向后执行；**老单不自动迁移**。语义重叠的旧状态标签只报告；要迁老单另开 issue，迁移清单先给 owner 过目再改远端标签。
