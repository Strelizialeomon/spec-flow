原文：

原文：

## R10 体量护栏：为什么要预算、数字怎么来、红了怎么办

来源：#37 专项 spec `docs/specs/2026-09-26-skill-md-slim.md`（背景、调研表、D4 / D5）。现行预算数字**以 `scripts/check-docs.sh` 顶部为准**；下文出现的数字是定预算时的历史记录，改预算时改脚本、并在这里补一行历史。

**红了怎么办**：先别调预算。新增的案例 / 统计 / 来龙去脉挪进本档案、编新 R 号，规则旁只留一句理由 + 指针；同一条规则在多处重述的，合并成一处完整陈述，其余处改成按名指向。

**为什么要护栏**：
- 技能被调用时正文整份进上下文、之后不再重读；Claude Code 自动压缩后每个技能只重挂最近一次调用的前 5,000 token，越靠后的规则越先丢。所以「例外」「闸」前置，体量也要压。
- 增长（逐提交实测，各取当日末次提交）：09-10 1,386 → 09-16 4,712 → 09-21 6,064 → 09-24 10,233 → 09-26 10,497 字。09-21 至 09-26 六天净增 5,785 字，日均约 960——没有护栏，瘦完几天就涨回去。

**预算数字怎么来的**：spec 原定 8,000（目标约 7.5k、留约 500 余量）。实施时严格按 B 档（不删规则、不改判据语义，只挪案例、去重、缩非流程节、重排、收敛强调）瘦完，实测正文 8,586 字（补回原文细节、按实施期轻审修订后定稿 8,776），超出原预算；owner 2026-09-26 卡片改为 9,000（定稿余量约 220），不靠改写规则文字去凑数。2026-10-04 加〈已合并的 spec：动正文先问〉一节会超 9,000，owner 卡片选「先落闸，重构另开」：临时放到 9,200（插入后 9,157），待主文件重构 spec 收回（#51 专项 spec `docs/specs/2026-10-04-merged-spec-edit-gate.md`）。同日 #56 重构：用 `claude -p` 差值法实测正文 9,161 字 = 8,118 token，压缩后只保留前 5,000 token，截断点约在第 5 步「改表格」那段，其后的第 6 步、段二、参考目录在长会话里会丢；重构后正文 4,168 字 / 3,585 token，预算改为 5,000 字（约 4,300 token，每字 0.86 token），离截断线留约 700 token（#56 专项 spec `docs/specs/2026-10-04-skill-md-restructure.md`）。字数口径 = frontmatter 结束行之后到文件末的全部字符，每行计换行（等价 `tail -n +5 SKILL.md | wc -m`，UTF-8）。

## R11 审核结论贴 PR 评论、改不改问用户（闸·gate-details §一）

来源：#41 专项 spec `docs/specs/2026-09-28-review-comment-and-revision-card.md`（背景、D4、D5、D8、D10、D11、D14）。

**现状（2026-09-28 实测）**：

**owner 拍板（2026-09-28 对话，卡片记录）**：三条机制全要；修订卡只问一次整体「改 / 不改」，不逐条标推荐；评论审完立即贴一次，处置照旧记进 spec 末尾「审核修订记录」表，不再回帖。

**为什么「原样」**：不改写、不删条、不降严重度——主 agent 转述会过滤或弱化对自己不利的发现。可加一行头（日期 · 档位 · agent 数 · 严重 / 一般 / 提示计数），沿用 #35 的「审核留档」头。「审核结论」含变异结果（重审 + 变异档），一轮一条评论、多个 agent 分节。

**为什么零发现不摆卡、「不审」档两样都免**：零发现没东西可改，摆卡只会让「没答不合并」把一张空卡变成合并的卡点；评论照贴（写「0 条发现」），证明审过。「不审」档没有审核 subagent，也就没有审核结论可贴、可问。

**为什么没答不合并，却不和闸卡「没点 → 不审、不阻塞」矛盾**：两张卡问的东西不一样。闸卡问的是花不花审核成本，不审是正当选择；修订卡问的是已知问题留不留，没答就合并 = 带着已知问题静默进主干。同理，「只含 spec / 文档的 PR 合并长期授权」只管合并动作要不要再问，不替用户回答修订卡。

**owner 拍板（2026-10-04 对话，卡片记录）**：agent 先提三个机制（开工先分流 / 冻结点 / 新旧两份互指），owner 否：「我觉得没那么麻烦，加一个闸口，如果 agent 拿不准到底是改老的 spec 还是新出 spec 就问用户，不要自作主张就好了」。agent 指出「拿不准才问」拦不住当次情况（那次 agent 并没有拿不准），owner 选客观触发「改已合并 spec 正文就问」。

**为什么免问「往末尾审核修订记录追加」**：实施后往 spec 末尾回填实施期审核记录是记账、不是改需求；不免的话每次回填都要多点一次卡。

## R19 可选备忘录采用契约（`references/apply-to-project.md` §十；主文件·项目体例与参考；三个备忘录的「采用口径」区块）

**现状（改动前实测）**：三个选修备忘录各写各的采用口径——ADR 在「三种使用状态」、文档生命周期散在 §三、issue 标签在 §六；`SKILL.md` 参考表里只有 ADR 行写了读取条件（且只写「用户明确要求本次」），另两行只写用途；`apply-to-project.md` 有三个注册修饰词，却没有任何一处写明「一个修饰词必须声明哪些采用元数据、执行时点、验收方式」。后果是新增备忘录只往 `references/` 放正文，就成了「仓库里有正文，agent 平时不知道它存在」。

### 采用链对照案例：ADR 从「有文档」到「主动执行」

**历史快照（2026-10-14 / 15）**：以下对照两个采纳仓的真实任务片段——一个是单入口 H5 项目（下称「单入口项目」），一个是多域 monorepo（下称「多域仓」）。本节依据的实测原件均不公开链接——文档与提交在采纳仓（私有），会话回读在本机会话记录；本节只描述形态，不指名项目，也不把任何仓永久分成正面 / 负面或建立采用名单。它补充 R19 的依据，不新增规则、固定闸或脚本；项目资产边界仍见 R21。

**先纠正归因**：起初把多域仓的不顺归因为「没有 ADR 检查脚本 / 固定三时点 Gate」，证据不足。单入口项目同样没有额外的 ADR 触发脚本、Hook 或固定闸，却有一次真实任务主动落 ADR 的记录。应比较的是「入口是否可达 → 拍板后动作是否明确 → 结果能否被下一任务找到」，不是脚本多少、ADR 文件多少或项目大小。

#### 正面快照：拍板后主动把决定接成 spec + ADR

2026-10-14 一次 H5 视觉改版，回读当时会话（下列时间均为北京时间）：用户在 **10:42:11** 说「demo方案过了，请你进入实施」，没有在这次答复中追加写 ADR 的提醒；agent 在 **10:42:33** 主动说明正式实现前先落 spec + ADR，随后在 **10:43:43 / 10:44:05** 分别写入两份文件。该次文档 PR 最终同批交付新 spec、新 ADR 和旧 ADR 的取代元信息。

为什么这条链能工作：

- **入口不只是声明制度**：当时的项目指令已写成动作——开工搜生效 ADR、用户拍板命中条件后继续设计前写、与 spec 同一文档 PR、只链不抄。中央给判断口径，项目给持久入口，agent 在这次任务里主动执行；不是项目自行实现了一个自动识别器。
- **本次变化有明确对照对象**：该次改版替换了已有的视觉决定，新 ADR 写出适用范围和取代关系，不只是把用户的话抄成笔记。
- **交付物会把决定带到下一任务**：spec 头部区分本次新增、沿用、被取代的 ADR。实施者经 issue → spec → ADR 能继续消费，不依赖原会话记忆。

**证明边界**：这是一次主动执行的正例，不是该项目永远不漏的保证。单一根入口、连续任务中反复引用既有 ADR，有利于看见约束，但没有对照实验能把成功单独归因于文件短、项目小或某个模型。

#### 负面快照：旧入口能查旧决定，写新决定的动作不完整

2026-10-15 一次删除对外接口可选返回字段的改版中，用户在拍板里补上「删概念，这就需要写 ADR 了，我们改系统决策了，然后完全删除这部分代码」（会话原答把 ADR 拼作 `ard`，规格按语义记为 ADR）。该次原始规格的 §1.1 / §1.3 保留了这条提醒。

当时可核的弱点：

- **任务基线的根指令**主要要求开工查已有 ADR、冲突时以 ADR 为准、决定必须来自用户拍板；没有把「拍板后何时新增 / 取代」写成明确动作。**消费已有决定的要求在，创建新记录的连接偏弱。**
- **同一基线的 spec 模板**没有统一 ADR 处理字段，相关结论容易散在不同节或使用不同叫法，收尾时不容易分辨「已判断不需要」还是「忘了判断」。
- 多目录启动还有入口可达性风险：**当时的域指令**已记录先读根规则的要求。**这是额外风险，不是该次人工提醒的已证实原因**；不能仅因项目有多个目录，就断言那次 agent 没读根规则。

**时间边界**：人工提醒发生在 **2026-10-15 15:29**；标准「已启用 ADR」入口由 **15:34 的提交**补齐。入口补齐后两仓核心动作已接近，不能继续拿旧版本证明新版本「没有写入要求」。

**证明边界**：这条负例记录的是用户仍在承担流程提醒，以及当时入口、载体的薄弱处。用户把业务选择和 ADR 提醒放在同一次拍板里，不能据此证明「若不提醒，agent 必然漏写」。两个检查脚本此前实装后被主动删除是真实历史，但不是已证实的失败原因；把它们恢复更不是单入口项目的正例所要求的条件。被删的治理指南也不等于活入口断链，当时入口页的相对链接实测可达。

#### 修复后的快照：靠 Markdown 接回动作，而非恢复脚本

多域仓的一次入口修复 PR 对齐两段流程入口与五个子目录入口，把搜索、拍板后写入、收尾核对融进日常流程；spec 模板补「生效 ADR / 本次 ADR 处理」。没有恢复两个检查脚本，也没有另设固定闸或为本次治理写 ADR。

验证分两层，不能合成一句「全自动已解决」：

- **受控演练**：那次修复 PR 的正文记录已有决定、重复拍板、形成新决定、不应记录四场（A / B / B2 / C），均无需补提醒。模拟拍板未写入真实 ADR；演练上下文仍含主仓旧指令、agent 另外读取了新文件，所以它们证明的是「读到新文本后的动作」，不是全新会话自动加载已解决。
- **子目录真会话**：随后补做的一次真会话验证从某个子目录启动 Claude Code，首次输入只有「我要给对外接口加一个筛选字段，先看看怎么开工」。记录中第一动作即读根 `AGENTS.md` 并加载 spec-flow，随后搜索 ADR、识别已有边界，停在真正的业务岔路上问用户，无需提示「先读根规则 / 先查 ADR」。它验证的是该客户端、该次启动条件下的执行，不是根规则已自动继承；Codex 客户端仍未覆盖。

收益限于证据：**该次入口修复 PR 未新增检查脚本，ADR 侧仍无脚本（同日该仓另加了一个只管 Markdown 表内列数的检查脚本，与本次决定无关）；四场受控演练和一次子目录真会话留下了无补提醒的记录**，不把一次成功写成所有任务、所有客户端的永久保证。

#### 好与坏指的是哪种采用形态

| 好的形态 | 坏的形态 |
|---|---|
| 入口能到达当前会话，并写清采用后何时做什么 | 只有制度名称、目录或链接，后续动作靠想起 |
| 用户只拍业务取舍，agent 按已有判据主动记录 | 用户还要承担「该查 / 该写 ADR」的提醒 |
| spec 分清沿用、新增、取代、不需要及理由 | 文件存在，却看不出是否判断过、约束是否仍有效 |
| 下一任务沿链接找到现行决定，不复制正文 | 决定只在旧会话、旧 spec 或重复正文里 |
| 用实际动作证明入口有效，并注明未验范围 | 以文档检查全绿代替行为验证，或把一次成功当永久保证 |

**可复用的教训**：保留最小但完整的「采用声明 + 持久入口 + 执行时点 + 产物链接 + 行为证据」，既不把选修变必修，也不把脚本当作自然执行的前提。这是 R19 / R21 的案例解释，不额外增加流程步骤。

## R21 默认项目资产边界与可执行资产升级闸（`references/apply-to-project.md` §十；主文件·应用到项目；三个备忘录的「采用口径」区块）

来源：2026-10-15 低副作用边界与 PR 关单语义 spec（`docs/specs/2026-10-15-script-boundary-and-issue-close-semantics.md`，PR #77 合并，实施 issue #78）。

**为什么要有这条边界**：采用动作原本只写 Markdown 入口，但备忘录正文里常有「加个 CI 才能拦住漏项」这类话——照着做，一次采用就把项目的维护面从一行指针扩成一堆可执行资产，而用户以为只是「启用了某个备忘录」。所以默认集合收成两类：文档入口，和 §十 登记表「项目资产」字段里写明的资产；**字段是机械检查（R20）认的登记面**，与「未登记 = 未生效」是同一把尺——想让它进默认集合，先改登记表并过用户，而不是在实施时顺手建。

**为什么留升级闸而不是一刀禁**：确有备忘录只能靠脚本 / CI 落地。闸的形状取「停下来给五个字段（路径 / 问题 / 触发 / 维护成本 / Markdown-only 替代）」，是因为用户否决一件事需要的是成本，而不是一句「需要加脚本」；同意只授权本次列出的路径，防止一次同意被扩成长期任意脚本写入权。用户不同意时的三条回落（Markdown-only、入口写明人工执行、报告写明「没有机械拦截」）针对的是同一种假绿：把「脚本没加」说成「检查已通过」。

**字数账（2026-10-15 逐字符实测，口径同 `scripts/check-docs.sh`：每行含换行）**：`SKILL.md` 正文 **4,995 → 4,984（净 −11）**，预算 5,000 不上调，警示符仍 3 / 3。加两处：第 9 步·回填 PR 关联句 **+83**、〈应用到项目〉边界句 **+23**（该句同批把五步枚举改成「五步流程照 … 执行」）；腾四处：主线句删「方案期六步 / 实施期三步」**−21**（六步与三步就在下方列表里）、「多份叠加」删批次卡半句 **−28**（细则在 `references/gate-details.md` §三）、拆分节删重复理由句 **−19**（依据指针所指的 R15 里就有）、〈项目体例与参考〉删两份参考节枚举 **−49**（枚举都是 `references/` 文件自己的节标题）。腾挪只删与 references 重复的句子，不动规则语义。

## R22 PR 关联 / 关单：默认不用自动关单关键词（主文件·第 9 步·回填；`references/issue-status-labels.md` §四）

来源：同 R21 的 spec（§3.4 / §3.5）。

**为什么**：GitHub 的 `Closes` / `Fixes` / `Resolves` 在 PR 合并那一刻自动关单（官方口径：认 `close/closes/closed`、`fix/fixes/fixed`、`resolve/resolves/resolved` 九种写法，大小写不敏感、可带冒号，另有跨仓写法 `Fixes owner/repo#N`——所以规则正文的简写只是代表，判据是「GitHub 认不认」，范围写在 `references/issue-status-labels.md` §四）——而第 9 步的回填和 issue-status 的上线分拣（R14 / R18 的下游动作）都发生在合并之后，关键词一写，这些动作全被跳过，issue 从此不再有人回看。默认文案取中性的「关联 issue：#N」：它照样把两边连起来，但关单必须由第 9 步显式执行。

**为什么留例外**：用户明确要求「本 PR 合并即关单」是正当需求。例外必须针对本次具体 PR，且 PR 正文与收尾报告都记下「这是一次明确例外」和被跳过的回填动作——不记，例外就会变成默认。项目自带的 PR 模板若已含关键词，只报告副作用、不擅自改写——那是项目 owner 的资产，与 §十 登记表「旧物处置」字段同一条线（细口径见 `apply-to-project.md` §七）。

## R23 主文件再瘦身：细则归位与常驻预算（主文件·各步要点；`references/done-criteria.md` 新建）

来源：#87 spec（`docs/specs/2026-10-16-skill-md-restructure-for-code-map.md`），2026-10-16 实施（PR #88）。

**为什么**：`SKILL.md` 正文已到 4,982 / 5,000 字符，余量 18，**新规则无处可放**。5,000 是自设的**字符**预算（`check-docs.sh` 顶部，约 4,300 token），存在的意义是离 R10 记的「会话压缩后每个技能只重挂前 5,000 token」那条截断线留约 700 token 的余量——超预算不是当场被截，而是**离截断线越来越近**。所以往下加规则不能靠上调预算，只能先腾地方。

**做了什么**：把〈各步要点〉里「完成标准 / 观察式收尾 / 例外」三 bullet 的细则移进新建的 `references/done-criteria.md`，正文留判据与限定（三类例外的枚举、须替代不了、须用户点头都留在正文）；「拆分大 spec」段保留全部判据（同批不算止损、甩不掉的、审查并入），只把列定义指向 `split-large-spec.md`。**主干九步、卡片总表、闸、豁免总表、工作区与锁五块一字不动。**

**实测账**（口径与 `check-docs.sh` 相同：frontmatter 结束行之后到文件末，含换行；由脚本从两版 `SKILL.md` 实算）：**4,982 → 4,952，净腾 30；余量 18 → 48**。分节：各步要点 1,372 → 1,258（−114；其中「完成标准与长尾验收」段 381 → 266，拆分段 232 → 233），〈项目体例与参考〉926 → 1,010（+84，含参考表补 `done-criteria.md` 一行、以及声明两份效例外）。

**spec 期预估错了，连错两次，记在这里**：spec 期估「归位约省 404、余量 ≈540」，实施中先被实测推成 177，**实施期重审又发现连 177 都是错的**（真实 48，且随抓回判据三次变动：4,823 → 4,924 → 4,952）。**三个数没一个是脚本算的**，全是口算——而本条要记的教训恰恰是「可实测的数必须用脚本实测」。根因有二：① 把「外移后应有的长度」当成「省下的量」；② 把已含的补行重复计入。**这条自己就是反面教材**：规矩写下「别口算」的当天就违反了它。实施时按 R18 的口径「腾不到就停下问用户」，摆卡后用户裁决按实测下调阈值：**≥400 → 48**。

**为什么三类例外枚举留正文**：卡片总表「例外卡」行（`SKILL.md` 卡片总表）写着「属三类例外之一」，且该块本次冻结不动。若枚举只在 `done-criteria.md`，冻结行会引用一个正文里查不到的定义——判据与它引用的定义不能分层。

**重审补回的三条**（首轮压缩时被我默默压掉，重审抓回，属实质错误）：① 机制清单的「没有就写「无新增机制」」——这条一丢，无新增机制时 agent 无从知道要表态，而 `gate-details.md` 仍按「缺任一 = 违规」判；② 拆分段的「必须同批合入 / 发布不算止损」「甩不掉的」「审查并入现有规格符合性检查」三处判据；③ 例外条款的「模拟时间或数据回放替代不了的」「用户点头才纳入」两个限定。**教训**：压缩「措辞」与删「判据」在 diff 里长得一样，回归清单必须逐句对旧文本，不能只对上一次的清单。

## R24 代码地图织进流程：总则一句 + 三处挂点，不新开章节（主文件·主线总则 / 第 3 步 / 闸·不审档 / 项目体例与参考；`references/code-map.md` 新建）

来源：#90 spec（`docs/specs/2026-10-16-code-map-woven-into-flow.md`），2026-10-16 实施（PR #91）。**试用性质**：用户在一个真实业务项目上验过后再定去留。

**为什么不是「加一节」**：用户要的不是「多一份代码地图文档」，而是**地图成为流程的一部分**——agent 在用它那个动作上就该想到它。实测对比：加一节 **212 字符**（正文多一个孤立的单元），织进去 **109 字符**（总则一句 + 三处挂点，长在已有动作上）。**省 103 字符，且读起来是流程不是文档。**

**四处挂点各挂在本来就存在的动作上**：主线总则（动笔前查图）、第 3 步（改动面先查图再落笔）、闸的「不审」档（agent 唯一自己拿 diff 对账的档位，正是「谁受影响」最该用图的时候）、参考表（细则入口）。**不挂**第 1、2 步（需求未成形，查图先于需求）、第 7、8 步（同一动作已被总则覆盖，重复会稀释）。
