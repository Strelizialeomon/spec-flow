## 开单前：体量评估与用户选择

**位置**：既有第 3 步里，需求确认、spec 草案成形后评估并摆拆分卡；第 6 步开单前只核决定是否仍适用。结构未变不重问；范围、实施里程碑或依赖等结构实质变化后重新评估、让用户重选，普通文字修订不重问。

### 评估与拆分卡

- 结合实际改动面说明交付目标、实施阶段、影响范围、依赖和可形成的中小交付单元，不仅凭行数、文件数、固定工时或会话长度设硬阈值。
- **多阶段必须提醒**：有多个需要分别推进、验收或重新安排节奏的交付里程碑就算，即使没写“阶段”。通常推荐拆；若确实不可分，推荐不拆时解释原因。编码、测试、提 PR 的普通步骤，以及开始 / 合入 / 发布三项就绪，本身不算多个实施阶段。
- 始终给“拆”和“不拆”两个选项，推荐项在前。先列真实候选子件、各自成果与范围、还保留哪些阶段及依赖、哪些可并行和哪些需先后，不能只摆一个没有拆法的空选项。
- 卡上给实际数量和代价：拆成 N 份 = 1 总纲 + N 份执行 spec + N 张执行 issue + 1 张仅跟踪的父 issue；不拆 = 1 spec + 1 执行 issue，说明仍保留哪些阶段。工期估计不能说成实测。
- 未选择就不定最终结构、不开执行单；不默认拆或不拆。结构选择不替代机制卡、改旧 spec 卡或审核档位卡；已合并 spec 正文要改，仍先走改旧 spec 卡。

### 选择后的体制与开单

**选拆**：总纲保留总体目标、共享约定、交付物地图和依赖台账；具体实施目标、边界和验收移入中小子 spec。默认每份执行 spec 聚焦一个完整可验收成果，带相关实现和测试，配一张执行 issue；不按章节或机械地按前后端切，也不限定一次会话、一次提交或一个 PR。

子件仍有多阶段，**同样再次提醒，由用户选再拆或保留**；可在同一轮选择里逐份说明，不对同一决定重复摆卡。总纲不重复保留所有子件的实施正文，不另开一张重复执行全范围的大单。尽可能并行是优化目标，不要求所有份同时开始、独立合入或独立发布。

**选不拆**：保留 1 份 spec、1 张执行 issue，记录用户的明确选择、保留的阶段及原因；不能偷偷改为大 spec 下的多张阶段执行单。用户选不拆不豁免已知阻断问题、必要依赖或验收的说明。

本次结构覆盖的总纲与执行 spec 定稿、**按份过闸并合并后**，才开父 / 子 issue。每张执行单锚对应 spec 永久链接，正文仅必要关系、改动面及未勾的验收要点，不复制全文。已合并的前置 spec 尚未实施，不妨碍先开后续 issue，开工按明确的就绪条件；不能把父单关闭当作所有子件开工的前置。

## 1. 交付物地图

设计权威留在总纲；放一张**交付物地图**，每行一份子 spec。它取代旧「拆分地图」（旧表 份 / 文档 / 范围 / 发布序 对应新表的子 spec、产出和波次 / 就绪判断），不另建重复进度台账。至少七列：

| 列 | 写什么 |
|---|---|
| 子 spec | 稳定组标识与子件编号、文件链接；issue 链接按既有回填规则机械补齐 |
| 产出 | 对外提供的接口、数据、配置、代码或文档结果 |
| 消费 | 要用到的上游产物；没有写「无」 |
| 文件 owner | 独占文件 / 目录，每个共享件只定一个 owner |
| 不碰 | 明确不修改的文件 / 目录 |
| 开始 / 合入 / 发布 | 三项各自能不能独立（判据见第 3 节），以及卡住它的依赖边 |
| 波次 | 由硬依赖推出来的执行波次（不是时间表或子件身份） |

## 2. 依赖台账

同样放总纲，子 spec 只引用与自己有关的行。**每条边必须有方向**——禁止只写「互相依赖」。

| 列 | 写什么 |
|---|---|
| 提供方 → 消费方 | 谁产出、谁要用 |
| 类型 | 契约 / 数据 / 配置·运行时 / 发布·验收（四类见下） |
| 产物 | 具体到接口、字段、事件、配置键、迁移结果、验收项或发布动作 |
| 就绪条件 | 什么事实成立后，消费方才可开工 / 合入 / 发布 |
| 验收证据 | 测试、文件、命令、截图、链接或人工确认 |
| owner | 对这个产物可用性负责的那一份 |
| 波次 | 这条边挡哪一步、挡在第几波 |

四类依赖：

- **契约**：API、函数签名、事件、CLI 参数、返回结构等调用约定。
- **数据**：数据库表、字段、迁移、文件格式、枚举值、缓存键等数据约定。
- **配置 / 运行时**：配置键、环境变量、特性开关、权限、部署资源或运行时顺序。
- **发布 / 验收**：必须同一批上线、跨端一致、共同验收，或必须由收尾份完成的条件。

两条纪律：

- **文件共享不是语义依赖**——同一个文件两份都要动，仍按旧做法 2、4 办（独占 + 一个 owner），别把它伪装成一条边；但如果既有文件共享又有接口依赖，两类都要记。
- **同一个判定只许一个 owner**（2026-09-22 实测）——两份各写一遍「同一个判定」，就是两条边指向同一产物而 owner 有两个，它会静默漂移：那天一份只认 `is_active = 1`、另一份只判「按姓名查得到行」，那家机构被静默挂空，预览、列表、审计里都没提示，拖到实施期才炸出来。

## 3. 开始、合入、发布三项就绪判定

每份在交付物地图里**分别**给出三项。它们不是一个 spec 的三个实施阶段，也不是拆分的全独立准入门槛。契约或测试替身明确后可并行开发；确有前置产物就保留先后，运行时互相调用不自动等于实施循环等待。

- **独立开始**：不等别的份合入就能开工；可以有前提（已冻结的契约、明确的 stub、测试夹具），但前提要写进台账。
- **独立合入**：合主干时不需要另一份没合入的实现；靠兼容层 / stub / 先行契约提交的，把它们列成就绪条件与验收证据。
- **独立发布**：单独发布后不会留下没满足的调用、数据、配置或验收条件。**必须和别的份同批发布的，本项就是不满足**——出路是点名一个收尾份、登记成一条发布边（见第 4 节），不是含糊过去。

**波次由硬依赖推**：前置产物没满足就只能排后面的波次；没有硬依赖的份可以并行。软协调关系记在台账里，但不许伪装成硬前置，也不许拿它去堵不相关的份。

## 4. 依赖不清时先修拆法

**有清楚的单向前置不妨碍拆分**，同批合入 / 发布也不是退回大 spec 的理由。以下问题不能含糊带进实施：

1. 实施依赖有未解的环，A 等 B、B 又等 A。
2. 一个跨份产物有多个 owner，或者一个 owner 都没有。
3. 某份无法独立合入，既没有兼容层 / stub / 先行提交，也没有明确的同批合入安排。
4. 某份无法独立发布，又没有点名承担发布的收尾份。
5. 依赖只写“等另一份完成”，没有具体产物、就绪条件和验收证据。

先重划边界、确定唯一 owner，或抽清共同契约 / 基础 spec，再说明哪些能并行、哪些需先后。基础件也要有具体产物、边界和验收，不能把所有前置又塞成一个巨型多阶段 spec。

同批合入登记实施批次，合并审核仍按主文件及 `references/gate-details.md` 的既有批卡规则；同批发布点名收尾份，并登记依赖边。不能因此宣称各份独立合入 / 发布，也不以此一概否决拆分。

无法给出可行拆法，就报告卡点、让用户重选结构或调整范围；**不得自行退回“单 spec + 多实施 issue”**。明确前置不等于未知阻断，按第 3 节记录即可；真正未解决的循环或归属 / 条件缺失不因用户选不拆而消失。

## 5. 稳定身份、子 spec 声明与父子单

### 同组身份与声明

同一组采用仓内唯一、稳定的组标识，默认日期 + 主题短名，子件用 S01、S02。**编号是身份，不是波次**；不随排期改变重编号，取消后不复用。尊重项目现有命名体例，不批量改名旧文件。

总纲头部写组标识与角色“总纲”；子 spec 头部写：

```text
组标识：本组稳定标识。
角色与编号：子件 S01（示例）；目标是一个完整可验收成果。
总纲：总纲链接及适用的共享约定；草案可用相对路径，定稿用可追溯链接。
上游依赖：开始 / 合入 / 发布前必须满足的台账条目；无则写“无”。
下游影响：本份产出的契约、数据、配置或验收会被哪些子件消费；无则写“无”。
合入前提：合入和发布所需具体条件；不能只写“依赖总纲”。
```

本份边界和验收写在子 spec，相关实现与测试同属本份；跨份验收指明归哪份。共享约定只有一个正文 owner，其他份引总纲或契约 spec 的对应位置，不复制正文。多阶段仍须按〈开单前〉提醒并由用户决定，不以头部写了“单交付”代替实际核对。

以 `2026-10-18-order-export` 为示例组标识：总纲标题 `[2026-10-18-order-export/总纲] 订单导出`；子 spec 与执行 issue 同用 `[2026-10-18-order-export/S02] 下载结果`。文件名含同一组标识、子件编号，例如 `2026-10-18-order-export-S02-download.md`，目录结构沿用项目约定。地图的子 spec 栏链接它们，不另建一份进度表。

### 父子归属不等于执行阻塞

拆分组定稿合并后开 1 张 `[组标识/总览] 主题（仅跟踪）` 父 issue，链接总纲并把执行单加为原生子 issue。父单不重复执行全部范围、不承载额外开发或观察任务，也不认领为执行任务、不开 worktree。子单按既有完成标准完成、已分配的跨份验收满足后关闭父单，不改变子单生命周期。

父子关系只表达“属于哪组”。真正需要另一单完成才能推进，才建立 blocked by / blocking；不能因同组或编号顺序全部串行。只等上游部分产物、或仅影响合入 / 发布时，依旧以 spec 的具体条件说明，不能错误等待整个上游 issue 关闭。

开单前 issue 字段可写待开，不能假报已有原生关系；开单后按既有第 9 步机械回填相关链接。本机 CLI 参数先核帮助；需要时查官方 API。平台权限或工具不支持原生关系，就保留编号与双向链接、明确报告关系尚未建立，不能宣称已原生归组，也不擅自安装或升级工具。

## 6. 审核与开单时核什么

核对**并进现有的规格符合性检查**，不新增审核档位、agent 或派发路线；未选审核时由主 agent 自查，不自派（见 `references/gate-details.md` §一）。

先核所有 spec 的体量评估、真实拆法、推荐和拆 / 不拆选择；多阶段已提醒，子件仍多阶段也有明确选择，决定未过期。普通步骤与三项就绪不误当实施阶段；有先后依赖不当作不可拆，也不自动只拆 issue。未答或结构未定，不开执行单。

本次含多份子 spec 时再逐项核：

- 地图里每份有稳定身份、产出、消费、owner、边界及三项就绪；默认单交付，本份测试与跨份验收有归属。
- 台账每条边有方向、类型、具体产物、就绪条件、验收证据、owner 与波次；同一个判定只有一个正文 owner。
- 波次与硬依赖一致，硬前置不伪装并行、软协调不伪装阻塞；没有未解释的实施环，同批合入 / 发布已安排批次 / 收尾份。
- 子 spec 的上下游、合入 / 发布条件逐条对上台账；身份贯通文件、头部、地图和 issue，编号不当作执行顺序。
- 总纲和父单不重复执行，父子归属与阻塞分开；仅部分产物或发布相关，不误挡整个开发。spec 期核约定与待回填位置，开单后核实际父子 / 阻塞关系；原生关系未建如实报告。

“不审”档也核上述适用项，发现依赖、选择或映射缺项先报告，不能把不确定关系带进实施。

## 以前是这么干的（六条·文件地盘的参考）

每条都来自上面那些真实案例，标「#N」「实测」的都是真发生过的。
**这一节管的是文件地盘那半边**，仍以当时说定的为准；做法 3、5、6 的语义部分已由上面第 1~6 节接管。

### 1. 按施工面切，不按章节或行数切

判据是「这坨活能不能派一个 agent 独立读完、独立干完、独立验收、不碰别人的文件」。
#600 按「后端 / 爬虫 / 控制台 / 前端 / 文档 / 换皮」切，每份 57~89 行。

### 2. 每份写死「独占文件」和「不碰」

例：爬虫那份独占 `heartbeat.py`，明确不碰 `crawler/console/**`（控制台那份占）、`backend/**`（后端那份占）。
理由：这仓真并行多 agent、共享同一个 `.git/`，两份改同一堆文件 = 合并时照撞。

### 3. 切完排波次，不排时间表

波次由**硬依赖**推（判据见第 3 节），标的是「谁能跟谁并行、谁卡在谁后面」。
旧写法把「硬前置 / 可并行 / 必须同批合入」三档混在一句里——**已废**：能开工不等于能合入，能合入不等于能上线，三件事分开判（第 3 节），其中「必须同批合入 / 发布」按第 4 节办（指定批次 / 收尾份并登记成边，不算止损）。
例：#600 是 A → D → C → B；B 可以和 A 并行开发，但上线要随 C 同一批——这条就是一条发布边，收尾份是 C。

### 4. 共享件只能有一个 owner

能划给某一份的就划进去，其余份在「不碰」里点名。
所有份都得动的那个文件（实测那轮是全批共享的 `conftest.py`）划不出去，
改用「动它之前先在协作 issue 下评论声明」+ 合并前对表远端。

### 5. 跨份的账挂一个收尾份

每份挂自己的验收 checklist，跨两份的账（比如两端白名单要一致）挂到专门那个收尾份上。
#544 就是这么分的：每段挂自己的验收，跨段的挂 d 段。
这条同时是第 3、4 节里「必须同批发布」的**唯一出口**——不点名收尾份，那一项就判不合格。

### 6. 拆完再单独审一次「拆分本身」

过去是「在常规的单份 spec 审核之外，再加一轮只看文件地盘」。
现在**并进现有的规格符合性检查**：地盘只是其中一项，另外还有地图、台账、波次一致性、环依赖、子 spec 对账（清单见第 6 节）。
实测这仍是最值钱的一步：#544 拆 7 份时抓出「某块归 b2 会和节奏解析抢同一个 `config.py`」——纯地盘判断，单份 spec 审核永远看不见；2026-09-22 那轮也是靠它才把 ⑥/⑤ 之间没定的落库载荷键逼成一张契约表。

## 还有几条配套的

- **先合后分（历史做法）**：当时先写完整大 spec、自洽后再拆，目的是不让设计漂移。现行要求是先确认完整需求与共享约定，不要求先写一份巨型多阶段实施 spec 才能拆（见〈开单前〉）。
- **总纲不删**：保留设计权威、目标以及第 1、2 节的地图和台账入口；不表示把所有子件实施正文继续重复放在总纲里。
- **子 spec 头部**：按现行第 5 节写稳定身份、总纲链接和上下游 / 合入前提；“总 spec = 设计权威，本文是其子件 X”是旧模板表达。
- **每份自带“管什么 / 不管什么”两列表**，边界写死。
- **拆出来的每份各过常规闸**——档位由用户当场点，agent 不自派；本批结构覆盖的总纲与子件定稿、过闸合并后再开对应 issue。
- **尺寸**：过去落在 50~120 行（总纲 300~970 行）。纯观察值，不是硬闸。
- **并行认领的防撞**：唯一真相源是主文件 `SKILL.md`「工作区与锁」与 `references/worktree-lock.md`——锁由 git 保管、命名定死 `issue-<N>` 纯号，不认项目自定格式。
- **后加的份**：总纲拆完、子 spec 有的已经开工或完工之后，又一个新需求插进来要落同一块施工面，这份新增子 spec 会替掉已有份的文件 owner、「不碰」边界、交付物地图里的产出/消费/开始/合入/发布/波次，或依赖台账里的提供方/消费方/产物/类型/就绪条件/验收证据/owner/波次——**核对并更新总纲的地图和台账，再开它的 issue**。顺序：① 先在新 spec 草案里列它要接手的文件、交付物和依赖边，标出从哪份转移；② 对照总纲的地图与台账，确认本次有没有语义变更；③ 总纲还没合并就直接在当前草案里补齐地图/台账（改动碰的是草案，不摆卡）；总纲已经合并且确需改正文时，先摆主文件那张「改旧 spec 卡」；④ 按卡片结果更新当前权威记录——地图和台账要反映新的 owner、产出、消费、依赖边和波次，原 spec 的历史链接保留；若卡片选了「新开一份 spec」，那份里必须写明它怎么承接或取代原总纲的权威记录，别留下两份互相矛盾的地图/台账；⑤ 这一步做完，再开新增子 spec 的 issue，正文里链接总纲和新 spec（开 issue 的时机照旧——spec PR 合并之后、实施之前开，这条不改现有 issue 生命周期）。
  边界：不改变地图/台账的新份按普通流程走，不套这条；改变未合并总纲的，直接在当前草案补齐、照常开 issue；改变已合并总纲的，先摆「改旧 spec 卡」再按卡片结果更新；新份本身要提新流程机制的另开一份 spec，这条只管拆分地盘和依赖的记录；地图/台账更新只是机械回填的，照主文件豁免表判断，别当新流程。
  这是**参考做法，不是硬闸**——不进主文件、不绕过「改旧 spec 卡」和合并卡的用户选择。依据见 `rationale.md` R16。
