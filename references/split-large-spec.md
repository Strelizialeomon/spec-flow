## 什么时候会翻到这一页

spec 写出来太大、一份装不下，要拆成几份小的子 spec、几个 agent 并行实施时。

## 以前是这么干的（六条）

每条都来自上面那些真实案例，标「#N」「实测」的都是真发生过的。
**是参考，不是规矩**——真要拆的时候，以当时说定的为准。

### 1. 按施工面切，不按章节或行数切

判据是「这坨活能不能派一个 agent 独立读完、独立干完、独立验收、不碰别人的文件」。
#600 按「后端 / 爬虫 / 控制台 / 前端 / 文档 / 换皮」切，每份 57~89 行。

### 2. 每份写死「独占文件」和「不碰」

例：爬虫那份独占 `heartbeat.py`，明确不碰 `crawler/console/**`（控制台那份占）、`backend/**`（后端那份占）。
理由：这仓真并行多 agent、共享同一个 `.git/`，两份改同一堆文件 = 合并时照撞。

### 3. 切完排波次，不排时间表

标出「硬前置 / 可并行 / 必须同批合入」。
例：#600 是 A → D → C → B；B 可以和 A 并行开发，但上线必须随 C 同一批。

### 4. 共享件只能有一个 owner

能划给某一份的就划进去，其余份在「不碰」里点名。
所有份都得动的那个文件（实测那轮是全批共享的 `conftest.py`）划不出去，
改用「动它之前先在协作 issue 下评论声明」+ 合并前对表远端。

### 5. 跨份的账挂一个收尾份

每份挂自己的验收 checklist，跨两份的账（比如两端白名单要一致）挂到专门那个收尾份上。
#544 就是这么分的：每段挂自己的验收，跨段的挂 d 段。

### 6. 拆完再单独审一次「拆分本身」

就是在常规的单份 spec 审核之外，再加一轮只看「文件地盘分得对不对」的审核。
实测这是最值钱的一步：#544 拆 7 份时抓出「某块归 b2 会和节奏解析抢同一个 `config.py`」——
这是纯地盘判断，单份 spec 审核永远看不见。

## 还有几条配套的

- **先合后分**：设计阶段先写一份完整的大 spec，自洽了再拆。拆着写容易各写各的、互相漂移。
- **总纲不删**：原大 spec 留成总纲，补一张「拆分地图」表（份 / 文档 / 范围 / 发布序）。设计权威留在总纲，子 spec 只写落地、只指向它。
- **每份子 spec 头部写一行**「总 spec = 设计权威，本文是其子件 X」。
- **每份自带「管什么 / 不管什么」两列表**，边界写死。
- **拆出来的每份再过一遍常规的独立审核**——档位与派发照主文件 `SKILL.md` 第 4 步（**agent 不得自派，每次由用户点档**），然后各自开 issue。
- **尺寸**：过去落在 50~120 行（总纲 300~970 行）。纯观察值，不是硬闸。
- **并行认领的防撞**：唯一真相源是主文件 `SKILL.md` 第 6 步「认领与防撞车」——锁由 git 保管、命名定死 `issue-<N>` 纯号，不认项目自定格式。
